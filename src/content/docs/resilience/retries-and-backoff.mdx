## The question

Your code calls another service, and once in a while the call fails. So you do what everyone does:
if a call fails, try it again, up to three times. Most days that fixes every hiccup. Yet the same
three retries can turn a six-second slowdown of the other service into an outage that lasts until
someone steps in, with no more users than before. How can trying again keep a server down, and how
should you retry instead?

The short answer: when one call fails by bad luck, trying again works. But when the server itself
is struggling, every caller fails at the same moment and every caller tries again, so the server
receives the most work exactly when it can do the least. Safe retries do three things: they retry
only failures a second try can fix, they wait a growing and random time before each retry
(**backoff** and **jitter**), and they cap how many retries all requests together may add (a
**retry budget**).

## The idea in plain words

Follow one pair of services through one bad minute. An order service calls a stock service to ask
"is item 42 in stock?". The stock service runs on one server.

1. **What the server can carry.** The stock server can answer at most 100 requests a second. That
   is its **capacity**. Each answer takes 1,000 ms ÷ 100 = 10 ms of its time.
2. **A normal day.** The order service sends 70 requests a second. That is 70 × 10 ms = 700 ms of
   work in every 1,000 ms, so the server is busy 70% of the time. Requests that arrive while it is
   busy wait in a short line in front of it, and every answer comes back within a few milliseconds.
3. **The rule in the caller.** The order service waits at most 1 second for an answer. If none
   comes, it gives up on that try and sends the same request again, up to 3 more times. On a normal
   day this rule fixes the rare failure, such as a dropped connection, and nobody notices.
4. **A six-second slowdown.** A new version of the stock service is being rolled out, and for 6
   seconds the server runs at half speed: 50 answers a second. Requests still arrive at 70 a second,
   so the line grows by 70 − 50 = 20 requests every second. After 6 seconds, 6 × 20 = 120 requests
   are waiting, and that is before counting a single retry.
5. **Back to full speed, but too late.** The server is healthy again and answers 100 a second. A new
   request joins the back of a line of 120. It waits for the 120 ahead of it: 120 ÷ 100 = 1.2
   seconds. That is longer than the 1 second its caller waits, so the caller gives up and retries.
6. **The server does not know the caller left.** The request that was given up on stays in the line.
   When the server reaches it, it spends its 10 ms working out an answer that nobody reads. The retry
   joins the back of the line and waits more than a second too.
7. **The line feeds itself.** Now every request waits more than a second, so every try fails, so
   every request is sent 4 times: once plus 3 retries. 70 requests a second become 70 × 4 = 280
   attempts a second, against a server that finishes 100. The line grows by 280 − 100 = 180 every
   second. The server is at full speed and busy all the time, and every answer it sends goes to a
   caller that already gave up. It stays like this until a person steps in.
8. **A shorter slowdown would have healed.** Had the slowdown lasted 2 seconds, the line would hold
   2 × 20 = 40 requests, a wait of 40 ÷ 100 = 0.4 seconds at full speed. That is under 1 second, so
   nobody gives up, nobody retries, and the line clears.

The picture shows the loop: a retry goes back into the same line that made the first try too slow.
It also shows the fix. The order service needs a limit on how many retries all its requests may
add together, not only on how many each request may send.

**Waiting longer between retries does not fix it.** Suppose the order service waits 0.1 s before
the first retry, 0.2 s before the second and 0.4 s before the third. Each request still sends 4
attempts; they arrive a little later. Meanwhile new requests keep arriving at 70 a second, because
the people placing orders do not know the stock server is struggling. After a second or two the
server again receives about 280 attempts a second.

**A limit on the total does fix it.** Say retries may add at most 10% of normal traffic: 10% of 70
is 7 retries a second. The server then receives at most 70 + 7 = 77 attempts a second. It finishes
100, so the line shrinks by 100 − 77 = 23 every second. The 120 requests left by the slowdown are
gone in about 120 ÷ 23 ≈ 5 seconds. Requests that are refused a retry fail at once with an error,
which is the price: a few seconds of errors instead of an outage.

**And the retries must be spread out.** If the server restarts and drops the whole line, 120
callers see the failure in the same millisecond. If each waits exactly 0.1 s, all 120 retries
arrive together, 0.1 s later: 120 attempts in one instant, more than the 100 the server finishes in
a whole second.
Each caller should wait a random time instead, so the retries spread over the interval.

An everyday picture: a customer care line with one agent. Callers who wait on hold longer than a
minute hang up and call again. If the phone system kept every abandoned call in the hold queue, the
agent would spend the day picking up calls where nobody is on the line, while the real callers keep
hanging up and redialling. The picture stops working in one place: a phone system knows when a
caller hangs up and drops the call. A server usually does not know, and that is why the wasted work
piles up.

## The building blocks

Eight ideas carry the rest of the page. Each gets a plain sentence, the reason it exists, a small
example, and then its precise version.

### A timeout and a deadline

**What it is.** A **timeout** is the longest a caller waits for one answer before it gives up.

**Why it exists.** A server that never answers would otherwise hold the caller forever: its memory,
its connection, and a user staring at a spinner.

**Example.** The order service's timeout is 1 second. An answer that would arrive at 1.2 seconds
arrives to nobody: the caller stopped listening at 1 second.

**The technical version.** A timeout covers one attempt. A **deadline** covers the whole request,
every attempt and every wait included: "the user gets an answer or an error within 2 seconds".
Giving up stops the waiting, not the work. The server is not told, so it still does the work for the
abandoned attempt (the [timeouts page](/resilience/timeouts/) covers why, and how to pass a deadline
along).

### Attempts, retries and transient failures

**What it is.** An **attempt** is one try at a call. A **retry** is every attempt after the first.

**Why it exists.** Many failures go away on their own within a second. A failure like that is called
**transient**, and for a transient failure, trying again is the cheapest fix there is.

**Example.** At 10:00:00.000 a call fails because the connection was closed by a server that was
restarting. The retry, 100 ms later, reaches the restarted server and succeeds. One request, two
attempts, one retry.

**The technical version.** Typical transient failures: a timeout, a connection reset (the other side
closed the connection in the middle of a call), `503 Service Unavailable` and `429 Too Many Requests`.
A **permanent** failure is one a second try repeats: `400 Bad Request`, `403 Forbidden`, `404 Not
Found`, `422` for invalid input, or a bug in your own code. Retrying those only makes the failure
slower.

### Safe to repeat

**What it is.** A request is **safe to repeat**, or **idempotent**, if sending it twice has the same
effect as sending it once.

**Why it exists.** After a timeout you do not know whether the server did the work. It may have
finished a millisecond after you gave up. A retry repeats whatever the first attempt did.

**Example.** `GET /stock/42` twice reads the stock twice; nothing changes. `POST /payments` for
₹500 twice may charge ₹500 + ₹500 = ₹1,000.

**The technical version.** By the HTTP standard (RFC 9110), `GET`, `PUT` and `DELETE` are idempotent
and `POST` is not. A `POST` becomes safe to repeat when the client sends an **idempotency key**: a
unique ID for the operation, which the server stores so it can recognise the repeat and return the
first result instead of doing the work again (the
[REST API design page](/networking/rest-api-design/) covers which requests are safe and why).

### A waiting line (a queue)

**What it is.** A **queue** is the line of requests waiting for the server, served in the order they
arrived.

**Why it exists.** The server can work on a fixed number of requests at once. A request that arrives
while it is busy either is refused or waits; waiting is the queue.

**Example.** 120 requests are waiting and the server finishes 100 a second. The newest request waits
120 ÷ 100 = 1.2 seconds before the server starts on it.

**The technical version.** Order of arrival is called **first in, first out** (FIFO). A queue can
only shrink when requests arrive more slowly than the server finishes them, and the waiting time
grows sharply as the server gets busier (the
[latency vs throughput page](/foundations/latency-vs-throughput/) shows why). The server works
through the queue whether or not each caller is still waiting.

### Amplification

**What it is.** **Amplification** is how many attempts the server receives for each request the
callers wanted.

**Why it exists as a measure.** It is the multiplier retries put on the server's load. A server
sized for 70 requests a second has to survive 70 times the amplification.

**Example.** The order service wants 1,000 answers. 100 of the first attempts fail and are retried
once, and those retries succeed. The server received 1,000 + 100 = 1,100 attempts for 1,000
requests: 1,100 ÷ 1,000 = 1.1. In the outage, every request was sent 4 times: 4,000 ÷ 1,000 = 4.

**The technical version.** Amplification = attempts ÷ requests. With no retries it is exactly 1. With
up to *N* retries per request it can reach 1 + *N*, and it does so exactly when every attempt fails.
Part 2 works out the value in between.

### Exponential backoff

**What it is.** **Backoff** is a wait before each retry. **Exponential** backoff doubles the wait
each time, up to a maximum.

**Why it exists.** Retrying the instant something fails hits the same problem again: the restarting
server is still restarting. Waiting gives it time, and doubling the wait gives more time to a problem
that is lasting longer.

**Example.** Start at 100 ms: wait 100 ms before the first retry, 200 ms before the second and 400 ms
before the third. In total the three waits add up to 100 + 200 + 400 = 700 ms.

**The technical version.** The wait before retry *k* is the **base** wait doubled *k* − 1 times,
never more than a **cap**: wait = min(cap, base × 2<sup>*k*−1</sup>). For the third retry, *k* = 3,
so the base is doubled twice: 100 ms × 2 × 2 = 400 ms.

### Jitter

**What it is.** **Jitter** is a random amount added to, or taken from, each wait.

**Why it exists.** Callers that fail at the same moment and use the same formula compute the same
wait, so they retry at the same moment and fail together again.

**Example.** 120 callers fail at 10:00:06.000. With waits of exactly 100 ms, all 120 retries land at
10:00:06.100, in the same millisecond. With a random wait anywhere between 0 and 100 ms, they arrive
spread over those 100 ms: 120 ÷ 100 = about 1.2 retries per millisecond.

**The technical version.** The most common form is **full jitter**: wait a random time between 0 and
the exponential wait *d*, written random(0, *d*). Part 2 compares it with the other forms.

### A retry budget

**What it is.** A **retry budget** is a limit on retries as a share of normal traffic, for example
"retries may add at most 10%".

**Why it exists.** Backoff and jitter decide *when* retries are sent. Neither changes *how many* are
sent. A budget does.

**Example.** The order service sends 70 new requests a second. A 10% budget allows 70 × 0.1 = 7
retries a second, however many attempts fail. On a normal day it needs fewer than that, so every
retry is sent; in the outage, 7 retries a second are sent and the rest of the failed requests fail
at once.

**The technical version.** The usual way to build one is a **token bucket**. A **token** is
permission to send one retry; the bucket holds a limited number of them. Every new request adds 0.1
token, every retry spends 1, and a retry that finds no whole token is not sent. 70 new requests a
second add 70 × 0.1 = 7 tokens a second, which pays for 7 retries a second.

:::tip[If you stop here]
- Retrying fixes **transient** failures, but only retry requests that are safe to repeat, and only
  errors a second try can fix.
- Each retry is extra load on the server. When the server struggles, every caller retries at once,
  and the extra load can hold it down after the original problem is gone.
- **Exponential backoff** (wait 100, 200, 400 ms) gives a server time to recover, and **jitter**
  (make each wait random) stops callers that failed together from retrying together.
- Neither of them reduces how many retries are sent. A **retry budget** does: retries may add at most
  a fixed share, such as 10%, to normal traffic.
:::

## Going deeper

Part 1's stock server stayed down because each request was sent four times. The callers in that
story are what most guides recommend, and the obvious repair, exponential backoff with jitter, did
not save it. Why does waiting longer between retries not reduce the load? A retry policy adds 11% to
the load when 10% of attempts fail, and 300% when all of them fail: why is the extra load largest
exactly when the server can least take it? And what decides whether a slowdown heals itself or tips
the server into a state it cannot leave on its own?

The answers rest on one distinction, about where requests come from.

**What it is.** In a **closed system**, a fixed set of clients each sends its next request only
after its previous one has finished. In an **open system**, new requests arrive from outside,
whatever is happening to the earlier ones.

**Why it matters.** In a closed system, a client that waits sends nothing during its wait, so
waiting removes load. In an open system, a client that waits removes only its own retry; the new
requests keep coming.

**Example.** Ten batch workers emptying a table of jobs form a closed system: if a worker waits 2 s
before a retry, it sends nothing else for those 2 s. The order service is an open system: while one
request waits 2 s before its retry, 70 × 2 = 140 new requests arrive from people placing orders.

**The precise version.** Most services you call from a web backend are open systems: their load
comes from users or from other services under their own traffic. Every load-related claim on this
page assumes an open system unless it says otherwise, and that is why backoff alone fails in Part 1.

## The obvious fix, and why it breaks

The retry loop most code starts with:

```python
for attempt in range(4):
    try:
        return call()
    except Exception:
        if attempt == 3:
            raise
```

It has three faults, and each fails in a different way.

1. **It retries everything.** A `422` or a bug in your own code gets four tries and fails four
   times, slower. A `POST /payments` that timed out may charge twice.
2. **It retries at once.** If the server dropped a connection because it restarted, the retry
   lands before the new copy of the server is ready. And every client that failed at the same moment
   retries at the same moment.
3. **Nothing limits the total.** Each request can cost four attempts, and the loop does not care
   how long they take. Four attempts with a 2 s timeout each take 4 × 2 = 8 s, perhaps long after
   the caller stopped waiting.

**"Then add exponential backoff."** Waiting 100 ms, 200 ms, 400 ms between tries fixes the second
fault for one client, and it helps a **dependency** (any service your code calls) that is
restarting. It does not fix the third. Each
request still sends up to four attempts; backoff only moves them later. Marc Brooker's 2022 analysis
of backoff makes the same point: when the number of clients has no limit, as in an open system,
per-request backoff barely changes how much retries amplify a long overload, because new clients
keep arriving and do not know the others are waiting.

Retries sit next to five ideas they get confused with:

- **Idempotency keys** (from Part 1) make a repeated write safe. They decide *whether* you may retry,
  not how much.
- A **circuit breaker** is a switch in the client that stops calling a dependency that keeps failing,
  first attempts included, for a while, and then tests whether it has recovered.
- **Rate limiting** is a server capping how many requests one client may send per second.
- **Load shedding** is a server refusing work it cannot finish in time, so that it can finish the
  rest.
- **Hedging**, covered below, sends a second copy of a request for speed, before any failure.

So a retry policy has to decide three things, separately. **Whether**: only failures a second
attempt can fix, only requests that are safe to repeat, and only while the deadline leaves time for
another answer. **How much**: cap the extra load with a retry budget, so retries help when a few
attempts fail and stop when most fail. **When**: back off and add jitter, so that clients that
failed together do not retry together. Most retry storms come from a policy that only answered
"when".

## How it works, piece by piece

### Which failures to retry

Every retry policy starts with a yes or no for each failure. Part 1 gave two of the three questions:
could a second attempt succeed, and is the request safe to repeat? The dangerous case is the
ambiguous failure. A timeout tells you nothing about whether the server did the work, so a timed-out
`POST` without an idempotency key must not be retried.

The third question is the one libraries answer for you: **did the request reach the application at
all?** If it never did, repeating it is always safe. To see how a library can tell, take gRPC as the
example.

**gRPC** is a framework for calls between services, made by Google. It sends each call as a stream
inside an HTTP/2 connection. HTTP/2 is the version of HTTP that carries many requests, called
**streams**, over one connection at the same time.

gRPC knows three stages of a call, and treats each differently:

- **The call never left the client.** gRPC retries it on its own, as often as the deadline allows.
- **The call reached the server's HTTP/2 layer but not the application.** The server's networking
  code refused it before any of the service's code ran: it reset the stream with `REFUSED_STREAM`,
  or it was closing the connection and said so with a `GOAWAY` message naming the last stream it
  would handle. gRPC retries this once, at once.
- **The server has started answering.** Once the response headers arrive, gRPC will not send the
  call again, whatever your policy says. gRPC calls this the **commit point**.

The first two are **transparent retries**: they do not count against your retry policy, because they
cannot cause the work to happen twice.

| Failure | Retry? | Why |
|---|---|---|
| Connection refused, reset before the request was sent | yes | nothing reached the server |
| Timeout, `502`, `504` on a `GET` or a keyed `POST` | yes | safe to repeat; the server may still be working |
| Timeout on a `POST` with no idempotency key | no | it may have succeeded |
| `503`, `429` | yes, after `Retry-After` if given | the server says "not now", not "no" |
| `400`, `401`, `403`, `404`, `422` | no | the same request fails the same way |
| Your own `TypeError`, a bug | no | retrying a bug only delays the error |

`502 Bad Gateway` and `504 Gateway Timeout` come from a proxy in front of the server, a program that
forwards requests: they say the proxy could not get an answer, not that the request was wrong.

AWS's **SDKs**, the libraries AWS ships for calling its services from each language, make this list
concrete. Their standard mode retries `500`, `502`, `503` and `504`, connection errors, two timeout
error codes and fourteen **throttling** codes (errors meaning "you are sending faster than your
limit"), from `Throttling` and `TooManyRequestsException` to `SlowDown` from S3, AWS's file
storage, and nothing else ([aws-sdk-go-v2 source](https://github.com/aws/aws-sdk-go-v2/blob/main/aws/retry/standard.go), November 2026).

### How retries multiply load

Part 1 gave amplification two values: about 1.1 on a good day, 4 in an outage. Here is the value in
between, worked out first with numbers.

Take the stock service again, allow 3 retries, and suppose 10% of attempts fail, each one
independently of the others. Follow 1,000 requests:

1. All 1,000 send a first attempt.
2. 10% of those fail: 1,000 × 0.1 = 100 send a second attempt.
3. 10% of those fail: 100 × 0.1 = 10 send a third.
4. 10% of those fail: 10 × 0.1 = 1 sends a fourth.
5. In total: 1,000 + 100 + 10 + 1 = 1,111 attempts, so 1,111 ÷ 1,000 = 1.111 attempts per request.

Retries add 11% to the load, and almost every request succeeds. The same steps at 50% failing give
1,000 + 500 + 250 + 125 = 1,875 attempts: 1.875 per request. When every attempt fails, every request
sends all four: 4.

Written as a formula, with *p* the share of attempts that fail and *N* the number of retries: each
step multiplies the previous count by *p*, so the attempts per request are

1 + *p* + *p*² + … + *p*ᴺ

where *p*² means *p* × *p*. With *p* = 0.1 and *N* = 3: 1 + 0.1 + 0.01 + 0.001 = 1.111, the number
from the steps above. The extra load is smallest when the server is healthy and largest when it is
failing: the opposite of what a struggling server needs.

steeply it climbs on the right.

The curve assumes failures are independent. Overload makes them depend on the load itself: more
attempts mean a longer queue, a longer queue means more timeouts, and more timeouts mean more
attempts. The simulation below lets you watch that feedback.

100 attempts a second from a first-in, first-out queue; clients give up on an attempt after 1 s. The

What the sim shows has a name.

**What it is.** A **metastable failure** is a bad state that a system stays in after the event that
pushed it there has gone.

**Why the name matters.** It tells you where to look. The cause you can see, the slowdown, is over.
What keeps the system down is something the bad state itself produces, here the retries, and fixing
the cause does nothing.

**Example.** The stock server in Part 1. The rollout ended after 6 seconds, and the server ran at
full speed afterwards, yet it answered nobody in time, because 280 attempts a second kept the queue
wait above 1 second.

**The precise version.** Bronson and others (HotOS 2021) describe three states. A **stable** system
absorbs a bad moment and recovers. A **vulnerable** system is healthy, but has too little spare
capacity to absorb its own retries; it can run like that for months with nothing looking wrong. A
**trigger** (a slowdown, a **deploy** of new code, a sudden jump in traffic) pushes a vulnerable system into the **metastable** state,
and a **sustaining effect**, here the retries, keeps it there after the trigger has gone.

The stock server's numbers show exactly where the line between vulnerable and stable lies. A system
is safe from this loop when its normal load times its largest possible amplification stays below
its capacity:

- With 3 retries and no budget: 70 × 4 = 280 attempts a second, above 100. Vulnerable.
- With a 10% budget: 70 × 1.1 = 77 attempts a second, below 100. Stable.

A vulnerable system tips over when the trigger pushes the queue wait past the clients' timeout. With
the stock server, a 1 s wait at full speed means 1 × 100 = 100 attempts in the queue. At half speed,
the queue grows by 70 − 50 = 20 a second, so it reaches 100 after 100 ÷ 20 = 5 seconds. Any slowdown
of about 5 seconds or more tips it; shorter ones heal. The sim agrees: at the defaults, a 4 s trigger
recovers and a 5 s one does not.

The same arithmetic shows why spare capacity matters. At 50% load, the half-speed server still
finishes 50 a second, as many as arrive, so the queue does not grow at all, and in the sim even a
10 s trigger heals. At 80% load, the queue grows by 80 − 50 = 30 a second and reaches 100 after
100 ÷ 30 ≈ 3.3 seconds.

The loop has no step that depends on the trigger, so ending the trigger cannot end the loop. Getting
out needs the load to fall below capacity: fewer retries, load shed at the server, or more capacity.

This is not a thought experiment. Huang and others studied 22 metastable failures at 11
organisations (OSDI 2022) and found the retry policy was the sustaining effect in more than half of
them; at least 4 of 15 major AWS outages in a decade were metastable.

This page owns the arithmetic for one caller. When several layers each retry, the numbers multiply:
a caller that tries 3 times, around a library that also tries 3 times, makes 3 × 3 = 9 attempts.
The [proxy, load balancer and gateway page](/traffic/proxy-lb-gateway/#what-every-extra-hop-costs)
covers that case and why only one layer should retry.

### Exponential backoff: what it is for

Part 1 gave the doubling. The **cap** matters because doubling grows fast. With a base of 100 ms and
no cap, the seventh wait is 100 ms doubled six times: 100 → 200 → 400 → 800 → 1,600 → 3,200 → 6,400
ms, or 6.4 s. The tenth wait, doubled three more times, is 51,200 ms, about 51 s, long after anyone
wants the answer. With a cap of 2 s, the waits are 100, 200, 400, 800 ms, 1.6 s, and then 2 s for
every retry after that.

The waits come out of the caller's deadline, along with the attempts themselves. Take a 2 s deadline,
a 500 ms timeout per attempt, and the waits above:

1. Three attempts can take 3 × 500 ms = 1,500 ms.
2. The two waits between them take up to 100 + 200 = 300 ms.
3. Together that is up to 1,500 + 300 = 1,800 ms, or 1.8 s: inside the 2 s deadline.
4. A fourth attempt would add a wait of up to 400 ms and another 500 ms attempt: up to 1,800 + 400 +
   500 = 2,700 ms, past the deadline.

A policy that checks the deadline before each wait fails at once in that case, instead of sending an
attempt whose answer nobody will read.

**Envoy** works this way by design. Envoy is a **proxy**: a program that runs next to your services
and forwards their requests, applying rules such as retries along the way. Its **route timeout**, the
time limit for one request through Envoy, includes all retries. A request with a 3 s route timeout that
spends 2.7 s on its first try has 3 − 2.7 = 0.3 s left for every retry and wait together.

What backoff buys:

- **Time for a dependency to come back.** A restarting server, or a **cache** (a store of recent
  answers kept in memory) that is empty after a restart and has to fill again: a retry 100 ms later
  fails, a retry 1.6 s later succeeds.
- **Less load in a closed system.** A batch worker that waits sends nothing meanwhile.
- **Smaller bursts.** Retries spread over seconds instead of arriving in the same instant.

What it does not buy, in an open system: fewer attempts. During an outage each request still sends
1 + *N* attempts; backoff delays the 4× by a second or two. In the sim at 70% load, "retry at once"
tips over with a 4 s trigger, and backoff with jitter with a 5 s trigger: one second later, the
same outcome. With no retries at all, even a 10 s trigger heals. Brooker's 2022 conclusion is the
one to keep: backoff is a good idea for short spikes and does not reduce the total work or the
amplification of retries. Something else has to do that.

### Jitter: why clients that fail together retry together

Failures are shared in time. When a deploy closes 600 connections, all 600 clients see the error in
the same millisecond. With the same backoff formula and no randomness, they compute the same wait,
say 500 ms, and send 600 retries in the same millisecond. Suppose the server can take 60 of them. The
other 600 − 60 = 540 fail together, wait together and return together. The clients stay in step for
as long as they keep retrying.

There are several ways to add randomness. In the table, *d* is the capped exponential wait from Part
1, before any randomness: *d* = min(cap, base × 2<sup>*k*−1</sup>) before retry *k*. For the third
retry with a 100 ms base, *d* = 100 × 2 × 2 = 400 ms. **random(a, b)** means a number picked at
random between a and b, each value equally likely.

| Variant | Wait before retry *k* | Third retry, *d* = 400 ms | Who uses it |
|---|---|---|---|
| None | *d* | exactly 400 ms | urllib3 (jitter is off by default) |
| ±20% | *d* × random(0.8, 1.2) | 400 × 0.8 = 320 to 400 × 1.2 = 480 ms | gRPC |
| Equal | *d* ÷ 2 + random(0, *d* ÷ 2) | 200 + (0 to 200) = 200 to 400 ms | |
| Full | random(0, *d*) | 0 to 400 ms | AWS SDKs, Envoy |
| Decorrelated | drawn from a range set by the *previous* wait | varies | Polly (.NET), when jitter is on |

urllib3 is a Python HTTP library (the one `requests` is built on); Polly is a library for retries and
similar policies in .NET.

The diagram runs the deploy example with three of these variants: none, ±20% and full. 600 clients fail at once against a
server that completes 60 attempts in each 100 ms, which is 60 × 10 = 600 a second. They retry with a
500 ms base, up to 6 times. Each bar is how many attempts arrive in one 100 ms slot; look at how tall
and how wide each burst is.

<Figure caption="With no jitter, the 540 clients that fail together retry together, and each burst is as large as the last: after 8.5 s only 300 of the 600 have succeeded. Full jitter spreads the first retries over half a second, and every client is done by 2.5 s with 1,435 attempts instead of 2,400.">
  <Jitter />
</Figure>

Full jitter needed 2,400 − 1,435 = 965 fewer attempts than no jitter, and 965 ÷ 2,400 ≈ 0.4: 40%
fewer. It wins because it spreads each round of retries over the whole interval, from 0 to *d*. The
540 first retries land across five 100 ms slots, about 540 ÷ 5 = 108 per slot, instead of all 540 in
one. The ±20% that gRPC uses stops the clients from matching to the millisecond, but leaves each round in a band only
480 − 320 = 160 ms wide when *d* is 400 ms, so the server still sees humps. Full jitter's one cost is
that some waits are close to zero; the cap and the budget handle that.

Jitter is not only for retries. Anything that many machines schedule with the same timer falls into
step the same way: cache entries written together that expire together, scheduled jobs that all run
at the top of the hour, connections that are all closed after the same lifetime. The
[load balancing page](/traffic/load-balancing/) shows gRPC adding ±10% to connection lifetimes for
exactly this reason.

### Retry budgets: capping the extra load

Part 1 built the budget as a token bucket. The bucket also has a size, and the size decides how many
retries can go out in a burst before the ratio takes over.

A small example: a bucket that holds at most 10 tokens and starts full.

1. Twenty new requests each add 0.1 token: 20 × 0.1 = 2 tokens. The bucket is already at its cap of
   10, so it stays at 10.
2. Three of them fail and retry: 10 − 3 = 7 tokens left.
3. Now every request starts failing. The 7 tokens pay for 7 retries in a burst.
4. After that, every 10 new requests earn 10 × 0.1 = 1 token: one retry.

The ratio of 0.1 means retries cannot stay above about 10% of first attempts for long. The size of
the bucket only decides how big the first burst can be.

The figure shows two days for a client sending 100 new requests a second with up to 3 retries per
request. The bucket earns 100 × 0.1 = 10 tokens a second either way.

<Figure caption="On a normal day the bucket earns more than retries spend, stays full, and every retry is sent. In an outage, 3 retries per request would mean 300 retries a second; the budget lets 10 through, and the other requests fail at once without adding load.">
  <Budget />
</Figure>

On the good day, 5% of 100 = 5 retries a second are wanted and 10 tokens a second are earned, so the
bucket stays full. In the outage, 100 × 3 = 300 retries a second are wanted and 10 are sent. With a
budget, amplification stays at about 1.1 whatever happens, so the stock server at 70% load can absorb
its own retries, and its queue drains when the trigger ends.

The cost is real, and the runnable example in "Build it yourself" measures it. Against a dependency
failing 20% of attempts:

- **With 3 retries and no budget, 99.84% of requests succeed.** A request fails only if all four of
  its attempts fail: 0.2 × 0.2 × 0.2 × 0.2 = 0.0016, which is 0.16%. And 100% − 0.16% = 99.84%.
- **The clients wanted 26% extra attempts.** The run measured 1.26 attempts per request: 1 first
  attempt plus 0.26 retries, so retries wanted to add 26% to the load.
- **With a 10% budget, 87.58% succeed.** The budget allowed 10% extra instead of 26%, so some requests
  that a retry would have saved failed instead.

A budget trades some success during a **brownout**, a partial failure where a service is slow or
failing some requests but not down, for survival during an outage. That is why its ratio is a choice
and not a constant.

Real budgets, as of November 2026:

- **gRPC retry throttling** keeps a count per server name that starts at `maxTokens`. Every failed
  call subtracts 1, every successful call adds `tokenRatio`, and retries stop while the count is at
  or below half of `maxTokens`. With the documented example, 10 and 0.1, the count holds steady when
  successes add as much as failures take away. With a share *f* of calls failing, that is
  0.1 × (1 − *f*) = *f*. Multiply out the left side: 0.1 − 0.1*f* = *f*. Add 0.1*f* to both sides:
  0.1 = 1.1*f*. Divide by 1.1: *f* = 0.1 ÷ 1.1 ≈ 0.091, a failure rate of about 9.1%. Above that,
  the count falls to 10 ÷ 2 = 5, and retries stop until successes refill it.
- **AWS SDKs** (standard mode) give each client a 500-token quota. A retry costs 5 tokens, a retry
  after a timeout 10, and a first attempt that succeeds adds 1. A full quota pays for 500 ÷ 5 = 100
  retries in a burst. After that, it takes 5 successful requests, adding 1 token each, to pay for one
  more retry.
- **Envoy** limits retries in progress at the same time, per **upstream cluster** (the group of
  servers it forwards one service's requests to). By default at most 3 retries are in progress at
  once (`max_retries`, in the settings Envoy calls circuit breakers). With a `retry_budget`, retries
  in progress may be at most 20% of the active and waiting requests, but never fewer than 3.
- **Finagle**, Twitter's library for calls between services on the Java platform, allows by default
  about 20% of requests to be retried, on top of 10 retries a second so that a new or quiet client
  can still retry at all.

The floor matters more than it looks. A pure 10% ratio gives a client that sends 2 requests a minute
2 × 0.1 = 0.2 tokens a minute, so it needs 1 ÷ 0.2 = 5 minutes to earn one retry. So budgets add a floor: Finagle's
10 a second, Envoy's 3 at once, a bucket that starts full.

:::caution[A budget per process is a budget per process]
The bucket lives in each client process, each running copy of the client program. **Serverless
functions**, code that the cloud starts on demand in short-lived copies, often create a fresh SDK
client per run. A fleet of 2,000 such copies,
each with a full 500-token quota, can send 2,000 × 100 = 200,000 retries before any bucket runs dry.
Brooker's 2022 comparison found the same: a token bucket that starts full, in short-lived clients,
behaves almost like plain *N* retries. Keep clients alive across requests, share one per process,
and give short-lived workers small buckets.
:::

A circuit breaker is the other way to stop retrying a failing dependency: it watches the failure
rate and stops all calls, first attempts included, for a while. A budget only removes retries, so
first attempts keep testing the dependency and its recovery is seen at once. The circuit breakers
page, later in this track, covers when you want the stronger tool.

### Listening to the server

The server knows things the client does not: whether it is overloaded, when a limit resets, and
whether the request can ever succeed. There are three common ways for it to say so:

- **`Retry-After`** on a `429` or `503`, as a number of seconds or a date. A client waits at least
  that long, plus jitter, so that clients told the same time do not return in the same second (the
  [rate limiting page](/resilience/rate-limiting/#429-retry-after-and-the-client-on-the-other-side)
  measures the difference). urllib3 honours it on `413`, `429` and `503` by default. Envoy can read
  `Retry-After` or `X-RateLimit-Reset` with `rate_limited_retry_back_off`.
- **gRPC pushback**: the server sets `grpc-retry-pushback-ms` in its response **metadata**, the
  key-value pairs gRPC sends alongside a response, like HTTP headers. A value of zero or more means
  "retry after exactly this many milliseconds", and the backoff starts again from the base after it;
  a negative value means "do not retry". It is the only way a gRPC server can switch its clients'
  retries off during an incident without changing every client's configuration.
- **Throttling errors get a longer base.** In the 2026 update to the AWS SDKs, a throttling error
  backs off from a 1 s base and other transient errors from 50 ms. A throttle means "you are over
  your limit", and the limit will still be there in 50 ms.

On the server side, the same thinking says: when you are overloaded, answer quickly with `503` and
`Retry-After` instead of slowly with a timeout. A fast refusal costs the server microseconds; a
timeout costs it the whole request, and the client retries either way.

### Hedged requests: retrying for speed

A retry waits for a failure. A hedged request does not wait for one; it fires when an answer is
merely late. "Late" is measured with a percentile, so that comes first.

**What it is.** The **p95 latency** is the time within which 95% of requests finish; only 5 in 100
take longer.

**Why it exists.** An average hides the slow few, and the slow few are the ones users notice.

**Example.** Out of 100 reads, 95 finish within 40 ms and the other 5 take between 60 and 180 ms.
The p95 is 40 ms. An average of all 100 can look healthy and still say nothing about the read that
took 180 ms.

**The precise version.** Sort the latencies and take the value 95% of the way up the list. The p99
is the value 99% of the way up. The slowest few percent of requests are called the **tail**.

A **hedged request** works like this: if the first attempt has not answered by a delay, usually
around the p95, the client sends a second copy to another **replica** (a copy of the same service on
another machine) and uses whichever answer arrives first, cancelling the other. It cuts the tail
when the slowness comes from one replica, such as a slow disk or a program that pauses, rather than from the
request itself.

The figure follows one read with illustrative numbers: a p95 of 40 ms, and a first copy stuck behind
a slow disk.

<Figure caption="The first copy waits behind a slow disk; the hedge sent at the p95, 40 ms, answers 12 ms later, at 52 ms, instead of 180 ms. Only requests slower than the p95 send a second copy, so the cost is about 5% more load on a normal day.">
  <Hedging />
</Figure>

The costs follow from the mechanism. A hedge sends a duplicate, so the request must be safe to run
twice: reads, or writes with an idempotency key. On a normal day only requests slower than the p95
send a copy, which is 5% of them by the definition of the p95. On a bad day, when every replica is
slow, every request passes the p95, every request sends a copy, and the extra load is up to 100%.
That is why gRPC throttles hedges with the same token count as retries: once failures pass the
threshold, only first attempts are sent.

gRPC's `hedgingPolicy` sets `maxAttempts` (5 at most), `hedgingDelay`, and `nonFatalStatusCodes`,
the errors that send the next copy at once. A method has a retry policy or a hedging policy, never
both. Hedging is supported in gRPC's Java, .NET and Node implementations, not in Go or in C-core (the C library that gRPC's C++,
Python and Ruby versions are built on), according to gRPC's design document.

## Choosing between them

The table compares the policies on the same two days: a normal day with 5% of attempts failing, and a
full outage. On the normal day, retrying the failed 5% adds about 5%. In the outage, 3 retries per
request means 3 extra attempts for every first attempt: 300% extra.

| Policy | Extra load, normal day (5% failing) | Extra load, full outage, 3 retries | What it fixes | Pick it when |
|---|---|---|---|---|
| No retries | 0 | 0 | nothing | the caller (a user, a queue) will retry anyway |
| Retry at once | 5% | 300%, in bursts that arrive together | one dropped packet | never as a default |
| Exponential backoff | 5% | 300%, a little later | a dependency restarting; closed systems | always, but never alone |
| Backoff + full jitter | 5% | 300%, spread out | clients failing together | always |
| + retry budget | 5% | about 10% | retry storms, metastable failures | every client of a shared service |
| Hedging | about 5% | up to 100% unless throttled | tail latency from one slow replica | safe-to-repeat reads with a long p99 |

The order I would build in: classify failures and check the deadline first, because a wrong retry is
worse than none; then full jitter on a capped exponential; then a budget sized for the failure rate
you want to survive, 10% to 20%. Retry at one layer: the one closest to the caller that still
knows whether the request is safe to repeat. Add hedging only after you have measured a tail it would
fix.

## Build it yourself

The naive loop from the start of Part 2, and two steps beyond it: a correct retry that classifies
errors, backs off with full jitter and respects the caller's deadline, then the same with a retry
budget. The full files run each policy for 10,000 requests against a fake dependency; `sleep` moves
a pretend clock forward instead of waiting, so a run takes about a second.

```python title="retries.py"
# runnable version: examples/retries-and-backoff/python/retries.py
class TransientError(Exception):
    """Worth retrying: a timeout, a reset connection, 503, 429. May carry the server's Retry-After."""

    def __init__(self, message: str = "", retry_after: float | None = None):
        super().__init__(message)
        self.retry_after = retry_after


def backoff_delay(retry: int, base: float, cap: float, rand: Callable[[], float] = random.random) -> float:
    """Full jitter: anywhere between 0 and the capped exponential (base, 2×base, 4×base...)."""
    return rand() * min(cap, base * 2 ** (retry - 1))


def call_with_retries(
    fn: Callable[[], T],
    *,
    deadline: float,  # a time.monotonic() value: the caller's whole budget
    retries: int = 3,
    base: float = 0.1,
    cap: float = 2.0,
    budget: RetryBudget | None = None,
    rand: Callable[[], float] = random.random,
    clock: Callable[[], float] = time.monotonic,
    sleep: Callable[[float], None] = time.sleep,
) -> T:
    if budget:
        budget.on_request()
    retry = 0
    while True:
        try:
            return fn()
        except TransientError as err:  # PermanentError and bugs propagate on the first try
            retry += 1
            if retry > retries:
                raise
            delay = max(err.retry_after or 0.0, backoff_delay(retry, base, cap, rand))
            if clock() + delay >= deadline:
                raise  # the caller will have given up before the next answer arrives
            if budget and not budget.try_spend():
                raise  # many attempts are failing: fail fast, don't add load
            sleep(delay)
```

```js title="retries.mjs"
/** Worth retrying: a timeout, a reset connection, 503, 429. May carry the server's Retry-After. */
export class TransientError extends Error {
  constructor(message = '', retryAfter = null) {
    super(message);
    this.retryAfter = retryAfter;
  }
}

/** Full jitter: anywhere between 0 and the capped exponential (base, 2×base, 4×base...). */
export function backoffDelay(retry, base, cap, random = Math.random) {
  return random() * Math.min(cap, base * 2 ** (retry - 1));
}

const realSleep = (s) => new Promise((resolve) => setTimeout(resolve, s * 1000));

export async function callWithRetries(fn, {
  deadline, // a performance.now()/1000 value: the caller's whole budget, in seconds
  retries = 3, base = 0.1, cap = 2.0, budget = null,
  random = Math.random, clock = () => performance.now() / 1000, sleep = realSleep,
}) {
  budget?.onRequest();
  for (let retry = 1; ; retry++) {
    try {
      return await fn();
    } catch (err) {
      if (!(err instanceof TransientError)) throw err; // PermanentError and bugs: no retry
      if (retry > retries) throw err;
      const delay = Math.max(err.retryAfter ?? 0, backoffDelay(retry, base, cap, random));
      if (clock() + delay >= deadline) throw err; // the caller will have given up by then
      if (budget && !budget.trySpend()) throw err; // many attempts are failing: fail fast
      await sleep(delay);
    }
  }
}
```

Read it like this. `TransientError` marks the failures worth retrying; anything else, a permanent
error or a bug, leaves the function on the first try. `backoff_delay` is full jitter: a random number
between 0 and 1, times the capped exponential wait. Each time a transient error arrives, the function
counts the retry, gives up if it has used them all, works out the wait (never shorter than the
server's `Retry-After`), gives up if that wait would end past the deadline, asks the budget for a
token, and only then sleeps and tries again. The `clock`, `sleep` and `rand` parameters exist so the
example can swap in a pretend clock and a seeded random generator, which makes every run print the
same numbers.

Two details carry most of the value. The deadline check happens *before* the wait, so a retry that
cannot finish in time is never sent. And `Retry-After` sets a floor under the backoff rather than
replacing it, so clients told the same time still spread out.

The budget is a dozen lines: the token bucket from Part 1. One instance per process and dependency,
shared by every request:

```python title="retries.py"
class RetryBudget:
    """Retries may add at most `ratio` extra load. Share one per client process and dependency."""

    def __init__(self, ratio: float = 0.1, max_tokens: float = 10.0):
        self.ratio, self.max_tokens, self.tokens = ratio, max_tokens, max_tokens
        self._lock = threading.Lock()

    def on_request(self) -> None:  # every new request earns a fraction of a retry
        with self._lock:
            self.tokens = min(self.max_tokens, self.tokens + self.ratio)

    def try_spend(self) -> bool:  # every retry costs a whole one
        with self._lock:
            if self.tokens < 1:
                return False
            self.tokens -= 1
            return True
```
  </TabItem>
  <TabItem label="JavaScript">
```js title="retries.mjs"
/** Retries may add at most `ratio` extra load. Share one per client process and dependency. */
export class RetryBudget {
  constructor(ratio = 0.1, maxTokens = 10) {
    Object.assign(this, { ratio, maxTokens, tokens: maxTokens });
  }
  onRequest() { this.tokens = Math.min(this.maxTokens, this.tokens + this.ratio); } // earn a fraction
  trySpend() { // spend a whole one
    if (this.tokens < 1) return false;
    this.tokens -= 1;
    return true;
  }
}
// Node runs this on one thread, so no lock is needed; in a worker pool, keep one per worker.
```

## How real systems do it

**AWS SDKs** have three retry modes. *Standard* makes up to 3 attempts with full jitter, a 1 s base
and a 20 s cap, under the 500-token quota described above. *Adaptive* adds a client-side rate limiter
that can delay first attempts when throttled; AWS calls it experimental. *Legacy* is each SDK's older
behaviour, with no quota, and it is still the default in some. botocore, the library under boto3
(AWS's Python SDK), uses legacy, with 5 attempts, and 10 for AWS's DynamoDB database, unless you set
`AWS_RETRY_MODE=standard`.

A 2026 update changes standard mode. Transient errors back off from 50 ms and throttling errors from
1 s; the cap applies before the jitter; and a retry costs 14 tokens (5 after a throttle), so a full
quota pays for 500 ÷ 14 ≈ 35 retries rather than 100. As of November 2026 it is opt-in with
`AWS_NEW_RETRIES_2026=true`. AWS's announcement (May 2026) says it becomes the default this month,
and that it moves botocore's default mode from legacy to standard. Check your SDK version before
relying on either set of numbers.

**gRPC** retries nothing unless the **service config** says so: a JSON document that tells gRPC
clients how to call a service. A retry policy names `maxAttempts` (counting the first, at most 5),
`initialBackoff`, `maxBackoff`, `backoffMultiplier` and the `retryableStatusCodes`, and the deadline
covers all attempts. The service config can be delivered by the team that runs the service rather
than compiled into every client, which puts the retry policy, and the throttling that stops it, under
the control of the people who see the server struggling:

```json
{
  "methodConfig": [{
    "name": [{ "service": "inventory.Stock" }],
    "retryPolicy": {
      "maxAttempts": 3,
      "initialBackoff": "0.1s",
      "maxBackoff": "1s",
      "backoffMultiplier": 2,
      "retryableStatusCodes": ["UNAVAILABLE"]
    }
  }],
  "retryThrottling": { "maxTokens": 10, "tokenRatio": 0.1 }
}
```

This config allows 3 attempts (one first try and two retries), waits of about 0.1 s and 0.2 s with
gRPC's ±20% jitter, and retries only `UNAVAILABLE`, gRPC's code for "the server cannot take the call
right now". The `retryThrottling` part is the 9.1% budget worked out above.

**Envoy** retries only when a **route** (Envoy's rule for where one kind of request goes) has a
retry policy, and then once by default (`num_retries`). Backoff is full jitter from a 25 ms base: retry *N* waits a random time below (2<sup>*N*</sup> − 1) ×
25 ms. For the first retry that is (2 − 1) × 25 = 25 ms, so 0–24 ms; for the second, (4 − 1) × 25 =
75 ms, so 0–74 ms; for the third, (8 − 1) × 25 = 175 ms, so 0–174 ms. The cap is 10 times the base:
10 × 25 = 250 ms.

`retry_on` names the conditions (`5xx`, `gateway-error`, `reset`, `connect-failure`,
`retriable-4xx`, `refused-stream`, gRPC status names). A rule such as `previous_hosts`
sends the retry to a different server from the one that failed, which is most of the value of a retry
at a proxy. The route timeout includes every retry, and the cluster's `max_retries` or `retry_budget`
caps them.

:::note[From the trenches]
The useful exercise is to list every retry between your user and your database: the mobile app,
the API gateway (the proxy at the front door of your system), the service mesh sidecar (a proxy
such as Envoy running beside each service), your code, the SDK, the database driver (the library
your code uses to talk to the database). Teams that do it the first time usually find three or four,
each configured by a different person who assumed the others did not retry.
:::

## Gotchas and war stories

:::danger[Retries that keep an outage going]
On December 7, 2021, an automated scaling activity (a system adding capacity on its own) in AWS's
us-east-1 region (its data centres in Northern Virginia) triggered a surge of connection activity from a large number of clients on AWS's
internal network. The surge overwhelmed the network devices between that internal network and the
main one. AWS's summary describes the loop on this page: the delays increased latency and errors,
which caused even more connection attempts and retries, and the congestion persisted; a hidden
fault kept those clients from backing off adequately. Removing the trigger does not end a metastable
failure. Plan how you will shed load or switch retries off before you need it.
:::

:::caution[Retries stacked in the libraries you did not write]
Defaults as of November 2026: Python's `requests` retries nothing (`max_retries=0`), but urllib3 used
directly retries 3 times with no backoff. AWS SDKs make 3 to 5 attempts. Polly (.NET) defaults to 3
retries, 2 s apart with no jitter, on any exception. Envoy retries once when a policy exists. Your own
loop of 3 attempts around an SDK call of 3 attempts makes 3 × 3 = 9 attempts per request, before the
gateway adds its own. Find the library defaults, turn retries off in all but one layer, and log
attempt numbers so that a storm is visible.
:::

:::caution[Retrying a timeout duplicates work]
A timed-out attempt is usually still running on the server (the
[timeouts page](/resilience/timeouts/#a-timeout-stops-the-waiting-not-the-work) covers why). The
retry starts a second copy of the same expensive query beside the first. That is exactly the wasted
work in the sim. Pass the deadline to the server so it can stop, and do not retry a timeout on an
endpoint you know is overloaded.
:::

:::caution[Retrying while holding a lock]
A database transaction that changes a row holds a **lock** on it: other transactions that want the
same row wait until this one commits or rolls back. A retry loop inside the transaction holds the
lock through every backoff wait; so does a loop that holds a connection borrowed from a **pool** (a
fixed set of open database connections shared by all requests). Three retries with waits of up to
2 s each can keep a row locked for 3 × 2 = 6 s. Retry outside the transaction: roll back, wait, start
again.
:::

:::caution[Budgets that hide failures]
A budget that refuses retries turns "slow and recovering" into "fast errors", which is the point,
but the errors must still be counted and alerted on. Log refused retries as their own metric; a
rising count is the earliest signal that a dependency is in trouble.
:::

## Trade-offs and when not to use it

Every retry policy trades load for success. No retries puts the failure in front of the user at once
and adds nothing to a struggling server. Unlimited retries hide every blip and turn a long failure
into an overload. A budget sits between, and its ratio decides where: 10% survives blips and
stops storms; 20%, Finagle's default, survives worse brownouts and adds more load during
outages.

Retries also cost latency. Each one adds a wait and another attempt to the request's time, and a
request that succeeds on its third try took longer than the user wanted. For interactive paths with a
tight deadline, one retry is often all that fits.

Do not retry when:

- **Someone else will.** A message queue (a service that holds tasks until a worker takes them)
  delivers a failed task again, a user taps again, a batch job reruns. Retrying inside a worker
  whose task the queue will also deliver again multiplies attempts, as stacked layers do.
- **The request is not safe to repeat** and has no idempotency key.
- **The server said no**: a `4xx` other than `408 Request Timeout`, `425 Too Early` and `429`, or a
  gRPC pushback that says stop.
- **The deadline cannot fit another attempt.**
- **The dependency is known to be overloaded.** Then the server needs less load: shed it there, and
  let callers fail fast.

## Interview corner

Retries come up as a follow-up to any design with a network call: "what happens when the payment
service is slow?" A strong answer covers four things: which failures you retry and why the request
is safe to repeat; that each layer's retries multiply and only one layer should retry; capped
exponential backoff with full jitter; and a budget that caps retries during an outage, with numbers.

Typical questions:

- *"Why add jitter to exponential backoff?"* Clients that fail together compute the same wait and
  retry together, in bursts the size of the first failure. Full jitter spreads each round of
  retries over the whole interval.
- *"Does exponential backoff protect an overloaded server?"* Only from short spikes. In an open
  system new requests keep arriving, and each request still sends up to 1 + *N* attempts. A budget
  limits the extra load; backoff only delays it.
- *"The service recovered, but errors stayed high for an hour. Why?"* A metastable failure:
  retries keep the queue wait past the clients' timeout, so every answer arrives late. Shed load or
  switch retries off; waiting does not help.
- *"How would you retry a payment?"* Only with an idempotency key, only on errors that a retry can
  fix, at one layer, inside the user's deadline, and with a budget.

## Check yourself

<details>
<summary>1. Each attempt to a dependency fails with probability 0.3, independently. How many attempts per request do 2 retries send, and what share of requests fail after all of them?</summary>

Follow 1,000 requests. All 1,000 send a first attempt; 30% of them fail, so 1,000 × 0.3 = 300 send a
second; 30% of those fail, so 300 × 0.3 = 90 send a third. That is 1,000 + 300 + 90 = 1,390 attempts:
1.39 per request. A request fails only if all three attempts fail: 0.3 × 0.3 × 0.3 = 0.027, which is
2.7%. Retries turned a 30% failure rate into 2.7%, for 39% more load.

</details>

<details>
<summary>2. You change your clients from "retry at once" to exponential backoff with full jitter, still 3 retries. During a full outage, by how much does the load on the dependency fall?</summary>

Barely. Each request still sends 4 attempts; backoff delays the last three by up to a few seconds,
and in an open system new requests keep arriving meanwhile. The load is still close to 4 times normal
after the first few seconds. Only a budget, fewer retries or a circuit breaker reduces it.

</details>

<details>
<summary>3. A gRPC client has retryThrottling with maxTokens 10 and tokenRatio 0.1. Roughly what failure rate stops its retries?</summary>

The count is steady when successes add as much as failures take away. With a share *f* failing, that
is 0.1 × (1 − *f*) = *f*, which works out to *f* = 0.1 ÷ 1.1 ≈ 9%. Above that, the count falls to half
of `maxTokens`, 5, and retries stop while it stays there. First attempts keep going, and their
successes refill the count.

</details>

<details>
<summary>4. Part 1's stock server normally runs at 80% load instead of 70%: 80 requests a second against a capacity of 100. With 3 retries and no budget, roughly how long a half-speed slowdown tips it over?</summary>

At half speed the server finishes 50 a second while 80 arrive, so the queue grows by 80 − 50 = 30 a
second. Clients give up at 1 s, which at full speed is a queue of 1 × 100 = 100 attempts. The queue
reaches 100 after 100 ÷ 30 ≈ 3.3 seconds. So a slowdown of about 3 to 4 seconds is enough; in the sim
at 80% load, 3 s recovers and 4 s does not. Less spare capacity means a shorter trigger tips it.

</details>

<details>
<summary>5. 2,000 serverless functions each create a new AWS SDK client per run and call a throttled API. Why does the SDK's retry quota not stop a retry storm?</summary>

Each client has its own 500-token quota, full when it is created. A client that lives for one run
never drains its bucket, so each behaves like plain "3 attempts". Create the client once per copy of
the function, outside the code that handles each run, so its quota lasts across runs, and add a
budget or a circuit breaker that is shared more widely.

</details>

## Recap

- Retries multiply load by 1 + *p* + … + *p*ᴺ: about 1.1 on a healthy day, and 1 + *N* when
  everything fails, which is when the dependency can least afford it.
- In an open system, retries can hold a server down after its trigger has gone: a metastable
  failure. A system is safe when its normal load times its largest amplification stays below
  capacity.
- Exponential backoff with a cap decides when to retry. It helps restarts and closed systems; it
  does not reduce the number of attempts.
- Full jitter, random(0, *d*), spreads out clients that failed together; ±20% only blurs them.
- A retry budget, tokens earned by new requests and spent by retries, caps the extra load at a ratio.
  It costs some success during brownouts and saves the service during outages.
- Retry only transient failures, only safe requests, only inside the deadline, at one layer, and
  listen to `Retry-After` and pushback.
