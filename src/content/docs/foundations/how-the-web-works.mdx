## A slow page, far away

Imagine your first month as a junior engineer at a small food-ordering startup. The app works
beautifully on your laptop: the home page appears in about 40 ms. The team deploys it to a cloud
region in the United States, because that was the default in the tutorial everyone followed, and
launches to customers across India.

A week later, the support inbox fills up. A customer in Lucknow writes that the site "takes
forever, about three seconds, before anything shows". Your manager asks you to find out why. You
open the server logs and every request for the home page was handled in about 50 ms. The database
is fast, the code is fast, the CPU is mostly idle.

So the server says 50 ms and the customer says 3 seconds, and both are telling the truth. The
missing 2.95 seconds were spent somewhere your logs cannot see: in the browser, in the phone's
network, in a dozen small conversations that happen before your code receives a single byte, and
in the many more that happen after it replies.

This is the most important map in web engineering, and most engineers carry around a blurry
version of it. This page draws it properly. It answers one question: **what actually happens
between pressing Enter and seeing a page, where does each millisecond go, and where can each step
break?** Every other topic on this site, from DNS to load balancers to caching, is one part of
this journey zoomed in. This page is the whole journey at once.

## Why this problem exists

The web was not designed as one system. It is a stack of separate agreements, built by different
people in different decades. DNS, which turns names into addresses, took its current form in 1987.
TCP, which delivers bytes reliably, is older still. The encryption layer, SSL and then TLS, has
been redesigned six times since the 1990s, and HTTP is on its third major version. Each solves its
own problem well, and each needs its own little conversation before it can do its job.

A few terms will come up on every line of this page:

- A **client** is the program asking for something, here the browser. A **server** is the program
  answering.
- An **IP address** is a number that identifies a machine on the internet, such as `104.20.23.154`
  (IPv4) or `2606:4700:10::6814:179a` (IPv6). Routers move data using addresses, never names.
- A **packet** is one small chunk of data, usually up to about 1,500 bytes, travelling on its own
  across the network. Everything you send is cut into packets.
- A **protocol** is an agreed set of rules for a conversation: who speaks first, what each message
  means.
- A **port** is a number that picks which program on a machine gets the packet. HTTPS servers
  listen on port 443 by default.
- **Latency** is how long one message takes to arrive. A **round trip** is a message there and its
  reply back, and the time it takes is the **round-trip time (RTT)**.
- **Bandwidth** is how many bytes per second a connection can carry. It is not the same as
  latency, and for most web pages it matters less.

Here is the force that creates the whole problem. Light in an optical fibre travels at about
200,000 km per second, two thirds of its speed in a vacuum. That sounds instant, but the Earth is
big. Mumbai to northern Virginia is roughly 13,000 km in a straight line, so even a perfect fibre
needs about 65 ms each way. Real cables do not run in straight lines, and every router on the path
adds a little, so as of October 2026 the measured round trip between the AWS regions in Mumbai and
North Virginia is about 187 ms ([cloudping.co](https://www.cloudping.co/)). On a busy mobile
network it is often worse.

You can buy more bandwidth; you cannot buy lower latency, only shorter distances. And a page load
is not one round trip. It is a chain of conversations, most of which must finish before the next
can start. If a page needs 15 round trips and each costs
190 ms, that is nearly 3 seconds, even if the server answers in no time at all.

That is our customer in Lucknow. The cost lands on users who are far away or on slow networks, and
on the business: people leave slow pages, and teams buy bigger servers that do not help, because
the server was never the slow part.

## The obvious picture, and why it breaks

The picture most of us start with has one arrow: the browser asks the server for the page, and the
server sends it back. The code we write first matches that picture. One call, one result:

<Tabs syncKey="lang">
  <TabItem label="Python">
```python title="naive_fetch.py"
# runnable version: examples/how-the-web-works/python/naive_fetch.py
def naive_fetch(url: str) -> None:
    started = time.perf_counter()
    with urllib.request.urlopen(url) as response:  # no timeout: waits as long as the OS allows
        body = response.read()
    elapsed = (time.perf_counter() - started) * 1000
    print(f"{url}: {response.status}, {len(body)} bytes in {elapsed:.0f} ms. Which part was slow? No idea.")
```
  </TabItem>
  <TabItem label="JavaScript">
```js title="naive-fetch.mjs"
// runnable version: examples/how-the-web-works/js/naive-fetch.mjs
async function naiveFetch(url) {
  const started = performance.now();
  const response = await fetch(url); // no timeout of our own
  const body = await response.text();
  const elapsed = performance.now() - started;
  console.log(`${url}: ${response.status}, ${body.length} bytes in ${elapsed.toFixed(0)} ms. Which part was slow? No idea.`);
}
```
  </TabItem>
</Tabs>

It works. The example file runs it twice: once against a healthy site, and once against
`10.255.255.1`, a private address that nothing answers on most networks.

```text title="naive_fetch.py output"
https://example.com/: 200, 577 bytes in 196 ms. Which part was slow? No idea.
http://10.255.255.1/: still waiting after 5.0 s, with no error and no idea why. Giving up on it.
```

The one-arrow picture breaks in two ways, and the output shows both.

1. **It hides where the time goes.** 196 ms is one number. Was it finding the server, connecting,
   encrypting, or the server thinking? When a page is slow, that number cannot tell you which of
   five very different problems you have.
2. **It hides where things fail.** When one hidden step never completes, the call hangs. We measured
   how long that unanswered connection takes to give up when nobody sets a timeout: 21 s on
   Windows 11, 135 s on Linux with its default settings, and 10.8 s with Node's built-in `fetch`,
   which has a 10 s connect limit of its own. Your users will not wait that long, and neither
   should your code: set a connect timeout and a total timeout on every outgoing call.

Before we open the box, a few words that beginners often treat as the same thing:

| These are often confused | The difference |
|---|---|
| **The internet** vs **the web** | The internet is the global network that moves packets between addresses. The web is one thing that runs on it: pages and APIs spoken over HTTP. Email and video calls use the internet without being the web. |
| **URL** vs **domain** vs **IP address** | `https://shop.example.in/cart` is a URL: the full address of one thing. `shop.example.in` is the domain name inside it. `104.20.23.154` is the IP address that name currently points to. Names are for people; addresses are for routers. |
| **HTTP** vs **HTTPS** vs **TLS** vs **SSL** | HTTP is the request and response language. TLS is the encryption layer underneath it. HTTPS is HTTP sent through TLS. SSL is TLS's old, retired name, surviving in phrases like "SSL certificate". |
| **DNS** vs **hosting** | DNS only tells browsers where your site lives. Hosting is the machines that serve it. They are often bought from different companies, and they fail separately. |
| **Latency** vs **bandwidth** | Latency is how long a message takes to arrive; bandwidth is how many bytes per second fit in the pipe. A 1 Gbit/s connection to a server 190 ms away still waits 190 ms for every round trip. |

## The core idea

Think about calling a restaurant you have never ordered from in a new city. First you look up its
number in a directory. Then you dial and wait for someone to pick up. Then, because you are paying
by card, you want to be sure this really is the restaurant and not someone pretending, so you
check. Only then do you place your order, the kitchen cooks it, and a delivery arrives that you
unpack and lay out on the table.

That is a page load: **look up** the number (DNS), **dial** (TCP), **check who answered** (TLS),
**order** (HTTP), **cook** (the servers), **lay it out** (rendering). Each step waits for the one
before it.

The analogy breaks in three places, and they matter.

- A phone call is one conversation. A web page needs a median of about 75 to 80 separate files,
  often from several servers, and the browser runs many conversations at the same time.
- Looking up a phone number takes the same time every time. DNS answers are cached, so the first
  lookup can take hundreds of milliseconds and the next one almost nothing.
- On a phone call, picking up is quick. On the internet, every "hello, are you there?" costs a full
  round trip, so the distance to the server multiplies every step.

Put precisely: **loading a page means finding the server's address, opening a connection, securing
it, sending a request, waiting while the servers behind that address build the answer, and turning
the answer into pixels, then doing the same for every file the page refers to. The cost is
counted mostly in round trips, which is why so much of web engineering is about removing them:
caching answers, reusing connections, and moving servers closer to users.**

The diagram below is the map for the rest of the page. Follow the numbers: four conversations with
the outside world, then one step that happens entirely inside the browser.

The right-hand box is not one server: behind one address there is usually a CDN, a load balancer,
several copies of your app and a database. And only step 4 involves your code. Steps 1, 2 and 3
happen before your server knows anyone is there, which is why your logs showed 50 ms while the
customer waited seconds.

## How it works, step by step

We will follow one request, for `https://shop.example.in/cart`, from a customer in India to a
server in North Virginia: a round trip of about 190 ms, and 50 ms for the server to build the page.
Where we measured something ourselves, we will say so.

### Step 0: the address bar works out what you meant

Before any network traffic, the browser has to decide what you typed. The address bar is also a
search box, so "cheap flights" becomes a search and `shop.example.in/cart` becomes an address,
which the browser splits into parts. Each part has a different job, and one of them never leaves
your machine.

<Figure caption="A URL is six parts. The host is what DNS looks up, the port picks the door, the path and query say what you want, and the fragment after # stays in the browser: the server never sees it.">
  <UrlAnatomy />
</Figure>

The fragment is the surprise for most people. `#pay` tells the browser where to scroll, or tells a
single-page app which view to show, but it is never sent to the server
([RFC 3986](https://www.rfc-editor.org/rfc/rfc3986#section-3.5)). Before using the host, the
browser also checks whether it must use HTTPS.

That last check matters for both speed and safety. A site can send a header,
`Strict-Transport-Security`, that tells the browser "only ever talk to me over HTTPS", which is
called **HSTS** ([RFC 6797](https://www.rfc-editor.org/rfc/rfc6797)), and browsers ship a built-in
**preload list** of sites that are HTTPS-only from the very first visit. As of October 2026 Chrome
and Safari also upgrade plain HTTP navigations to HTTPS by default
([hstspreload.org](https://hstspreload.org/)), and Google has announced that Chrome 154, scheduled
for October 2026, will ask before opening any public site with no HTTPS at all
([Google](https://blog.google/security/https-by-defau/)).

Finally, the browser checks whether it already has the answer: a cached copy in its HTTP cache, or
a **service worker** (a script the site installed earlier) that can answer from its own storage.
If either can, every step below is skipped. That is the fastest page load there is.

### Step 1: find the server (DNS)

Routers move packets by address, not by name, so the browser needs the IP address of
`shop.example.in`. The **Domain Name System** (DNS) is the internet's directory for this. It is not
one big database. It is a tree of servers, each responsible for one part of the name, with caches
everywhere in between.

The question travels outwards through three caches on your side, and only goes to the wider
internet if all of them miss.

<Figure caption="The question moves right until a cache has the answer. On a full miss, the resolver asks a root server, then a .com server, then the domain's own servers, and every answer is cached for its TTL on the way back.">
  <DnsLookup />
</Figure>

Here is the full walk, step by step, for a name nobody nearby has asked about recently:

1. The browser checks its own cache, then asks the operating system, which checks its cache too.
2. The OS sends the question to a **recursive resolver**: your internet provider's, your office's,
   or a public one such as Cloudflare's 1.1.1.1 or Google's 8.8.8.8. This is the server that does
   the hard work.
3. If the resolver has no cached answer, it asks a **root server**. There are 13 root server
   identities, named A to M and run by 12 organisations, and as of October 2026 they are served from
   2,047 instances worldwide ([root-servers.org](https://root-servers.org/)). The root does not
   know the address. It replies with a **referral**: "I don't know, but here are the servers for
   `.com`."
4. The resolver asks a `.com` server, a **top-level domain** (TLD) server, which refers it to the
   domain's own **authoritative** servers, the ones that hold the real records.
5. The authoritative server answers with the address, and a **TTL** (time to live): how many
   seconds anyone may cache the answer.

We ran this walk ourselves, from a network in India, with a script that builds raw DNS question
packets in the [RFC 1035](https://www.rfc-editor.org/rfc/rfc1035) format, sends them over UDP to a
root server and follows the referrals
([`dns_walk.py`](https://github.com/udaysingh236/senior-dev-notes/tree/main/examples/how-the-web-works/python/dns_walk.py)).
For `example.com`:

```text title="dns_walk.py output"
1. asked a.root-servers.net (198.41.0.4) about example.com: 126 ms
   referral: ask the com. servers, e.g. l.gtld-servers.net., j.gtld-servers.net.  (cache for 172800 s)
2. asked l.gtld-servers.net. (192.41.162.30) about example.com: 122 ms
   referral: ask the example.com. servers, e.g. hera.ns.cloudflare.com., elliott.ns.cloudflare.com.  (cache for 172800 s)
3. asked hera.ns.cloudflare.com. (173.245.58.162) about example.com: 12 ms
   answer: example.com. A 104.20.23.154  (cache for 300 s)

example.com is at 104.20.23.154, found in 265 ms from a cold start
```

Read the TTLs. The referral to the `.com` servers may be cached for 172,800 seconds, two days, so
a busy resolver almost never asks the root. The address itself may be cached for 300 seconds. So
the 265 ms walk is rare; the same lookup through the operating system's resolver, which had it
cached, took 15 to 40 ms in our runs. Aliases make a walk longer: `www.wikipedia.org` is a
**CNAME** (an alias) for `dyna.wikimedia.org`, so the script had to start again for the real name,
and the cold walk took 810 ms. Real resolvers also remember which name servers answer fastest; our
script always asks the first one in the list.

**A worked example of the trade-off.** Say your site's address has a TTL of 86,400 seconds (one
day) and you move to a new server. Resolvers that cached the old address an hour ago will keep
sending users there for the next 23 hours, and you cannot make them forget. A long TTL makes
lookups fast and saves your DNS provider work; a short TTL lets you change things quickly. Teams
usually lower the TTL to a few minutes a day or two *before* a planned move, then raise it again
afterwards.

DNS uses UDP (a protocol that sends single packets with no connection set-up) on port 53, so a
lookup is one round trip to the resolver. If DNS fails, nothing else on this page can even start,
which is why DNS appears in so many outage stories. The [DNS](/networking/dns/) page goes inside
this step: record types, how caches treat TTLs, and how to change records without an outage.

### Step 2: open a connection (TCP)

The browser now has an address. Before it can send the request, it needs a reliable connection
to that address. The internet itself only promises to *try* to deliver packets: they can be lost,
duplicated or arrive out of order. **TCP** (the Transmission Control Protocol,
[RFC 9293](https://www.rfc-editor.org/rfc/rfc9293)) builds a reliable, ordered stream of bytes on
top of that, by numbering every byte, acknowledging what arrived, and resending what did not.

To start numbering, both sides must agree on starting points. That is the **three-way handshake**.
Time runs down the page in the diagram, so each arrow slopes by half a round trip.

<Figure caption="The browser sends SYN, the server answers SYN-ACK, and the browser's ACK travels together with its first request. Connecting costs one full round trip before a single byte of the request reaches the server.">
  <TcpHandshake />
</Figure>

The handshake is SYN ("let's talk, I'll start counting from here"), SYN-ACK ("agreed, and I'll
count from here"), and ACK ("agreed"). The browser does not wait after its ACK: the request can
travel in the same moment, so the handshake costs exactly one round trip. At 190 ms per round trip,
that is 190 ms in which nothing useful has happened yet.

Two details here show up in real debugging:

- **Ports.** The server listens on port 443. The browser picks a temporary port of its own, such
  as 51234, so one laptop can hold hundreds of connections. A connection is identified by all four
  numbers: two addresses and two ports.
- **IPv6 and IPv4 race.** Our lookup of `example.com` returned both IPv6 and IPv4 addresses. If
  the IPv6 path is broken, waiting for a timeout would make the page hang. So browsers use
  **Happy Eyeballs** ([RFC 8305](https://www.rfc-editor.org/rfc/rfc8305)): try IPv6 first, and if
  it has not connected within about 250 ms, start IPv4 in parallel and keep whichever wins. The
  catch: broken IPv6 then shows up only as a page that is 250 ms slow, and can go unnoticed for
  months, so test both address families on purpose.

One more TCP behaviour affects page loads directly. A new connection does not know how fast the
path is, so it starts cautiously. Under [RFC 6928](https://www.rfc-editor.org/rfc/rfc6928) the
first flight of data is at most 10 packets, about 14.6 KB, and the amount roughly doubles with
each round trip that goes well. This is called **slow start**. A 100 KB HTML page therefore takes
about three round trips to arrive in full (14.6, then 29.2, then 58.4 KB), which is where the
advice "fit what the first screen needs into the first 14 KB" comes from. The
[TCP vs UDP](/networking/tcp-vs-udp/) page goes inside this step.

### Step 3: make it private (TLS)

The connection works, but anything sent on it can be read, and changed, by every network on the
path, from the café Wi-Fi onwards. **TLS** (Transport Layer Security) fixes three things at once. It *encrypts* the data so nobody on the path can read
it, it *protects* it so nobody can change it unnoticed, and it *authenticates* the server so you
know you are talking to `shop.example.in` and not an impostor. The [TLS](/networking/tls/) page
builds each of those three promises up from first principles.

The current version, TLS 1.3, needs one round trip to set all of this up. Its specification was
revised in July 2026 as [RFC 9846](https://www.rfc-editor.org/rfc/rfc9846.html), a minor update
that keeps the version number. Step through it:

**SNI** (server name indication) explains a lot of real-world behaviour. One IP address often
serves thousands of websites, especially behind a CDN, so the server needs the site name before
encryption starts, and the browser sends it in the ClientHello, readable by anyone on the path.
A newer extension, **Encrypted Client Hello** ([RFC 9849](https://www.rfc-editor.org/info/rfc9849)),
hides it.

Certificates are also getting shorter lives. In April 2025 the CA/Browser Forum, the body of
certificate authorities and browser makers that sets the rules,
[voted](https://cabforum.org/2025/04/11/ballot-sc081v3-introduce-schedule-of-reducing-validity-and-data-reuse-periods/)
to cut the maximum lifetime of a public TLS certificate from 398 days to 200 days from March 2026,
100 days from March 2027, and 47 days from March 2029. As of October 2026 Let's Encrypt still
issues 90-day certificates by default, offers 6-day ones, and plans to reach 45 days by February
2028 ([Let's Encrypt](https://letsencrypt.org/docs/cert-lifetimes/)). It issues them through
**ACME**, a protocol that lets a server prove it controls a domain and renew automatically. The
practical consequence: renewing certificates by hand is over. Automate it, or you will have an
outage.

Now put steps 1 to 3 together and watch the round trips add up. The defaults are our worked
example: a 190 ms round trip, a 40 ms DNS lookup and 50 ms of server work. The simulation runs five
times slower than real life so you can follow each packet.

With these numbers the first byte of the page arrives at 40 + 3 × 190 + 50 = **660 ms**. Of that,
the server's own work is 50 ms, less than a tenth. The rest is the speed of light, three times
over. Drag the round trip down to 20 ms, roughly the distance to a server in your own city, and the
same page arrives in 150 ms with no change to your code at all.

### Step 4: ask for the page (HTTP)

The connection is open and private. The browser can finally ask. **HTTP** (the Hypertext Transfer
Protocol) is a request-and-response language, and in its 1.1 form it is plain text you could type
by hand. The request names a **method** (what to do: `GET` to read, `POST` to submit), a path, and
**headers**, which are lines of extra information. The response starts with a **status code**, then
its own headers, a blank line, and the body.

<Figure caption="An HTTP request is a start line and headers. The response is a status line, headers, a blank line, and the body. Headers like Cache-Control decide whether anyone may reuse this answer later.">
  <HttpMessage />
</Figure>

A handful of headers do most of the work. `Host` says which site you want, since one server hosts
many. `Cookie` carries your session. `Content-Type` says what the body is. And
`Cache-Control: max-age=60` says the browser, and any cache in between, may reuse this response
for 60 seconds without asking again; that one header is behind most of the speed of a second
visit. Status codes come in five families, and the family tells you who to blame:

| Code | Family | Means | Typical examples |
|---|---|---|---|
| 1xx | Informational | Keep going | `103 Early Hints` (start fetching these files now) |
| 2xx | Success | Here it is | `200 OK`, `204 No Content` |
| 3xx | Redirect | Look over there | `301 Moved Permanently`, `304 Not Modified` (your cached copy is still good) |
| 4xx | Client error | Your request was wrong | `404 Not Found`, `401 Unauthorized`, `429 Too Many Requests` |
| 5xx | Server error | We failed | `500 Internal Server Error`, `502 Bad Gateway`, `503 Service Unavailable`, `504 Gateway Timeout` |

Redirects deserve a warning. When we fetched `https://wikipedia.org/`, the answer was `301 Moved
Permanently`, pointing at `www.wikipedia.org`. That is a whole extra round trip, often with a fresh
DNS lookup and handshake for the new host, before the real page even starts.

HTTP has three versions in daily use. HTTP/1.1 sends one request at a time per connection, so
browsers open several connections in parallel. HTTP/2 ([RFC 9113](https://www.rfc-editor.org/rfc/rfc9113))
interleaves many requests on one connection. HTTP/3 ([RFC 9114](https://www.rfc-editor.org/rfc/rfc9114))
runs on **QUIC** ([RFC 9000](https://www.rfc-editor.org/rfc/rfc9000)), a newer transport over UDP
that merges the TCP and TLS handshakes into one round trip. The browser learns that a server
speaks HTTP/3 from a response header; `example.com` sent us `alt-svc: h3=":443"`, which means "you
can reach me over HTTP/3 on port 443 next time". As of 2025, Cloudflare saw HTTP/3 carry about 21%
of the requests to its network ([Cloudflare Radar](https://blog.cloudflare.com/radar-2025-year-in-review)),
and every browser falls back to HTTP/2 over TCP when UDP is blocked. Watch what QUIC does to our
round trips:

<RoundTripSim protocol="quic" />

Two round trips to the first byte instead of three: 40 + 2 × 190 + 50 = **470 ms**. One whole
handshake has disappeared, which from far away is worth more than any server optimisation.

### Step 5: the servers behind the address

The request has arrived at "the server", but in production that address belongs to a chain of
machines, each with its own job. This is the part of the journey you will spend most of your career
building.

<Figure caption="One address, several layers. A CDN edge near the user can answer from its cache; on a miss the request goes to a load balancer, which picks one of many app servers, which read from a cache and a database.">
  <ServerSide />
</Figure>

- A **CDN** (content delivery network) runs **edge** servers in hundreds of cities and keeps
  copies of your files close to users. When we fetched `example.com` from India, the answer
  carried `cf-ray: ...-BOM` and `age: 2031`: it came from Cloudflare's edge in Mumbai, from a
  cached copy about 34 minutes old. The origin in the US was never involved.
- A **load balancer** spreads requests across several identical copies of your app, and stops
  sending to any copy that fails its health check.
- The **app servers** run your code. This is the 50 ms your logs measure.
- **Caches and databases** hold the data. A database query that misses an index can make this the
  slowest step of all, which is when the server really is the problem.

in a city pays the long trip; everyone after them does not.

The time from sending the request to receiving the first byte of the answer has a name you will
see in every performance tool: **time to first byte** (TTFB). It includes one round trip plus all
the work on the server side, so it is where the server's share of the delay shows up.

### Step 6: turn bytes into pixels

The first bytes of HTML arrive, and the browser starts work before the rest has finished
downloading. Chrome, for example, splits the work between a browser process that handles the
network and a separate **renderer** process per site, which turns the page into pixels. What
happens inside the renderer is called the **critical rendering path**.

<Figure caption="HTML becomes the DOM and CSS becomes the CSSOM; together they make the render tree, which is laid out, painted and composited onto the screen. Every image, script and font the HTML mentions starts a new trip through the network steps.">
  <RenderPipeline />
</Figure>

1. **Parse the HTML into the DOM** (Document Object Model), a tree of every element on the page.
2. **Parse the CSS into the CSSOM**, a tree of style rules. A page will not show until its CSS is
   ready, because showing it unstyled and then restyling it would flash. That makes CSS
   **render-blocking**.
3. **Build the render tree**: only what will be displayed, each with its final styles. Hidden
   elements are left out.
4. **Layout** works out the size and position of every box. **Paint** fills in the pixels.
   **Composite** stacks the painted layers onto the screen in the right order.

The part that matters most for speed is the loop at the bottom. Every `<link>`, `<script>`, `<img>`
and font the HTML mentions is a new request, and each one goes through steps 1 to 4 again: a DNS
lookup if it is on a new host, a handshake if there is no open connection, and a round trip for the
request itself. That is why every extra host a page uses (fonts from one, analytics from another)
costs time. Browsers help: a **preload scanner** reads ahead in the HTML and starts downloads
early, and connections to the same host are reused. But some requests can only start once an
earlier one finishes. The HTML names a stylesheet, the stylesheet names a font, a script calls an
API. Each link in that chain is at least one more round trip.

A plain `<script>` tag also stops the HTML parser until the script has downloaded and run, because
scripts can change the page; `defer` or `async` on the tag lets parsing continue. And there is a
lot to fetch: in the HTTP Archive's 2025 Web Almanac, the median home page was about 2.6 MB on
mobile, made of roughly 75 to 80 requests
([Web Almanac 2025](https://almanac.httparchive.org/en/2025/page-weight)).

This is the rest of the three seconds in our opening story. The HTML arrived at about 660 ms. The
CSS and the main script took one more round trip each, and the script called an API, one more.
The images were on a separate domain: a new DNS lookup and a new handshake. Five or six dependent
round trips at 190 to 300 ms each on a mobile network add up to three seconds, while the server
did 50 ms of work for each request.

### The second visit is different

Load the same page again a minute later and almost every step above is skipped or shortened:

- **DNS**: answered from the browser's or the OS's cache, 0 ms.
- **Connection**: browsers keep connections open for a while after use, so a request soon after
  can reuse one and skip TCP and TLS entirely. If the connection has closed, TLS 1.3 can resume a
  previous session, and with **0-RTT** the browser can even send its request in the first flight.
  0-RTT data can be replayed by an attacker, so it is only safe for requests that change nothing.
- **The files**: anything with a fresh `Cache-Control` lifetime comes straight from the browser's
  cache with no request at all. Anything stale can be checked with a short "has it changed?"
  request, answered with `304 Not Modified` and no body.

Our hand-made client in "Build it yourself" measured this directly: the first request to
`example.com`, with DNS, TCP and TLS included, took 151 ms. A second request on the same open
connection took 17 ms. Nearly 90% of the first request was set-up.

## Build it yourself

The naive fetch gave us one number and no diagnosis. We will build two tools, each closer to what
production systems use: a client that does every step by hand and times it, and a probe that puts
a timeout on every step and reports which one failed. Both use only the standard library. Every
file, including the DNS walker from step 1, is in

### Step 1: every step by hand, with a stopwatch

Instead of one `fetch`, we look up the address, open the TCP connection, wrap it in TLS, and write
the HTTP request ourselves, timing each step. Printing and reading the response (which must handle

    #    its configured resolver (and may answer from its own cache).

    family, _, _, _, sockaddr = infos[0]
    t = time.perf_counter()

### Step 2: a probe that says which step failed

The production-shaped version is the kind of check uptime monitors run: a timeout on every step,
every address tried in turn, and when something fails, the name of the step and what a browser
would have shown. Here is the connect step; the DNS, TLS and response steps in the full file follow
the same pattern, and the TLS step maps certificate errors to the browser's names for them:

<Tabs syncKey="lang">
  <TabItem label="Python">
```python title="probe.py"
# runnable version: examples/how-the-web-works/python/probe.py
TIMEOUTS = {"dns": 3.0, "connect": 3.0, "tls": 5.0, "response": 10.0}  # seconds, per step


def connect(infos: list[tuple]) -> socket.socket:
    # Try each address in turn (browsers race IPv6 and IPv4 instead: "Happy Eyeballs").
    last = StepFailed("connect", "no addresses", "ERR_NAME_NOT_RESOLVED")
    for family, _, _, _, sockaddr in infos:
        sock = socket.socket(family, socket.SOCK_STREAM)
        sock.settimeout(TIMEOUTS["connect"])
        try:
            sock.connect(sockaddr)
            return sock
        except TimeoutError:
            last = StepFailed("connect", f"no answer from {sockaddr[0]}", "ERR_CONNECTION_TIMED_OUT")
        except ConnectionRefusedError:
            last = StepFailed("connect", f"{sockaddr[0]} refused", "ERR_CONNECTION_REFUSED")
        sock.close()
    raise last
```

/** Try each address in turn (browsers race IPv6 and IPv4 instead: "Happy Eyeballs"). */
async function connect(addresses, port) {
  let last = new StepFailed('connect', 'no addresses', 'ERR_NAME_NOT_RESOLVED');
  for (const { address } of addresses) {
    const sock = net.connect({ host: address, port });
    try {
      await within(TIMEOUTS.connect, new Promise((ok, fail) => sock.once('connect', ok).once('error', fail)),
        () => new StepFailed('connect', `no answer from ${address}`, 'ERR_CONNECTION_TIMED_OUT'));
      return sock;
    } catch (err) {
      sock.destroy();

    }
  }
  throw last;
}

## How real systems do it

The steps are standard; what differs between real systems is how hard they work to skip them.

**Browsers race and guess ahead.** Chrome starts finding or launching the renderer process for a
site while the network request is still in flight, because it already knows which site it is
going to. It reads ahead in HTML with the preload scanner, races IPv6 against IPv4, and keeps
connections open to reuse them. Pages can help it further: `<link rel="preconnect">` tells the
browser to do the DNS lookup and handshake for a host before it is needed, and the `103 Early Hints`
status lets a server name critical files while it is still building the page.

**CDNs move the far end closer.** Large CDNs use **anycast**: the same IP address is announced from
hundreds of data centres, and the internet's routing sends each user to the nearest one. That is
why our `example.com` requests from India were answered in Mumbai, with a TCP round trip of about
14 ms. The DNS root servers use the same trick, which is how 13 identities become over 2,000
instances. The CDN also keeps long-lived connections back to the origin, so even uncacheable
requests skip a long handshake.

**Everything degrades gracefully.** Old clients, old servers and network devices that block UDP,
such as some corporate firewalls, keep older protocols alive for years. So every browser falls
back: if HTTP/3 does not work it uses HTTP/2 over TCP, if IPv6 is slow it uses IPv4, and if a
session cannot be resumed it does a full handshake. The fast path is an optimisation, never a
requirement.

## Gotchas and war stories

:::danger[A real outage: the day DNS could not find Facebook]
On 4 October 2021, a command meant to check Facebook's backbone capacity took the whole backbone
down. Facebook's DNS servers are designed to stop advertising their addresses when they lose
contact with the data centres, and that is what they did. The servers were still running, but
nobody could reach them, so `facebook.com`, Instagram and WhatsApp stopped resolving everywhere for
about five and a half hours, while resolvers handled around 30 times their usual load from
retries. Recovery was slow partly because the same failure broke the engineers' internal tools.
([Facebook's write-up](https://engineering.fb.com/2021/10/05/networking-traffic/outage-details/),
[Cloudflare's view](https://blog.cloudflare.com/october-2021-facebook-outage/))
:::

The lesson: if your DNS is unreachable, a perfectly healthy server is invisible.

**You cannot take back a cached answer.** On 30 September 2021, Slack enabled DNSSEC (a system that
signs DNS answers so they cannot be forged) and some users began seeing `ERR_NAME_NOT_RESOLVED`. The
team rolled the change back, which made things worse: resolvers had cached a record from the `.com`
zone saying "slack.com is signed", with a 24-hour TTL Slack did not control, so unsigned answers
now looked forged. Fewer than 1% of users were affected, but it lasted about 24 hours
([Slack's write-up](https://slack.engineering/what-happened-during-slacks-dnssec-rollout/)). Plan
every DNS change around the longest TTL involved, including ones set by someone else.

**One resolver is one point of failure.** On 14 July 2025, a configuration error withdrew the
routes to Cloudflare's 1.1.1.1 resolver worldwide for 62 minutes. For users whose devices used only
1.1.1.1, almost every site appeared to be down, though nothing was wrong with the sites
([Cloudflare's postmortem](https://blog.cloudflare.com/cloudflare-1-1-1-1-incident-on-july-14-2025/)).
Devices and servers should be configured with resolvers from more than one provider.

:::caution[Always set a timeout on every step]
The naive fetch near the top of this page waited 21 to 135 s for a server that never answered. A
service that calls another service without timeouts can have every one of its threads stuck
waiting like that, and stop serving everyone. The Timeouts page in the Resilience track is about
exactly this.
:::

**A 301 can be forever.** Browsers cache permanent redirects, often with no expiry, so a mistaken
`301` keeps sending visitors to the wrong place after you fix the server. Use `302` or `307` while
testing a redirect.

**"It works on my machine" is often a cache.** Your laptop may have an old DNS answer, a hosts file
entry from a previous project, a VPN with its own DNS, an HSTS entry, or a cached `301`. When you
cannot reproduce a user's problem, try a private window, a different network (your phone's mobile
data is a good one), and `curl -v`, which bypasses the browser's caches entirely.

## Trade-offs and limits of the model

Every step of this journey is a trade-off someone made, and you will make the same ones.

- **Layers cost round trips, and buy independence.** Each layer can be replaced without the
  others: TLS moved from 1.2 to 1.3 without changing HTTP. The price is that each needs its own
  set-up. QUIC trades some of that independence for speed by merging two layers.
- **Caching trades freshness for speed.** Long DNS TTLs and long `Cache-Control` lifetimes make
  repeat visits fast and reduce load, and make every change slow to reach users. Short ones do the
  opposite. There is no right answer, only a right answer for each record and each file.
- **Encryption is no longer the expensive part.** TLS 1.3 costs one round trip, often zero on a
  reused connection, and the computing cost is small on modern hardware.
- **Moving closer costs money and complexity.** A CDN or servers in several regions remove round
  trips for distant users, but add a bill, a cache to invalidate, and more places for things to go
  wrong. For an internal tool used in one office, they are not worth it.

This page's model also has limits. A mobile app skips the address bar and rendering but makes the
same network trips. A chat or a live dashboard opens one long-lived connection, such as a
WebSocket, and then pays close to one-way latency per message. Server-to-server calls inside one
data centre have round trips of well under a millisecond, so there the server work dominates and
this page's latency arithmetic flips around.

:::note[From the trenches]
When a page is slow, people reach for the part of the stack they know best: back-end engineers tune
queries, front-end engineers shrink bundles. The first useful question is simpler: how many round
trips does this page need, and how long is each one?
:::

## Interview corner

"What happens when you type a URL into a browser and press Enter?" is one of the oldest interview
questions in the industry, asked of new grads and senior engineers alike. It can go as deep as the
interviewer likes; what it tests is whether you have the whole map and know where the time and the
failures are.

Typical questions, and what a strong answer covers:

1. **"Walk me through what happens when I type example.com and press Enter."** Give the outline
   first, in order: URL parsing and HSTS, cache checks, DNS, TCP, TLS, HTTP, the servers behind the
   address, rendering, and further requests. Then offer to go deep on any step. Mentioning what a
   repeat visit skips, and why, is a strong signal.
2. **"How does DNS resolution work?"** Browser and OS caches, the recursive resolver, root, TLD and
   authoritative servers, referrals, and TTLs, and why the root is rarely asked.
3. **"A page loads slowly for users in another country. How would you investigate and fix it?"**
   Measure first, from that country, and separate round trips from server time. Then: a CDN, fewer
   hosts and redirects, connection reuse, HTTP/2 or HTTP/3, caching headers, then the server code.
4. **"A user gets `ERR_CONNECTION_REFUSED` and another gets `ERR_CONNECTION_TIMED_OUT`. What is
   different?"** Refused means a machine answered and nothing listens on that port; timed out means
   nothing answered at all, often a firewall or a wrong address.

Interviewers also listen for the server side. Saying "and then the server responds" misses the
load balancer, the app servers and the database, which is where most of your actual job will be.

<details>
<summary>1. A user is 150 ms (round trip) from your server. DNS is already cached, the server needs 30 ms to build the page, and it uses TCP with TLS 1.3. When does the first byte arrive? What if the server supported HTTP/3?</summary>

TCP takes one round trip, TLS 1.3 one more, and the request one more, plus the server's work: 3 ×
150 + 30 = 480 ms. With HTTP/3, QUIC sets up the connection and encryption in a single round trip,
so it is 2 × 150 + 30 = 330 ms. On an already-open connection it would be 150 + 30 = 180 ms.

</details>

<details>
<summary>2. A user visits https://shop.example.in/cart#pay. Which parts of that URL does the server receive?</summary>

The server receives the host (in the TLS handshake's SNI and in the `Host` header) and the path
`/cart`. The scheme decides how the browser connects, and the port is implied (443). The fragment
`#pay` is never sent; it stays in the browser. Any query string, such as `?item=42`, would be sent
with the path.

</details>

<details>
<summary>3. You moved your site to a new server and updated the DNS record an hour ago. Half your users still reach the old server. The record's TTL was 86,400. Why, and what should you have done?</summary>

Resolvers that looked up the old address before your change may keep it for up to 86,400 seconds,
one day, and nothing you do now can make them forget. Keep the old server running until the old
TTL has passed. Next time, lower the TTL to a few minutes a day or two before the move, so that by
the time you switch, no resolver holds the old answer for long.

</details>

<details>
<summary>4. Your certificate covers *.example.com. Will browsers accept it for api.example.com? For v2.api.example.com? For example.com itself?</summary>

`api.example.com`: yes, the wildcard covers one level. `v2.api.example.com`: no, that is two levels
below `example.com`, and a wildcard never covers more than one. `example.com`: no, the bare domain
is not covered by `*.example.com`; certificates usually list it separately, as `badssl.com`'s
certificate does.

</details>

## Recap

- A page load is **find (DNS), connect (TCP), secure (TLS), ask (HTTP), serve (servers behind the
  address), draw (render)**, then the same again for every file the page needs.
- The cost is counted in **round trips**, and **distance sets their price**: light in fibre covers
  about 200 km per ms, so India to the US East Coast is about 190 ms. On a first visit over TCP and
  TLS 1.3, the first byte needs three round trips plus DNS and server work; HTTP/3 needs two; a
  reused connection needs one.
- **DNS is a cached tree**: browser, OS, resolver, then root, TLD and authoritative servers. TTLs
  make lookups fast and changes slow.
- **TLS 1.3** encrypts, protects and authenticates in one round trip. Certificates must match the
  name, be in date and chain to a trusted root, and their lifetimes are shrinking towards 47 days,
  so automate renewal.
- Behind one address sit a **CDN edge, a load balancer, app servers and a database**. A CDN helps
  distant users even for pages it cannot cache, because handshakes happen close to them.
- The **critical rendering path** waits on CSS and plain scripts, and **chains of dependent
  requests** are what make pages slow.
- Every step fails with its own error. **Measure each step** with the waterfall or `curl -w`, and
  **put a timeout on every step** of every outgoing call.
