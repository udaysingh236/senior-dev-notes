## The question

A user on a 1 Gbit/s fibre line is 150 ms from your server and asks for a 100 KB HTML page. The
line could carry 100 KB in under a millisecond. The last byte arrives about 450 ms after the
request, and upgrading the user to 10 Gbit/s would not change that by a single round trip. Then
you put a CDN in front of the server, one that cannot cache this page at all because it is built
per user, and the page gets twice as fast anyway. Why?

You already know the order: DNS, then TCP, then TLS, then HTTP. This page is about the accounting
nobody shows you: **which round trips a page load cannot avoid, which ones can overlap, which caches
skip which ones, and what quietly adds a second without an error anywhere.**

## Why the time is not where you think

A **round trip** is a message to the server and its reply back; the **round-trip time** (RTT) is
how long that takes. Light in optical fibre covers about 200 km per millisecond, so distance sets a
floor no hardware removes. Mumbai to northern Virginia is about 13,000 km in a straight line, 65 ms
each way at best; the measured round trip between the AWS regions there is about 187 ms, as of
October 2026 ([cloudping.co](https://www.cloudping.co/)), because cables do not run straight and
every router adds a little.

The time to load anything over a network has three terms:

- **Round trips that must happen one after another**, times the RTT.
- **Work on the server**, the only part your logs and APM traces measure.
- **Bytes divided by bandwidth**, the only part a faster connection improves.

For web pages the first term dominates, and it is the one people forget to count. Mike Belshe at
Google measured this in 2010: holding the RTT at 60 ms and raising bandwidth, page load time
improved by only 5% going from 5 to 10 Mbit/s, and at 10 Mbit/s pages used about 16% of the link
they had. Lowering the RTT, by contrast, improved load time steadily at every step
([Belshe, 2010](https://www.belshe.com/2010/05/24/)). Pages are bigger now, and a 2025 study argues
that on mobile networks bandwidth matters more than that result suggests for large images
([Mostafa et al., 2025](https://arxiv.org/html/2503.03641v1)). The shape still holds for the part of
the page that blocks the first render: HTML, CSS, fonts and the first API calls are small, and
small transfers are bound by round trips.

The rest of this page counts those round trips: how many each step costs, why a small file can
cost three of them, which ones a warm connection or a cache removes, and which ones are stuck in a
chain behind each other.

## The obvious fixes, and why they miss

When a page is slow for distant users, teams usually try one of two things.

**A bigger server.** If your logs say the HTML takes 50 ms to build and the user waits 2 s, then
shaving 20 ms off the server leaves 1.98 s. The server is the only part of the load you can see
from the server, so it gets all the attention.

**More bandwidth.** It helps when the transfer is bandwidth-bound, which for most of a page load
it is not. Here are the numbers from the runnable latency budget in
["Build it yourself"](#build-it-yourself), for 100 KB of HTML on a new connection with 50 ms of
server work:

| RTT | 10 Mbit/s | 100 Mbit/s | 1 Gbit/s | Naive estimate at 1 Gbit/s |
|---|---|---|---|---|
| 20 ms | 270 ms | 198 ms | 191 ms | 0.8 ms |
| 75 ms | 545 ms | 473 ms | 466 ms | 0.8 ms |
| 150 ms | 920 ms | 848 ms | 841 ms | 0.8 ms |

Read across a row: a hundred times the bandwidth saves about 80 ms. Read down a column: every 75 ms
of distance costs about 375 ms, because the load needs five sequential round trips (connect,
secure, request, and two more rounds of data) and each one pays the distance again. The fix is in
the count of round trips and in their length, not in the pipe.

Two terms get mixed up here. **Latency** is how long one message takes to arrive; **throughput** is
how many bytes per second you actually get, which on a short transfer is far below the link's
**bandwidth** because the sender has not been allowed to use it yet (the slow start section shows
why). And **time to first byte** (TTFB) in DevTools is not server time: it is one full round trip
plus server time, so a 50 ms handler shows as a 200 ms TTFB to a user 150 ms away.

## The core idea

A page load is not one download. It is a **chain of discoveries**: the browser cannot ask for the
CSS until the HTML names it, cannot ask for the font until the CSS names it, and cannot call the
API until the JavaScript runs. Each link in the chain costs at least one round trip, and a link to
a host the browser has not talked to yet costs a DNS lookup plus a connection set-up on top. The
load time is the length of the **critical path**: the longest chain of round trips that each wait
for the previous one.

Everything in web performance attacks one of three numbers in that picture: the **length of each
round trip** (move the server closer, or end connections at an edge near the user), the **round
trips per link** (fewer handshakes, warm connections, bigger first windows), and the **number of
links in the chain** (find resources earlier, cache them, cut dependencies). The sections below take
the round trips one kind at a time.

## How it works, piece by piece

### Before the first byte: set-up round trips

On a new connection, the request cannot leave until the transport and the encryption are agreed.
Over TCP that is one round trip for the handshake and one for TLS 1.3; TLS 1.2 needed two. QUIC,
the transport under HTTP/3, does the transport and TLS 1.3 handshakes in the same packets. Here is
what each costs at 150 ms, with 50 ms of server work after the request arrives:

<Figure caption="Round trips before the first byte at 150 ms per round trip, plus 50 ms of server work. Each newer protocol removes one round trip; 0-RTT resumption and a reused connection leave only the request itself.">
  <HandshakeCost />
</Figure>

The jump from 650 ms to 200 ms is pure protocol: the server and the code did not change. The
[TLS page](/networking/tls/) covers the handshake messages; three behaviours around them matter
for timing:

- **0-RTT is not free.** TLS 1.3 and QUIC let a returning client send its request in the first
  flight using a key from the last visit. An attacker who records that flight can replay it, so
  servers should accept 0-RTT only for requests that are safe to run twice. nginx leaves it off
  unless you set `ssl_early_data on`
  ([nginx docs](https://nginx.org/en/docs/http/ngx_http_ssl_module.html#ssl_early_data)). Plain
  resumption without 0-RTT skips the certificate work but still costs the full round trip.
- **The first visit usually cannot use HTTP/3.** A browser learns that a server speaks HTTP/3 from
  an `Alt-Svc` header on an HTTP/2 response, so the first connection is TCP and only the next one
  is QUIC. An `HTTPS` record in DNS ([RFC 9460](https://www.rfc-editor.org/rfc/rfc9460)) can
  advertise `h3` before the first connection, where the browser asks for it. And between 3% and 5%
  of networks block UDP entirely ([RFC 9308](https://www.rfc-editor.org/rfc/rfc9308)), so browsers
  race QUIC against TCP and fall back without telling anyone.
- **Broken IPv6 costs 250 ms, silently.** When a name has both IPv6 and IPv4 addresses, browsers
  try IPv6 first and start IPv4 in parallel if it has not connected after about 250 ms (**Happy
  Eyeballs**, [RFC 8305](https://www.rfc-editor.org/rfc/rfc8305)). A broken IPv6 route is therefore
  never an error, only a quarter of a second added to every new connection.

DNS sits in front of all of this, once per new host. A hit in the browser's or the operating
system's cache is free; a hit in the resolver's cache costs one round trip to the resolver, usually
a few milliseconds to tens; a miss sends the resolver to the root, the top-level domain and the
domain's own servers, which can take hundreds. The [DNS page](/networking/dns/) covers how those
caches decide. For timing, the rule is that each extra hostname on the critical path is another
lookup that may miss.

### Slow start: why bandwidth does not help small responses

The connection is open; now the response has to arrive. A new TCP connection does not know how
much the path between you can carry, so it may not send everything at once. It starts with an
**initial congestion window** of 10 packets, about 14.6 KB
([RFC 6928](https://www.rfc-editor.org/rfc/rfc6928)), waits for those to be acknowledged, and
doubles the window each round trip that goes well. This is **slow start**.

So the number of round trips a response needs depends on its size, not on the link:

| Response | Packets of 1,460 bytes | Round trips of data |
|---|---|---|
| 14 KB | 10 | 1 |
| 15 KB | 11 | 2 |
| 100 KB | 69 | 3 (10 + 20 + 39) |
| 1 MB | 685 | 7 |

To fill a 100 Mbit/s link with a 150 ms round trip, a sender needs about 1.9 MB in flight, the
**bandwidth-delay product**: 1,284 packets. Starting from 10, the window needs seven doublings to
get there, so the first second of every new connection runs far below the speed you paid for. This
is the reason behind the advice to fit what the first screen needs into the first 14 KB of HTML:
the first round trip is the only one that arrives with the first byte.

The comparison bars carry the lesson: 455 ms on the default link, 450 ms with ten times the
bandwidth, 230 ms with half the distance. Bandwidth only starts to matter once the window is wider
than the pipe, which for a fresh connection means a response well past a megabyte. Raising the
initial window to 30 packets saves a round trip on 100 KB, which is why several CDNs run with more
than 10: a 2017 survey measured 32 at Akamai and 46 at CacheFly, against Linux's default of 10 at
Cloudflare and Fastly ([CDN Planet, 2017](https://www.cdnplanet.com/blog/initcwnd-settings-major-cdn-providers/);
these values are old and may have changed).

**Loss ends the doubling.** In the sim, set the loss to 2%: one lost packet in the second round cuts
the window to 70% (CUBIC's reduction; older Reno halves it), and from then on it grows by one packet
per round trip instead of doubling. The same 100 KB now takes six rounds, 900 ms. On a link that
loses 1% of packets, 1 MB takes over six seconds at 150 ms. Loss is the reason a page that is fine
on office Wi-Fi crawls on a train.

**TLS records can cost a round trip of their own.** TLS encrypts data in records of up to 16 KB,
and the browser cannot decrypt a record until all of it has arrived. A 16 KB record that does not
fit in the 14.6 KB first window waits for the second round trip, along with every byte inside it,
including the `<head>` the browser wanted first. nginx writes 16 KB records by default
(`ssl_buffer_size`); Cloudflare patched it to start with records that fit one packet and grow them
later ([Cloudflare, 2016](https://blog.cloudflare.com/optimizing-tls-over-tcp-to-reduce-latency/)).
Setting `ssl_buffer_size 4k;` is a common middle ground.

### Reused connections, and what quietly resets them

A request on a connection that is already open skips DNS, TCP and TLS, and it finds a window that
has already grown. Measured against Cloudflare's edge in Mumbai from a network in India, the first
request to `example.com` took 151 ms with set-up included and the second, on the same connection,
17 ms (the full output is in ["Build it yourself"](#build-it-yourself)). Connection reuse is the
biggest saving on any page that is not the first, and several things take it away without telling
you.

**Idle connections forget their window.** Linux servers, by default, shrink the congestion window
of a connection that has been idle for longer than its retransmission timeout (at least 200 ms plus
the round trip): the window halves for each timeout of idleness, down to the initial 10 packets.
The setting is `net.ipv4.tcp_slow_start_after_idle`, on by default
([kernel docs](https://www.kernel.org/doc/html/latest/networking/ip-sysctl.html)). A keep-alive
connection that sat quiet for a second while the user read the page is back to slow start for the
next response. Servers that hold long-lived connections to clients (HTTP/2 front ends, APIs called
in bursts) often turn it off.

**HTTP/1.1 opens many connections, each one cold.** HTTP/1.1 carries one response at a time per
connection, so browsers open several per host: six in Chromium, as of October 2026
([Chromium source](https://chromium.googlesource.com/chromium/src/+/main/net/socket/client_socket_pool_manager.cc)).
Each pays its own handshakes and starts its own slow start. HTTP/2 and HTTP/3 send every request to
a host over one connection, which stays warm. HTTP/2 can even **coalesce** hosts: if
`img.example.com` resolves to the same address as `www.example.com` and the certificate covers
both names, the browser may reuse the existing connection
([RFC 9113, section 9.1.1](https://www.rfc-editor.org/rfc/rfc9113#section-9.1.1)). The old HTTP/1.1
trick of **domain sharding**, spreading files over `static1`, `static2` and so on to get more
parallel connections, now costs extra lookups and handshakes for nothing.

**The browser keeps separate pools.** "The connection is already open" is true less often than it
looks, because the browser will not mix connections across certain boundaries:

<Figure caption="One server, three connections. A request with cookies and an anonymous request (fonts are always fetched this way) use different pools, and so do requests made on behalf of different top-level sites. Each pool pays its own handshakes and its own slow start.">
  <ConnectionPools />
</Figure>

Two of those boundaries surprise people. Fonts are fetched in **anonymous** (credential-less) CORS
mode, so they cannot reuse a connection opened for credentialed requests; a
`<link rel="preconnect">` to a font host does nothing useful unless it carries `crossorigin`
([web.dev](https://web.dev/articles/preconnect-and-dns-prefetch)). And Chromium partitions
connections, DNS cache entries and TLS session tickets by the top-level site, so a connection
your site opened to a shared CDN cannot be reused by another site, and vice versa
([Chromium Intent to Ship, 2022](https://groups.google.com/a/chromium.org/g/blink-dev/c/tJa6uzXu_IA)).
The same partitioning applies to the HTTP cache (see the cache section below).

### HTTP/1.1, HTTP/2 and HTTP/3: where head-of-line blocking went

**Head-of-line blocking** is when one slow or lost item holds up items behind it that are ready.
Each HTTP version moved it to a different layer:

- **HTTP/1.1**: one response at a time per connection, so a slow response blocks the next request
  on that connection. Browsers work around it with six connections.
- **HTTP/2**: many streams interleaved on one TCP connection, so no response waits for another at
  the HTTP layer. But TCP delivers bytes strictly in order. When one packet is lost, every byte
  behind it on the connection waits for the resend, whichever stream it belongs to.
- **HTTP/3**: streams over QUIC, which orders bytes per stream. A lost packet stalls only the
  stream it belonged to.

That suggests HTTP/3 should win clearly on lossy links. Watch what happens with twelve files on a
link that loses 2% of packets, with every connection already open so only the transfer counts.
Amber marks bytes that have arrived but cannot be used, because an earlier packet is missing:

<HolSim />

Two things show up that the protocol diagrams do not tell you. First, HTTP/3 removes the amber, but
with these defaults it finishes at the same 2.1 s as HTTP/2: both run every file through one
congestion window, and every loss cuts that one window. Head-of-line blocking delays individual
files; the shared window slows all of them. Second, HTTP/1.1 finishes first, at 600 ms, because six
connections means six windows: 60 packets in the first round instead of 10, and a loss cuts only
one sixth of the sending. That matches an old observation from curl's author that at around 2%
loss, HTTP/1.1 users tend to do better than HTTP/2 users
([HTTP/3 explained](https://http3-explained.haxx.se/)). The sim's model is
simplified (no selective acknowledgements, no pacing differences), so read its gaps as directions,
not predictions.

HTTP/3's real gains come from elsewhere: one round trip less to connect, 0-RTT on return visits, and
better loss recovery. Google reported that QUIC cut search latency by 8% on desktop and 3.6% on
mobile, and YouTube rebuffering by 18% and 15%
([Langley et al., SIGCOMM 2017](https://research.google/pubs/the-quic-transport-protocol-design-and-internet-scale-deployment/)).
HTTP/3 carried about 21% of requests to Cloudflare in 2025, against 50% for HTTP/2
([Cloudflare Radar 2025](https://blog.cloudflare.com/radar-2025-year-in-review)).

### The critical path: what waits for what

Now put the pieces together on a whole page. This one has HTML on `www`, a stylesheet and a 120 KB
script on the same host, eight images on an image host, a web font on a third-party font CDN, and an
API call the script makes once it has run. The sim works out, at every millisecond, what the
browser knows it needs, which connection can carry it, and when each window of data arrives.

<WaterfallSim />

The defaults are the story from the opening: 50 ms of server work, about 1.8 s of loading. Read the
rows from the top and the chain is visible:

1. HTML: lookup, two set-up round trips, the request: first byte at 540 ms.
2. CSS and JS are named in the first HTML packets and ride the same HTTP/2 connection, whose window
   has already grown.
3. The font is not discovered until the CSS has arrived and been parsed, at 990 ms. New host: a
   lookup and two round trips more before its request even leaves.
4. The API call waits for the JavaScript to download and run, then pays for a new host as well.
   It is the last thing to finish, at 1.76 s.

Now try the levers one at a time and compare with the defaults:

| Change | First render | Everything loaded | Why |
|---|---|---|---|
| None (HTTP/2, 150 ms, first visit) | 990 ms | 1.78 s | |
| HTTP/1.1 | 1.14 s | 2.06 s | CSS and JS need new connections while the HTML one is busy; 11 connections, all cold |
| HTTP/3 | 840 ms | 1.48 s | One set-up round trip less on each of four hosts |
| Preconnect to font and API hosts | 990 ms | 1.78 s (API at 1.42 s) | Set-up overlaps the HTML download instead of following it |
| CDN edge 20 ms away | 360 ms | 760 ms | Every handshake and slow-start round costs 20 ms, not 150 |
| Repeat visit | 650 ms | 1.08 s | DNS and static files come from caches; HTML and the API call still pay |

The table makes the priorities plain. Preconnect does not move first render at all here, because
the font and API are not on the chain to it, but it takes 340 ms off the moment the data appears.
The CDN beats every protocol change, because it shortens every round trip at once. And the repeat
visit is still over a second, because the two per-user responses (the HTML and the API call) are
exactly the ones no cache can serve.

The tools for shortening the chain itself: the browser's **preload scanner** already reads ahead in
the HTML for files it will need; `<link rel="preload">` names files it cannot find that way (a font
inside CSS, an API response); `rel="preconnect"` starts DNS and handshakes for hosts it will need;
and the `103 Early Hints` status lets the server send those hints while it is still building the
HTML ([RFC 8297](https://www.rfc-editor.org/rfc/rfc8297)). The most effective fix is structural:
render the data the first view needs into the HTML, so there is no JavaScript-then-API link at all.

### Caches at every layer, and what each one skips

Every layer of the journey has a cache, and each one removes a different set of round trips. They
fail differently too:

| Cache | Skips | Lifetime set by | What surprises people |
|---|---|---|---|
| Browser and OS DNS cache | the lookup | the record's TTL | Moving a server takes up to the old TTL to reach everyone |
| HTTP cache, fresh entry | everything: no request at all | `Cache-Control: max-age` | Partitioned by top-level site since Chrome 86 (2020) and Firefox 85 (2021): a library on a shared public CDN is downloaded again for every site |
| HTTP cache, stale entry | the body only | `ETag` or `Last-Modified` | A `304 Not Modified` still costs a full round trip, plus a connection if none is open |
| TLS session ticket | certificate checks; with 0-RTT, the TLS round trip | the server's ticket lifetime | Without 0-RTT, resumption saves CPU, not a round trip |
| Open connection | DNS, TCP and TLS, and the window has grown | browser and server idle timeouts | An idle connection may be back in slow start |
| CDN edge | the trip to the origin | `Cache-Control`, `s-maxage` | Even a miss is faster than going direct (next section) |
| Back/forward cache | the whole page load | the browser | some pages are not eligible, for example ones holding an open WebSocket |

The shared-library point deserves a sentence of its own, because the advice is still repeated:
"load jQuery from a public CDN so it is already cached" stopped working when browsers partitioned
the HTTP cache to stop sites detecting each other's visitors
([Chrome developers blog](https://developer.chrome.com/blog/http-cache-partitioning)). Self-host it
on a host you already have a connection to.

The second-visit numbers depend heavily on `Cache-Control`. A file served with
`max-age=31536000, immutable` and a content hash in its name (`app.3f9a2c.js`) costs nothing on the
next visit. The same file with `no-cache` costs a round trip every time to learn that it has not
changed.

### Why a CDN speeds up pages it cannot cache

Back to the second question from the top. A **CDN edge** is a server near the user, reached
through anycast or DNS steering, that ends the user's TCP and TLS connection. For a per-user page
it has to ask the origin, but it does so over a connection it keeps open all the time, whose window
is already large. The handshakes and the slow-start rounds, the round trips that multiply, now
happen over 20 ms instead of 150:

<Figure caption="The same 30 KB of uncacheable HTML. Direct, every set-up and slow-start round trip crosses the full 150 ms. Through the edge, those happen over 20 ms, and the one long hop rides a connection that is already open with a warm window. Numbers from the page sim's model.">
  <SplitConnection />
</Figure>

From 690 ms to 320 ms for a response the CDN never stores. This is called **split TCP**, or TCP
termination at the edge, and it is the part of a CDN's value that does not depend on cache hit
ratios. The cost: one more hop that can fail, and a provider in the middle of your TLS.

## Choosing what to fix first

Measure before you choose: the DevTools Network tab breaks every request into queueing, DNS,
initial connection, SSL, waiting (TTFB) and content download. Then match the pattern:

| What the waterfall shows | Likely cause | Fix, cheapest first |
|---|---|---|
| Long "initial connection" and "SSL" on many rows | many hosts, distant server | fewer hosts, preconnect, a CDN, HTTP/3 |
| TTFB far above your server time | distance (TTFB = RTT + server) | a CDN edge, or a region nearer the users |
| TTFB high even nearby | the server | your code, queries, downstream calls |
| Gaps where nothing downloads | a dependency chain | preload, inline critical CSS, render data into HTML |
| A large file that takes many round trips | slow start, or loss | smaller critical files, compression, bigger initial window at the edge |
| Fine on Wi-Fi, slow on mobile | loss and RTT variance | fewer round trips everywhere; HTTP/3 helps most here |

:::tip[Measure from where your users are]
A waterfall from your laptop, 5 ms from the data centre, shows none of this. Test from the
country your users are in, on a throttled mobile profile, or with a synthetic monitoring service
there. The numbers on this page change by a factor of ten with distance.
:::

## Build it yourself

Three tools, from arithmetic to measurement. All three use only the standard library; the files are
in [`examples/how-the-web-works/`](https://github.com/udaysingh236/senior-dev-notes/tree/main/examples/how-the-web-works).

### Step 1: a latency budget in round trips

Before measuring anything, count. This is the model behind the table near the top of the page: the
naive estimate divides bytes by bandwidth; the real one counts set-up, the request, server work and
slow-start rounds.

<Tabs syncKey="lang">
  <TabItem label="Python">
```python title="latency_budget.py"
# runnable version: examples/how-the-web-works/python/latency_budget.py
MSS = 1460  # bytes of payload in one TCP packet
INITCWND = 10  # packets in the first round trip of data (RFC 6928)


def data_rounds(size_bytes: int, initcwnd: int = INITCWND) -> int:
    """Round trips of data a fresh connection needs: the window doubles every round trip."""
    packets = math.ceil(size_bytes / MSS)
    rounds, window = 0, initcwnd
    while packets > 0:
        packets -= window
        window *= 2
        rounds += 1
    return rounds


def naive_ms(size_kb: int, mbps: float) -> float:
    """What most people estimate: bytes divided by bandwidth."""
    return size_kb * 1000 * 8 / (mbps * 1000)


def fetch_ms(size_kb: int, rtt: float, mbps: float, server: float = 50, dns: float = 40,
             setup_rtts: int = 2, origin_rtt: float = 0) -> float:
    """First byte to last byte of one response on a new connection.

    setup_rtts: 2 for TCP + TLS 1.3, 1 for QUIC, 0 for a connection that is already open.
    origin_rtt: for an edge that forwards to the origin on its own open, warm connection.
    """
    rounds = data_rounds(size_kb * 1000)
    wire = naive_ms(size_kb, mbps)  # the bandwidth term: only matters once the window is large
    return dns + setup_rtts * rtt + rtt + origin_rtt + server + (rounds - 1) * rtt + wire
```

```js title="latency-budget.mjs"
// runnable version: examples/how-the-web-works/js/latency-budget.mjs
const MSS = 1460; // bytes of payload in one TCP packet
const INITCWND = 10; // packets in the first round trip of data (RFC 6928)

/** Round trips of data a fresh connection needs: the window doubles every round trip. */
function dataRounds(sizeBytes, initcwnd = INITCWND) {
  let packets = Math.ceil(sizeBytes / MSS);
  let rounds = 0;
  for (let window = initcwnd; packets > 0; window *= 2) {
    packets -= window;
    rounds++;
  }
  return rounds;
}

/** What most people estimate: bytes divided by bandwidth. */
const naiveMs = (sizeKB, mbps) => (sizeKB * 1000 * 8) / (mbps * 1000);

/**
 * First byte to last byte of one response on a new connection.
 * setupRtts: 2 for TCP + TLS 1.3, 1 for QUIC, 0 for a connection that is already open.
 * originRtt: for an edge that forwards to the origin on its own open, warm connection.
 */
function fetchMs(sizeKB, rtt, mbps, { server = 50, dns = 40, setupRtts = 2, originRtt = 0 } = {}) {
  const rounds = dataRounds(sizeKB * 1000);
  const wire = naiveMs(sizeKB, mbps); // the bandwidth term: only matters once the window is large
  return dns + setupRtts * rtt + rtt + originRtt + server + (rounds - 1) * rtt + wire;
}
```

### Step 3: a timeout on every step

The production-shaped version is a probe, the kind uptime monitors run: a timeout on each step and,
when one fails, the name of the step. Here is the connect step; DNS, TLS and the response follow the
same pattern in the full file.

```python title="probe.py"
# runnable version: examples/how-the-web-works/python/probe.py
TIMEOUTS = {"dns": 3.0, "connect": 3.0, "tls": 5.0, "response": 10.0}  # seconds, per step


def connect(infos: list[tuple]) -> socket.socket:
    # Try each address in turn (browsers race IPv6 and IPv4 instead: "Happy Eyeballs").
    last = StepFailed("connect", "no addresses", "ERR_NAME_NOT_RESOLVED")
    for family, _, _, _, sockaddr in infos:
        sock = socket.socket(family, socket.SOCK_STREAM)
        sock.settimeout(TIMEOUTS["connect"])
        try:
            sock.connect(sockaddr)
            return sock
        except TimeoutError:
            last = StepFailed("connect", f"no answer from {sockaddr[0]}", "ERR_CONNECTION_TIMED_OUT")
        except ConnectionRefusedError:
            last = StepFailed("connect", f"{sockaddr[0]} refused", "ERR_CONNECTION_REFUSED")
        sock.close()
    raise last
```

## How real systems do it

**CDNs attack the length of every round trip.** Anycast announces the same address from hundreds of
cities, so the user's packets reach the nearest edge, and the edge keeps warm connections to the
origin. That is why the `example.com` measurement above connected in 14 ms from India. Cloudflare
has also tuned the record-size detail this page describes, starting TLS records small.

**Browsers attack the count of round trips.** Chrome races QUIC against TCP, races IPv6 against
IPv4, keeps connections open for reuse, reads ahead with the preload scanner, and honours
`preconnect`, `preload` and `103 Early Hints`. When it does not yet know whether a server speaks
HTTP/2, it may open several connections at once rather than wait to find out.

**Search and video engineered the protocol itself.** Google built QUIC because TCP and TLS could not
be changed fast enough in operating systems and middleboxes; it now lives in user space in the
browser and the server, which is why HTTP/3 can evolve without kernel upgrades. Its 0-RTT return
visits and its per-stream ordering are the two features this page has shown the value and limits of.

## Gotchas and war stories

:::danger[A connect with no timeout waits for the operating system]
When nothing answers a SYN, TCP retransmits it with an exponentially growing wait, and gives up only
when the retry count runs out. On Linux, `tcp_syn_retries` defaults to 6 with a 1 s initial timeout:
1 + 2 + 4 + 8 + 16 + 32 s to the last retry, plus 64 s waiting for its answer, about 127 s
([tcp(7)](https://man7.org/linux/man-pages/man7/tcp.7.html)). Windows waits 3 s, 6 s, then 12 s:
21 s. Measured against `10.255.255.1` with no timeout of our own: 21.1 s on Windows 11, 135 s on
Linux under WSL, and 10.8 s with Node's built-in `fetch`, whose client has a 10 s connect limit of
its own. A service whose threads all sit in that wait has stopped serving, with nothing in the error
logs until the timeout fires. Set a connect timeout and a total timeout on every outgoing call.
:::

**A redirect is a whole extra load.** `http://` to `https://`, or `example.com` to
`www.example.com`, costs at least one round trip and often a new lookup and handshake for the new
host, before the real page starts. HSTS and the browser's preload list
([hstspreload.org](https://hstspreload.org/)) remove the `http://` one; the `www` one you remove by
linking to the right name. And browsers cache `301` responses, often with no expiry, so a mistaken
permanent redirect keeps costing after you fix it; use `302` while testing.

**A `304` is not free.** Revalidation saves the body, not the round trip. A page whose twenty
static files are served with `no-cache` makes twenty conditional requests on every visit, and on a
150 ms link that is never fast, however small the answers are.

**The fast path fails silently, by design.** Broken IPv6 shows up as 250 ms of Happy Eyeballs delay.
A firewall that drops UDP turns HTTP/3 into HTTP/2 after a race. An idle connection quietly returns
to slow start. A font preconnect without `crossorigin` is wasted. None of these produce an error; all
of them show up only as a slower waterfall, which is why the waterfall is the first thing to read.

:::caution["It works on my machine" is often a cache]
Your laptop has warm DNS entries, open connections, a filled HTTP cache, maybe a hosts-file entry
and an HSTS record from last month. A user arriving fresh has none of them. Test in a private window
on a throttled connection, or with `curl -w`, which shares none of the browser's caches.
:::

## Trade-offs and limits of the model

- **Fewer round trips often costs safety or freshness.** 0-RTT can be replayed. Long cache lifetimes
  make changes slow to reach users. Long DNS TTLs make moves slow.
- **Fewer connections are not always faster.** One HTTP/2 connection is kinder to the network and to
  the server than six, but on a lossy link six windows can beat one, as the sim showed.
- **An edge is another dependency.** A CDN removes round trips and adds a hop that can fail, a bill,
  and a party that terminates your TLS.
- **This page's arithmetic assumes distance dominates.** Inside one data centre the RTT is well under
  a millisecond and server work dominates instead; for a chat or streaming connection that stays open,
  set-up is paid once and per-message latency is about one way. Large downloads (video, software
  updates) are bandwidth-bound, and there the bandwidth figure does matter.

:::note[From the trenches]
When a page is slow, people reach for the layer they know: back-end engineers tune queries,
front-end engineers shrink bundles. The question that usually finds the problem is different: how
many round trips are on the critical path, and how long is each one? Count them before changing
anything.
:::

## Interview corner

"What happens when you type a URL and press Enter?" is asked at every level. Listing DNS, TCP, TLS
and HTTP is what everyone does; what separates answers is where the time and the failures are.

1. **"Walk me through it."** Give the order in one breath, then go where the interviewer wants. Strong
   signals: round trips per step and how many overlap, what a repeat visit skips and why, and the
   critical path of dependent requests after the HTML.
2. **"A page is fast in the US and slow in India. How do you investigate?"** Measure from India.
   Separate round trips from server time in the waterfall. Count set-up round trips per host and
   dependency links. Fixes in order of leverage: an edge near users, fewer hosts and redirects,
   preconnect and preload, HTTP/3, then server work.
3. **"Why is HTTP/2 sometimes slower than HTTP/1.1?"** One TCP connection means one congestion window
   and in-order delivery: a loss stalls every stream and cuts the only window. Six HTTP/1.1
   connections have six windows. HTTP/3 fixes the in-order part, not the shared window.
4. **"How can a CDN help a page it cannot cache?"** It ends TCP and TLS near the user, so handshakes
   and slow start run at the short RTT, and it reaches the origin over a warm connection.

## Check yourself

<details>
<summary>1. A user is 100 ms from your server. DNS is cached and the server needs 30 ms. How long until the last byte of a 40 KB HTML response on a new TCP + TLS 1.3 connection? With HTTP/3?</summary>

40 KB is 28 packets: 10 in the first round, 18 in the second, so two rounds of data. TCP 100 + TLS
100 + request 100 + server 30 + one more data round 100 = 430 ms. HTTP/3 removes one set-up round
trip: 330 ms. Bandwidth barely appears in either number.

</details>

<details>
<summary>2. You add `<link rel="preconnect" href="https://fonts.example-cdn.com">` and the waterfall still shows a new connection when the font loads. Why?</summary>

Fonts are fetched in anonymous CORS mode, which uses a different connection pool from credentialed
requests. The preconnect opened a credentialed connection the font cannot use. Add `crossorigin` to
the link.

</details>

<details>
<summary>3. Your API server keeps connections alive for 60 s, yet a client that calls it every two seconds sees each response take as many round trips as on a fresh connection, minus the handshakes. What is going on?</summary>

Slow start after idle. Two seconds of silence is longer than the retransmission timeout, so Linux
shrinks the congestion window back towards 10 packets before the next response. Turning off
`net.ipv4.tcp_slow_start_after_idle` on the server keeps the window between bursts.

</details>

<details>
<summary>4. A repeat visit with every static file cached still takes over a second at 150 ms. Which round trips are left, and what would remove them?</summary>

A new connection to the HTML host (two set-up round trips, or none with QUIC 0-RTT), the HTML
request itself, and the same again for the API host after the cached JavaScript runs. Rendering the
first view's data into the HTML removes the API link; an edge shortens every remaining round trip;
HTTP/3 with 0-RTT removes the set-up.

</details>

## Recap

- Page load time is round trips on the **critical path** × RTT, plus server time. Bandwidth matters
  only once a transfer is past slow start.
- Set-up before the first byte: 4 round trips with TLS 1.2, 3 with TLS 1.3, 2 with HTTP/3, 1 with
  0-RTT or a reused connection. Each new host pays it again, plus DNS.
- **Slow start** sends 10 packets (about 14 KB), then doubles per round trip: 100 KB needs three
  rounds, and one loss ends the doubling.
- Warm connections are the biggest saving, and idle timeouts, separate pools (anonymous vs
  credentialed, per top-level site) and HTTP/1.1's six cold connections take it away.
- HTTP/3 removes TCP's head-of-line blocking but keeps one shared congestion window.
- Every layer has a cache that skips different round trips; a `304` still costs one, and a CDN
  helps even uncacheable pages by ending connections near the user.
