## A quiz app that froze on the train

Imagine you have recently joined a small team in Pune that builds a live quiz app for cricket fans.
During a match, friends join a room, answer questions about the next over together, and talk to
each other over voice chat. The first version sends everything over one WebSocket: voice in small
chunks every 20 milliseconds, and score updates as JSON. In the office, on good Wi-Fi, it is
perfect.

Then comes the first big match. On mobile data, voice freezes for half a second, then plays back
too fast to catch up, and the delay between friends slowly grows to several seconds. Someone senior
says, "Voice should never go over TCP. Use UDP, it's faster." So a teammate moves everything, voice
*and* score updates, to UDP.

Voice gets better at once. But new bugs arrive. Some players' scores never update. Sometimes the
"question closed" message arrives before "question opened". The end-of-match leaderboard, about
200 KB of JSON, never arrives at all; the server logs say "Message too long". And in the old
WebSocket server, someone finally finds the cause of a rare crash: when the server is busy, the
JSON parser fails with "Extra data", because two messages arrived glued together in one read.

Nothing here is a network failure. Every one of these bugs is TCP or UDP doing exactly what it
promises, and the team not knowing what that was. The pages on
[what happens when you type a URL](/foundations/how-the-web-works/) and [DNS](/networking/dns/)
used TCP and UDP as steps in a bigger journey. This page answers one question: **what do TCP and
UDP actually promise, what does each promise cost, and how do you choose, or build on top of, the
right one?**

## Why this problem exists

The internet moves data in **packets**: chunks of at most about 1,500 bytes on most links, each
carrying a source address and a destination address. The layer that moves them is **IP**, the
Internet Protocol, and it makes exactly one promise: it will try. A packet can be dropped when a
router's queue is full, corrupted by a noisy radio link, duplicated, or overtaken by a later packet
that took a faster path. Nobody is told. This is called **best-effort delivery**.

Best effort is a deliberate design. Routers stay fast because they remember nothing about the
conversations passing through them. Everything that needs memory is pushed to the two computers at
the ends. That leaves two jobs for the layer above IP, the **transport layer**:

1. **Find the right program.** An address gets a packet to a machine, but a machine runs many
   programs. A 16-bit **port** number says which one.
2. **Repair what IP breaks, if you want it repaired.** Put things back in order, resend what was
   lost, drop duplicates, and send no faster than the receiver and the network can take.

**UDP**, the User Datagram Protocol ([RFC 768](https://www.rfc-editor.org/rfc/rfc768), 1980), does
only the first job, in a specification three pages long. **TCP**, the Transmission Control Protocol
(today [RFC 9293](https://www.rfc-editor.org/rfc/rfc9293), 2022), does both, in about a hundred
pages. HTTP/1.1 and HTTP/2, databases, SSH and email run on TCP; DNS, voice and video calls, online
games, VPN tunnels and HTTP/3 run on UDP.

Picking the wrong one hurts users first, on crowded Wi-Fi and mobile data. These bugs hide in
testing, because office networks rarely lose packets; they appear in production, under load.

A few terms we will use throughout:

- A **segment** is one TCP packet's worth of data; a **datagram** is one UDP message.
- A **socket** is the handle your program uses to send and receive, bound to an address and port.
- The **round-trip time** (RTT) is how long a packet takes to reach the other side and an answer to
  come back: perhaps 10 ms from India to Mumbai, about 150 ms to Frankfurt.
- The **MTU** (maximum transmission unit) is the largest packet a link can carry, 1,500 bytes on
  Ethernet and most of the internet.

## The obvious picture, and why it breaks

The picture most of us start with fits in one line: **TCP is reliable but slow; UDP is fast but
unreliable.** It is not exactly wrong. It is dangerously incomplete, and three beliefs that grow
from it are behind every bug in our story.

**Belief one: a send on one side is a receive on the other.** Here is the read loop of a server
that receives JSON messages over TCP and parses each read as one message. The client sends five
small score updates and one large leaderboard; the server happens to be busy for 50 ms before it
starts reading:

Six messages went in, four reads came out, and not one parsed. The first read holds all five small
messages *and* the start of the leaderboard; the other three cut the leaderboard wherever they
happened to. TCP delivered every byte, in order, exactly as promised. What it never promised was to
keep your messages apart.

**Belief two: UDP is TCP minus the overhead.** Our second demo sends 5,000 numbered datagrams of
1,000 bytes from one process to another *on the same machine*, with no network involved at all.
The receiver does 0.2 ms of work per datagram, so it can handle 5,000 a second:

```text title="udp_loss.py output (Windows 11)"
full speed:
sender:   5000 datagrams sent in 127 ms, 0 send errors
receiver: 645 received, 4355 lost (87%), 561 gaps, 0 out of order

paced to 3,000 per second:
sender:   5000 datagrams sent in 1667 ms, 0 send errors
receiver: 5000 received, 0 lost (0%), 0 gaps, 0 out of order
```

At full speed, 87% of the datagrams vanished, and neither side got a single error. The receiver's
socket buffer filled up and the operating system dropped the rest; on Linux we saw 93–96% lost.
Only when the sender slowed itself down did everything arrive. TCP would have slowed the sender for
us; UDP never slows anyone down. That is not overhead removed. It is a job handed to you.

**Belief three: "reliable" means "delivered".** When `send()` returns on a TCP socket, your bytes
have been copied into a buffer in your own kernel. Nothing more. If the other side's process crashes
after its kernel acknowledged the bytes but before the application read them, they are gone, and
your side was already told "success". TCP promises that **every byte arrives, in order, or the
connection reports an error**, between two kernels. Whether the other *application* acted on your
request only an application-level reply can tell you, which is why payment APIs add their own
acknowledgements and idempotency keys on top of TCP.

Before we go inside, here are the neighbours TCP and UDP are most often confused with.

| These are often confused | The difference |
|---|---|
| **TCP** vs **TLS** | TCP makes bytes arrive reliably; anyone on the path can still read and change them. [TLS](/networking/tls/), layered on top, encrypts and authenticates them. |
| **UDP** vs **QUIC** | UDP is the thin envelope. QUIC is a full transport, with reliability, streams, congestion control and encryption, carried inside UDP datagrams. |
| **Connectionless** vs **stateless** | UDP has no handshake, but firewalls and NAT routers still keep state for every UDP flow, with a timer. |
| **Port** vs **connection** | A port names a program on a machine. A TCP connection is named by both addresses and both ports together, so one server port can hold thousands of connections. |

## The core idea

Think of the post office. TCP is a courier delivering a long book page by page. Before starting,
the courier phones you to agree that you are ready. Every page gets a number. You sign for what
arrives, and anything unsigned for is sent again. Pages are handed to you strictly in order: if
page 7 is missing, page 8 waits on the counter until page 7 turns up. And if the roads are jammed
or your desk is full, the courier slows down.

UDP is a stack of postcards. No phone call first, no numbers unless you write them, no receipts.
Each postcard is read on its own the moment it arrives. Most arrive. Some arrive out of order. Some
never arrive, and the post office will not tell you.

The analogy breaks in three places, and each one matters.

- **TCP does not keep pages.** It delivers a continuous stream of characters with no page breaks.
  Where one of your messages ends is invisible to it, which was belief one.
- **Postcards have no manners.** A person posting postcards can post ten thousand a second and jam
  the sorting office for everyone. Slowing down is the sender's job with UDP, which was belief two.
- **The post office does remember postcards, for a while.** Home routers and firewalls note every
  UDP conversation and forget it after a short silence.

Put precisely: **UDP adds ports and a checksum to IP and nothing else. Each datagram is delivered
whole, at most once, or not at all, with no order and no pacing. TCP opens a connection with a
handshake and turns IP's packets into a reliable, ordered stream of bytes, using sequence numbers,
acknowledgements and retransmissions, while flow control protects the receiver and congestion
control protects the network. TCP's guarantees are paid for in round trips before data moves and in
waiting whenever something is lost; UDP's freedom is paid for by doing yourself whatever you need of
the rest.**

Look at what travels between the applications in each half.

In the top half, the numbers inside the pipe are in order and the ACKs coming back are how the
sender knows what to resend. In the bottom half nothing comes back at all: datagram 5 is gone for
good, and datagram 4 arriving before 3 is the receiving application's problem.

## How it works, piece by piece

We will build TCP up piece by piece and keep UDP alongside for contrast. Our demos ran on Windows
11 and on Linux (Ubuntu in WSL 2) in October 2026, from a network in India.

### What both share: IP, ports and checksums

Both protocols sit inside IP packets and start with the same two fields, a source port and a
destination port. That is where the similarity ends: UDP's whole header is 8 bytes, TCP's is at
least 20.

<Figure caption="UDP's header is two ports, a length and a checksum: 8 bytes. TCP starts with the same ports, then adds the sequence and acknowledgment numbers, flags and a window, where all of its reliability and pacing lives.">
  <Headers />
</Figure>

The tinted fields are TCP's machinery, and the rest of this page is about what they do. About the
shared parts:

- **Ports are 16 bits**, 0 to 65,535. Servers listen on well-known ports (443 for HTTPS, 53 for
  DNS). Clients get a temporary **ephemeral port**: 32,768 to 60,999 on Linux by default as of
  October 2026 ([kernel docs](https://docs.kernel.org/networking/ip-sysctl.html)), which is 28,232
  ports. That number comes back in the war stories.
- **The checksum is weak.** A 16-bit sum catches most random corruption, and a packet that fails it
  is dropped silently. It does not protect against anyone deliberately changing your data; that is
  what TLS is for.

### UDP: a thin layer over IP

What UDP gives you is short enough to list in full: **ports**, a **checksum**, and **message
boundaries**. One send is one receive; a datagram arrives whole or not at all, never merged with
another and never split. Everything else is missing: no handshake, no acknowledgement, no
retransmission, no ordering, no flow control and no congestion control. A `sendto()` call returns as
soon as the kernel has the datagram, and you learn nothing about what happens next.

Size matters more than people expect. When a datagram is bigger than the path's MTU, IP cuts it into
**fragments**; if any fragment is lost the whole datagram is lost, and many firewalls drop fragments
on sight. On Ethernet the largest unfragmented UDP payload is 1,500 − 20 (IPv4 header) − 8 (UDP
header) = **1,472 bytes**, and real protocols stay below about 1,200 bytes: QUIC assumes paths carry
at least that, and the [DNS](/networking/dns/) page showed why DNS answers stop at 1,232.

That explains our story's leaderboard. The hard limit for one datagram over IPv4 is 65,507 bytes.
We tried: 65,507 worked, and 65,508 failed at once with "Message too long" on Linux (`EMSGSIZE`)
and error 10040 on Windows. A 219,813-byte document has to be split into numbered pieces by your own
code, and then you need to notice and resend lost pieces, which is the start of rebuilding TCP.

Why use something that promises so little? Because sometimes that small promise is exactly right:
for small, independent questions such as DNS, where a handshake would double the cost; for real-time
data, where a voice frame or game position is worth nothing late; for broadcast on a local network;
and as the base for new transports such as QUIC and WireGuard.

Three practical consequences come straight out of this sequence:

- **New connections cost a round trip, before any encryption.** At 150 ms to Frankfurt, that is
  150 ms of nothing for every new connection, and two round trips with TLS 1.3 on top. This is why
  every serious client reuses connections.
- **The side that closes first carries TIME_WAIT.** A client that opens and closes thousands of
  short connections to one server piles up sockets in TIME_WAIT, each holding an ephemeral port for
  60 seconds. At 28,232 ports per destination, that is about 470 new connections a second before
  the client runs out.
- **An abrupt end is a reset.** If one side sends **RST** instead of FIN, because the process died
  or a port is closed, the other side's next read or write fails with "connection reset by peer".

### Reliability: numbers, acknowledgements and retransmission

TCP numbers every **byte**, not every packet. Each segment carries the number of its first byte,
and each acknowledgement carries the number of the next byte the receiver expects: "ACK 5001" means
"I have everything up to byte 5,000; send 5,001 next". That single number tells the sender exactly
what is safe and what may need sending again.

There are two ways a sender discovers a loss. The fast one needs no timer at all: watch the
acknowledgements.

The slow way is the **retransmission timeout** (RTO). If no acknowledgement arrives in time, the
sender resends. Too short and you resend data that was only late; too long and you sit idle.
[RFC 6298](https://www.rfc-editor.org/rfc/rfc6298) keeps a smoothed average of measured round trips
(SRTT) and of how much they vary (RTTVAR), and sets

> RTO = SRTT + 4 × RTTVAR

with three rules around it: before any measurement, start at **1 second**; never go below a minimum,
which Linux sets at **200 ms**; and **double the timeout after each expiry**, so a dead path is not
flooded with retries. Retransmitted segments are never used to measure the round trip, because you
cannot tell which copy the ACK was for (Karn's rule).

**A worked example.** A connection with a steady 100 ms round trip has an RTTVAR close to zero, so
on Linux its RTO is about 100 + 200 = **300 ms**. A segment at the end of a burst is lost, with
nothing behind it to trigger duplicate ACKs. The sender waits 300 ms and resends. If that copy is
lost too, it waits 600 ms, then 1.2 s. One unlucky segment has now cost over two seconds. A lost SYN
is worse: there is no measurement yet, so the client waits the initial **1 second**.

That explains why the slowest requests on a latency graph often cluster at almost exactly 1 or 3
seconds above normal: lost SYNs, retried at 1 s and then 1 + 2 s. Linux keeps retrying a connect for
about 131 seconds, and data on an open connection for over 15 minutes ([kernel docs](https://docs.kernel.org/networking/ip-sysctl.html),
`tcp_syn_retries` and `tcp_retries2`). TCP's patience is measured in minutes, which is why your
application needs its own timeouts.

### A byte stream, not messages

Our first naive demo showed the consequence; here is the reason. TCP's specification says there is
no link between how the application writes and how the segments are cut
([RFC 9293 §3.7](https://www.rfc-editor.org/rfc/rfc9293)). The sender's kernel may combine small
writes into one segment, and must split a large write into segments of about 1,460 bytes. The
receiver's kernel puts all arriving bytes into one buffer, and a read returns whatever is there.

<Figure caption="The application writes three messages. TCP delivers the same bytes in whatever chunks happen to be ready, so a read can hold one and a half messages. UDP keeps each datagram whole. With a length field before each message, a TCP reader can find the boundaries again.">
  <Framing />
</Figure>

So every protocol on top of TCP must mark where its messages end, in one of three ways:

- **A length prefix.** Write the length first, then the bytes. DNS over TCP uses a 2-byte length;
  HTTP/2 starts every frame with a 24-bit length ([RFC 9113](https://www.rfc-editor.org/rfc/rfc9113)).
  This is the most robust choice and the one we build below.
- **A delimiter.** End each message with a byte that cannot appear inside it, as newline-delimited
  JSON does.
- **A protocol that does it for you.** WebSocket, HTTP and gRPC libraries frame messages so your
  code never sees the raw stream. Our quiz team's WebSocket server was fine; the bug was in a raw TCP
  side channel someone had added later.

### Flow control: not drowning the receiver

A fast sender can outrun a slow receiver; our UDP demo lost 87% of its datagrams exactly that
way. TCP prevents this with the **receive window**: every ACK carries a number saying how many more
bytes the receiver has room for, and the sender may have at most that many bytes sent but not yet
acknowledged. If the receiving application stops reading, the window shrinks to zero and the sender
stops, without losing a byte.

<Figure caption="The window is the number of bytes that may be sent but not yet acknowledged. Every ACK moves its left edge forward, which lets the sender send more at the right edge: the window slides.">
  <SlidingWindow />
</Figure>

This is TCP's built-in **backpressure**. It also sets a limit: throughput can never be more than
one window per round trip.

**A worked example.** To fill a 100 Mbit/s link to a server 100 ms away, you need 100,000,000 ÷ 8 ×
0.1 = **1.25 MB** in flight at all times. This amount, bandwidth × round trip, is the
**bandwidth-delay product**. The original 16-bit window field allows only 65,535 bytes, or
65,535 × 8 ÷ 0.1 ≈ **5.2 Mbit/s**, however fast the link. The **window scale** option
([RFC 7323](https://www.rfc-editor.org/rfc/rfc7323)) multiplies the field up to about 1 GB, and
modern kernels grow buffers automatically. When a transfer between two distant data centres is
mysteriously slow on a fast link, a small window or buffer is the first suspect.

### Congestion control: not drowning the network

The receive window protects the receiver. Nothing in it protects the routers in between, and that
nearly killed the early internet: in October 1986, throughput between two Berkeley sites 400 yards
apart fell about 800 times, because the network was full of retransmissions of packets dropped
because the network was full. Van Jacobson and Michael Karels' fix
([Congestion Avoidance and Control](https://ee.lbl.gov/papers/congavoid.pdf), 1988) is still the
shape of every TCP today.

The sender keeps a second limit, the **congestion window** (cwnd), its own estimate of how much the
network can take. It may have in flight only the smaller of the two windows.

- **Slow start.** A new connection starts at 10 segments, about 14.6 KB
  ([RFC 6928](https://www.rfc-editor.org/rfc/rfc6928)), and doubles the window every round trip
  while everything is acknowledged. "Slow" is a historical joke: the growth is exponential.
- **Loss means congestion.** When a loss is detected, the sender assumes a queue overflowed and cuts
  its window.
- **Then it probes again**, growing the window until the next loss, giving the famous sawtooth.

<Figure caption="Slow start doubles the window every round trip until the first loss. CUBIC cuts the window to 70%, climbs back quickly, slows down near the old peak where the last loss happened, then speeds up again to probe for more. Numbers are illustrative.">
  <CongestionWindow />
</Figure>

The algorithm in the drawing is **CUBIC** ([RFC 9438](https://www.rfc-editor.org/rfc/rfc9438)), the
default in the Linux, Windows and Apple TCP stacks. Google's **BBR** takes a different approach:
instead of reacting to loss, it measures the bottleneck's bandwidth and the minimum round trip and
paces packets to match ([ACM Queue, 2016](https://queue.acm.org/detail.cfm?id=3022184)). Its third
version is still an IETF draft as of October 2026
([draft-ietf-ccwg-bbr](https://datatracker.ietf.org/doc/draft-ietf-ccwg-bbr/)).

So a **new connection is slow at first**, as the foundations page showed; a warm one is not, one
more reason to reuse connections.

UDP has none of this. That is fine for a DNS question, and a disaster for a program that sends
megabytes as fast as the socket will take them. [RFC 8085](https://www.rfc-editor.org/rfc/rfc8085),
the IETF's guidelines for UDP applications, is blunt: anything that sends more than a little over UDP
must control its rate in a way comparable to TCP.

### Head-of-line blocking: the price of order

Here is where the two protocols really part ways. TCP's promise of order means that when one
segment is lost, **every byte behind it waits** until the retransmission arrives, even though those
bytes are already in the receiver's memory. This is **head-of-line blocking**, named after a queue
where the person at the front holds up everyone behind.

For a file download this hardly matters. For our quiz app's voice chat it is the whole problem. The
simulation sends 50 small messages a second, one every 20 ms, like voice frames, over a link with a
100 ms round trip and 4% loss. Each bar is one message's delay from sending to reaching the
application; the dashed line is 150 ms, roughly the most delay a conversation can take before it
feels awkward ([ITU-T G.114](https://www.itu.int/rec/T-REC-G.114)).

<TransportSim mode="tcp" />

Every loss in TCP looks the same: one tall amber bar for the lost message, then a staircase of
shorter amber bars descending from it, all messages that had already arrived and were waiting
behind the gap. Then they all reach the app at the same moment. That is exactly the "freeze, then
fast-forward" the quiz app's users heard.

**A worked example with the simulation's numbers.** Message *n* is lost at time 0. The next three
messages are sent at 20, 40 and 60 ms, and each arrives 50 ms later. The duplicate ACK triggered by
the third one gets back to the sender at 60 + 100 = **160 ms**; the resend leaves then and arrives at
**210 ms**. Meanwhile messages *n*+1 to *n*+7 arrived between 70 and 190 ms, and all of them were
held until 210 ms too. So *n* reaches the application 210 ms after it was sent, *n*+1 after 190 ms,
*n*+2 after 170 ms and *n*+3 after exactly 150 ms: one loss pushed three messages past the deadline
and dragged four more towards it. At 4% loss, the simulation's model ends up with about **14%** of
messages late, more than three times the loss rate, because now and then a resend is lost too and
only the slower timeout recovers it.

Now the same traffic, the same losses, over UDP:

<TransportSim mode="udp" />

No bar is ever tall: every message that arrives reaches the application 50 ms after it was sent.
The price is that about 4% never arrive. For voice, that is the better trade: a codec hides a missing
20 ms frame, but nobody can hide a 200 ms freeze. Raise the round trip to 200 ms in the TCP simulation
and watch the staircases grow.

### QUIC: TCP's ideas, rebuilt on top of UDP

Why not fix TCP instead? Because TCP lives in kernels and in millions of firewalls and load
balancers that inspect its headers, and a new TCP feature is often broken by some box on the path.
TCP Fast Open, which lets data ride on the SYN ([RFC 7413](https://www.rfc-editor.org/rfc/rfc7413)),
is the cautionary tale: boxes that drop SYNs carrying data kept it from wide use in browsers.
Engineers call this **ossification**: the network has frozen around what it already knows.

**QUIC** ([RFC 9000](https://www.rfc-editor.org/rfc/rfc9000), 2021) avoids all of that by running
in the application's own process, on top of UDP, which every network already passes. Inside, it
rebuilds TCP's ideas and changes several:

- **Streams.** One QUIC connection carries many independent streams. A loss holds up only the
  stream it belongs to.
- **Encryption built in.** QUIC always uses TLS 1.3 and sets up transport and encryption in one
  round trip instead of two; a returning client can send data in its very first packet (**0-RTT**).
- **Connection IDs.** A connection is not named by addresses and ports, so it survives your phone
  moving from Wi-Fi to mobile data.
- **Nearly everything encrypted**, headers included, so middleboxes cannot learn to depend on it
  and ossify it.

<Figure caption="Round trips spent before the first byte of a request can reach the server, at 100 ms each. QUIC sets up transport and encryption together, and a returning client can send data in its first packet.">
  <SetupCost />
</Figure>

HTTP/3 is HTTP over QUIC, and in 2025 it carried about 21% of the requests Cloudflare saw
([Cloudflare Radar Year in Review](https://radar.cloudflare.com/year-in-review/2025)). It costs more
CPU per byte than kernel TCP, some corporate networks block UDP, so every HTTP/3 client falls back
to TCP, and for one ordered stream a loss still holds up everything behind it. The win comes from
splitting independent data across streams.

### If you build on UDP yourself

If you use UDP directly, for a game server or a metrics pipe, RFC 8085 is a good checklist of what
you take on:

- **Stay small.** Keep datagrams within the path MTU, about 1,200 bytes if you cannot know it.
- **Control your rate.** Pace your sends and back off when you see loss. Our demo needed only to
  slow down to stop losing everything.
- **Add the reliability you need, and only that.** Sequence numbers to detect loss and reordering,
  acknowledgements and timeouts if something must arrive. "Build it yourself" below does this.
- **Expect duplicates.** Design messages so applying one twice does no harm.
- **Keep NATs awake.** Home routers and mobile networks translate addresses (**NAT**, network address
  translation) and must remember each UDP flow to let replies back in. They forget after a silence.
- **Do not amplify attacks.** With no handshake, anyone can forge the source address of a request.
  If your reply is much bigger than the request, you become a weapon pointed at that address. QUIC's
  rule: before an address is verified, send at most three times the bytes you received from it.

The NAT point deserves a picture, because it surprises everyone who thought UDP had no state.

<Figure caption="A NAT keeps a row for each UDP flow and deletes it after a silence. With a small keep-alive every 25 seconds the server's reply gets back in; after 30 seconds of silence the row is gone and the reply is dropped without a word.">
  <NatTimeout />
</Figure>

How long NATs remember varies wildly. The standard asks for at least 2 minutes
([RFC 4787](https://www.rfc-editor.org/rfc/rfc4787)), but QUIC's authors found that sending
something every 30 seconds is needed in practice ([RFC 9000 §10.1.2](https://www.rfc-editor.org/rfc/rfc9000)),
and RFC 8085 asks for no more than one keep-alive every 15 seconds. Somewhere between 15 and 30
seconds is the usual compromise, which is why voice and game apps send a tiny packet even in silence.

## Choosing between them

Read the table as "what you get without writing code"; you can always build more on UDP, at a
cost.

| | TCP | UDP | QUIC (over UDP) |
|---|---|---|---|
| Setup before data | 1 round trip, 2 with TLS 1.3 | none | 1 round trip with encryption, 0 when resuming |
| Lost data | resent | gone | resent |
| Order | one ordered stream | none | ordered within each stream |
| Message boundaries | none: a byte stream | kept: one datagram per message | per stream, a byte stream |
| A loss delays | everything behind it | nothing | only its own stream |
| Flow and congestion control | yes, in the kernel | none: your job | yes, in the application |
| Encryption | add TLS | add DTLS or your own | always on |
| Through firewalls and NATs | almost always | usually; flows forgotten after silence | usually; falls back to TCP |
| Typical uses | HTTP/1.1 and HTTP/2, databases, SSH, email | DNS, voice and video media, games, VPN tunnels, metrics | HTTP/3, modern mobile apps |

The simulation below runs all three on identical traffic with identical losses. In the QUIC lane,
the messages are spread over four independent streams, like four images on one web page.

<TransportSim mode="compare" />

TCP turns each loss into a staircase of late messages. QUIC repairs the same loss, but only its
own stream waits, so usually a single bar goes amber. UDP is never late, and loses exactly what the
network dropped. At the default 4% loss, our model shows about 14% of TCP messages
late, 5% of QUIC messages late and 4% of UDP messages lost.

**How to choose.** In practice you rarely choose TCP or UDP directly; you choose a protocol that
sits on one of them. So the useful questions are these:

1. **Must every byte arrive, and in order?** Payments, API calls, database queries: use TCP,
   through HTTP, gRPC or your database driver. This is the default for almost everything.
2. **Is late data worthless?** Voice, video, game state, live sensor readings: use UDP, usually
   through a library that adds what you need (WebRTC for media, a game networking library).
3. **Is it one tiny question and one tiny answer?** DNS, time sync: UDP, with a retry and a TCP
   fallback for big answers.
4. **Do you need TCP's guarantees on lossy mobile networks, many parallel streams, or connections
   that survive a network change?** Use HTTP/3 or QUIC through a library or your CDN. Do not write
   QUIC yourself.

:::tip[Mixing is normal]
Most real products use both. Our quiz app's final design sent voice over UDP (through WebRTC),
and scores, questions and the leaderboard over a WebSocket on TCP, framed by the WebSocket
protocol. Each kind of data got the promise it needed.
:::

## Build it yourself

We will build framing on top of TCP and reliability on top of UDP, then look at two measurements.
Everything uses only the standard library. Every file is in
[examples/tcp-vs-udp](https://github.com/udaysingh236/senior-dev-notes/tree/main/examples/tcp-vs-udp),
and every output on this page came from running them in October 2026.

### Step 1: framing messages on a TCP stream

The fix for belief one is a length prefix: 4 bytes saying how long the message is, then the
message. The reader reads exactly 4 bytes, then exactly that many more:

<Tabs syncKey="lang">
  <TabItem label="Python">
```python title="framing.py"
# runnable version: examples/tcp-vs-udp/python/framing.py
HEADER = struct.Struct(">I")  # 4-byte unsigned length, network byte order
MAX_MESSAGE = 1 << 20  # refuse anything over 1 MB: a bad length must not make us allocate 4 GB


def send_message(sock: socket.socket, message: dict) -> None:
    body = json.dumps(message).encode()
    sock.sendall(HEADER.pack(len(body)) + body)  # one buffer: header and body leave together


def recv_exactly(sock: socket.socket, n: int) -> bytes:
    """Read exactly n bytes. recv() may return fewer than asked for, so loop."""
    buf = bytearray()
    while len(buf) < n:
        chunk = sock.recv(min(n - len(buf), 65536))
        if not chunk:  # the peer closed: clean only if we were between messages
            raise ConnectionClosed("peer closed mid-message" if buf else "peer closed")
        buf += chunk
    return bytes(buf)


def recv_message(sock: socket.socket) -> dict:
    (length,) = HEADER.unpack(recv_exactly(sock, HEADER.size))
    if length > MAX_MESSAGE:
        raise ValueError(f"message of {length} bytes is over the {MAX_MESSAGE}-byte limit")
    return json.loads(recv_exactly(sock, length))
```

```js title="framing.mjs"
// runnable version: examples/tcp-vs-udp/js/framing.mjs
const MAX_MESSAGE = 1 << 20; // refuse anything over 1 MB: a bad length must not make us buffer 4 GB

function encode(message) {
  const body = Buffer.from(JSON.stringify(message));
  const header = Buffer.alloc(4);
  header.writeUInt32BE(body.length);
  return Buffer.concat([header, body]); // one buffer: header and body leave together
}

/** Turns a stream of chunks into whole messages. Call push() with each chunk. */
class MessageReader {
  buffer = Buffer.alloc(0);

  constructor(onMessage) {
    this.onMessage = onMessage;
  }

  push(chunk) {
    this.buffer = Buffer.concat([this.buffer, chunk]);
    while (this.buffer.length >= 4) {
      const length = this.buffer.readUInt32BE(0);
      if (length > MAX_MESSAGE) throw new Error(`message of ${length} bytes is over the ${MAX_MESSAGE}-byte limit`);
      if (this.buffer.length < 4 + length) return; // not all here yet: wait for more chunks
      this.onMessage(JSON.parse(this.buffer.subarray(4, 4 + length)));
      this.buffer = this.buffer.subarray(4 + length);
    }
  }
}
```

### Step 2: reliability on top of UDP

Now the other direction: we add enough of TCP's machinery to UDP to deliver 100 messages in order
over a bad link. A small wrapper drops 10% of datagrams each way and delays the rest by 20 to 30 ms,
so they also arrive out of order. The receiver buffers early arrivals and hands them over in order;
the sender keeps a timer per message and doubles it on each resend. The full file also sets the
timeout with RFC 6298's formula and Karn's rule:

```python title="reliable_udp.py"
            self.waits.append(time.perf_counter() - self.buffer.pop(self.expected))
```

understand TCP and a bad thing to ship. In production, use QUIC through a library.

### Step 3: the 40 millisecond mystery

A client sends each request in two writes, a small header and then the body, and waits for the
reply. On Linux every request takes about 40 ms, even on the same machine. Two good ideas are
colliding. **Nagle's algorithm**, on by default, holds back small writes while
earlier data is still unacknowledged, to avoid flooding the network with tiny packets. **Delayed
ACKs** wait up to about 40 ms on Linux before acknowledging, hoping to piggyback the ACK on a reply.
So the client holds the body until the header is acknowledged, and the server holds the
acknowledgement because it cannot reply until the body arrives. Each waits until the delayed-ACK
timer fires. `nagle.py` and `nagle.mjs` time 50 such requests three ways:

```text title="nagle.py output (Linux; node nagle.mjs gave the same)"
nagle on, two writes     median  43.99 ms   worst  48.40 ms
TCP_NODELAY, two writes  median   0.35 ms   worst   1.37 ms
nagle on, one write      median   0.28 ms   worst   2.52 ms
```

A hundred times slower, from one extra write. The better fix is the last line: build the whole
message in memory and write it once, as our framing code does. Setting `TCP_NODELAY` turns Nagle
off; Node's `http.createServer` does so by default since version 18
([Node docs](https://nodejs.org/api/http.html)), but a plain `net.Socket` does not. Windows loopback
did not show the stall at all, so test on the operating system you deploy to.

### Step 4: what a handshake costs on the real internet

Finally, a measurement. `dns_udp_vs_tcp.py` asks Cloudflare's resolver 1.1.1.1 the same DNS question
over UDP, over a fresh TCP connection (framed with a 2-byte length, the same idea as Step 1), and
again on that open connection:

```text title="dns_udp_vs_tcp.py output (Windows 11, a network in India)"
median of 7 rounds, asking 1.1.1.1 for example.com A
  UDP                         12.1 ms   one round trip, no setup
  TCP, new connection         24.2 ms   = connect 12.2 ms + query 12.0 ms
  TCP, connection reused      11.4 ms   the handshake is already paid for
```

UDP needs one round trip; a new TCP connection needs two, exactly double; and a TCP connection that
is already open costs the same as UDP. TCP's expense is in opening connections, not in using them.

## How real systems do it

**Voice, video and games ride on UDP.** WebRTC, used by browsers for calls, sends media over UDP and
can fall back to relaying over TCP when UDP is blocked. Discord described in 2018 how its native
clients send voice over UDP to its own servers, with periodic pings to keep firewalls open, serving
over 2.6 million concurrent voice users at the time
([Discord engineering](https://discord.com/blog/how-discord-handles-two-and-half-million-concurrent-voice-users-using-webrtc)).
Fast multiplayer games send frequent snapshots of the world and never resend a lost one, because the
next snapshot replaces it ([Gaffer on Games](https://gafferongames.com/post/udp_vs_tcp/)).

**HTTP/3 brings TCP's guarantees to lossy networks.** Google's 2017 paper on QUIC reported 15–18%
fewer YouTube rebuffers, with bigger gains on slower, longer paths
([Google Research](https://research.google/pubs/the-quic-transport-protocol-design-and-internet-scale-deployment/)).
Uber moved its rider and driver apps to QUIC in 2019 and reported a 10–30% drop in tail latency on
mobile networks ([Uber engineering](https://www.uber.com/blog/employing-quic-protocol/)).

**VPN tunnels use UDP so they don't fight themselves.** WireGuard deliberately does not run over TCP
([WireGuard](https://www.wireguard.com/known-limitations/)). If you carry TCP inside a tunnel that is
itself TCP, a single loss makes both layers retransmit and back off, and their timers fight each
other. Over UDP, only the inner connections repair losses.

**Load balancers forget idle connections.** As of October 2026, AWS's Network Load Balancer drops
TCP flows idle for 350 seconds by default (configurable from 60 to 6,000) and UDP flows after 120
seconds ([AWS](https://aws.amazon.com/blogs/networking-and-content-delivery/introducing-nlb-tcp-configurable-idle-timeout/));
its Application Load Balancer closes idle connections after 60 seconds by default
([AWS docs](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/edit-load-balancer-attributes.html)).
Linux's TCP keep-alive, when enabled at all, waits 2 hours before its first probe. Keep that gap in
mind for the war stories.

## Gotchas and war stories

:::danger[A real outage: 1.35 Tbps from a UDP amplifier]
On 28 February 2018, GitHub was hit by what was then the largest attack ever reported publicly:
1.35 Tbps at its peak. Attackers sent small requests to tens of thousands of memcached servers left
open on UDP port 11211, with GitHub's address forged as the source. Each server sent its large reply
to GitHub, amplifying the traffic up to 51,000 times. GitHub was unreachable for about five minutes
and intermittently for nine, until it moved its traffic behind DDoS protection
([GitHub incident report](https://github.blog/2018-03-01-ddos-incident-report/)).
:::

The lesson for anyone building on UDP: **without a handshake, the source address is a claim, not a
fact.** Never send a large reply to an address that has not proved it can receive.

:::caution[The five-second DNS lookups in Kubernetes]
Around 2017 to 2019, many Kubernetes clusters saw DNS lookups that occasionally took exactly 5
seconds. The C library sends the A and AAAA queries in parallel from one UDP socket, and a race in
Linux's connection tracking sometimes dropped one of the pair. Nothing retries a lost UDP packet
except the application, so the client waited out the resolver's 5-second timeout. The kernel races
were fixed in Linux 4.19 and 5.0
([kubernetes/kubernetes#56903](https://github.com/kubernetes/kubernetes/issues/56903)).
:::

A latency that is always the same odd number, 1 s, 3 s or 5 s, is almost never your code. It is a
timer somewhere: TCP's initial retransmission timeout, its first backoff, or a resolver's timeout.

**Idle connections that are dead without anyone knowing.** Your service keeps a pool of database or
HTTP connections behind a load balancer. Overnight, a connection sits idle for 10 minutes. The load
balancer forgot it at 350 seconds; Linux's keep-alive would not have probed for 2 hours. In the
morning, the first request on that connection fails with "connection reset". Make the pool discard
connections idle for less than the shortest idle timeout on the path, or enable keep-alives with an
interval below it. The mirror image bites servers behind an ALB: if your server closes idle
connections *before* the load balancer does, the load balancer may send a request down a connection
your server has closed and return a 502. Make your server's idle timeout longer than the load
balancer's.

**CLOSE_WAIT is always your bug.** A growing number of sockets in CLOSE_WAIT means the other side
closed and your application never did: a missing `close()`, usually on an error path. The kernel
will wait for ever.

**Ephemeral port exhaustion.** A client that opens many short connections to one destination can run
out of its 28,232 ports, between connections in use and those resting in TIME_WAIT. The symptom is
bizarre: "cannot assign requested address" from code that never binds a port. Cloudflare wrote up
the socket options needed to go beyond one port range
([Cloudflare](https://blog.cloudflare.com/how-to-stop-running-out-of-ephemeral-ports-and-start-to-love-long-lived-connections/));
for most of us the fix is to reuse connections instead of opening one per request.

## Trade-offs and when not to use it

**What TCP costs.** A round trip to open every connection, more with TLS. Head-of-line blocking,
which turns every loss into a stall for everything behind it. A byte stream you must frame yourself.
Kernel timers, measured in seconds and minutes, that your application must cut short with its own
timeouts.

**When not to use TCP.** When late data is useless: live voice and video, game state, live sensor
feeds. When you need one-to-many delivery on a local network. When the whole exchange is one tiny
question and answer, and the handshake would double its cost.

**What UDP costs.** Everything TCP would have done, if you need it: loss detection, ordering,
pacing, NAT keep-alives, protection against spoofing, and a fallback for networks that block it.

**When not to use UDP.** When all your data must arrive, in order: payments, API calls, file
transfers. You would end up rebuilding TCP, and the first version of a home-made TCP is always worse
than the real one. If you need TCP's guarantees without its head-of-line blocking, use QUIC through a
well-tested library.

:::note[From the trenches]
Teams usually discover their transport choices during an incident, not a design review. Before you
ship anything real-time, test it on a bad network on purpose. On Linux,
`tc qdisc add dev eth0 root netem loss 3% delay 100ms` turns a good link into a mobile one; browser
developer tools can throttle too. Ten minutes of that finds the head-of-line freeze, the missing
timeout and the glued-together messages before your users do.
:::

## Interview corner

A weak answer recites "reliable versus fast". A strong one talks about what each promise costs and
what happens when packets are lost.

1. **"What's the difference between TCP and UDP?"** Connection and handshake versus none; reliable,
   ordered byte stream versus independent datagrams; flow and congestion control versus none. Then
   the trade-off: TCP costs a round trip to open and stalls everything behind a loss; UDP leaves
   loss, order and pacing to the application. Give one example of each, and QUIC as the middle
   ground.
2. **"How does TCP guarantee delivery?"** Byte sequence numbers, cumulative ACKs, retransmission on
   three duplicate ACKs and on timeout (RTO from smoothed RTT and variance, with exponential
   backoff). Bonus: the guarantee ends at the receiving kernel, not the application.
3. **"Why would you build a voice or game protocol on UDP?"** Head-of-line blocking: a lost packet
   delays everything behind it by at least a round trip, and late audio is useless. A strong answer
   adds what you then must build: sequence numbers, jitter buffers, rate control, NAT keep-alives.
4. **"What is QUIC and why is it on UDP?"** Reliable, encrypted, multi-stream transport in user
   space, on UDP because middleboxes and kernels ossified TCP. Benefits: no head-of-line blocking
   across streams, one-round-trip setup, connection migration.

In system design interviews, say which data needs which promise, as our quiz app's final design
did.

## Check yourself

<details>
<summary>1. A server reads messages over a raw TCP socket, one read per message. It passes every test and fails in production under load with JSON errors. Why, and what is the fix?</summary>

TCP is a byte stream with no message boundaries. Under load, several messages pile up in the
receive buffer and one read returns them together, or a large message is split across reads. The
fix is framing: a length prefix (read exactly the header, then exactly that many bytes), a
delimiter, or a protocol such as WebSocket that frames messages for you.

</details>

<details>
<summary>2. A voice app sends 50 packets a second over TCP. The round trip is 120 ms, and one packet is lost in the middle of the stream. Roughly how late is the lost packet, and how many packets miss a 150 ms deadline?</summary>

The three packets after it are sent at 20, 40 and 60 ms and arrive 60 ms later; the third duplicate
ACK gets back to the sender at 60 + 120 = 180 ms. The resend arrives at 180 + 60 = 240 ms, so the
lost packet's delay is 240 ms. Packets sent at 20, 40, 60 and 80 ms wait until then too, with delays
of 220, 200, 180 and 160 ms. So five packets miss the deadline from a single loss, where UDP would
have lost one and delivered the rest on time.

</details>

<details>
<summary>3. Two processes on the same laptop talk over UDP. No network is involved, yet the receiver gets only a fraction of the datagrams. How is that possible?</summary>

The receiving socket has a fixed buffer. If the sender is faster than the receiver reads, the buffer
fills and the kernel drops new datagrams without telling anyone, because UDP has no flow control.
Pacing the sender, a bigger buffer or a faster receiver fixes it.

</details>

<details>
<summary>4. Every morning, the first few API calls from your service fail with "connection reset", then everything works. The service keeps a pool of TCP connections to another service behind an AWS Network Load Balancer, and traffic is near zero overnight. What is happening?</summary>

The connections sat idle for longer than the load balancer's idle timeout (350 seconds by default
for TCP), so it forgot them, and nobody told either end. The first request on each stale connection
is reset. Make the pool discard connections idle for, say, under 5 minutes, or enable keep-alives
with an interval below the timeout, and retry idempotent requests once on a reset.

</details>

<details>
<summary>5. A user is 100 ms away. Counting only round trips, when can the first byte of an HTTPS request reach the server over HTTP/2 (TCP with TLS 1.3), over HTTP/3 on a first visit, and over HTTP/3 when resuming?</summary>

HTTP/2 needs one round trip for TCP and one for TLS 1.3, so the request leaves after 200 ms and
reaches the server half a round trip later, at 250 ms. HTTP/3 sets up transport and encryption
together in one round trip, so the request arrives at about 150 ms. With 0-RTT resumption, the
request travels in the first flight and arrives after 50 ms.

</details>

## Recap

- **IP is best effort**: packets can be lost, duplicated, reordered or corrupted, and nobody is told.
- **UDP** adds ports, a checksum and message boundaries, nothing else. Keep datagrams under about
  1,200 bytes.
- **TCP** opens a connection with a one-round-trip handshake and delivers a **reliable, ordered byte
  stream**, using sequence numbers, ACKs, fast retransmit and a timeout that starts at 1 s and
  doubles.
- **A byte stream has no message boundaries.** Frame your messages: a length prefix, a delimiter, or
  a protocol that does it for you.
- **Flow control** protects the receiver; **congestion control** protects the network. Throughput is
  at most one window per round trip.
- **Head-of-line blocking** is TCP's price for order. For real-time data, late equals lost, so UDP
  wins.
- **QUIC** rebuilds TCP's guarantees on UDP with independent streams, built-in TLS 1.3 and
  one-round-trip setup. It is what HTTP/3 runs on.
- **Building on UDP means taking on its duties**: rate control, the reliability you need, NAT
  keep-alives every 15 to 30 seconds, and never amplifying spoofed requests.
