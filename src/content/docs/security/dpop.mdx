## The question

When your app calls an API, it sends an access token with every request: a long string that tells
the API "this request is from user 42, who may read their orders". Suppose that string ends up in a
log file and someone copies it. They can paste it into their own requests, from their own laptop,
and the API will treat them as user 42 until the token expires. Can we make a copied token useless?

Yes. **DPoP** (Demonstrating Proof of Possession) is the standard way to do it. The app makes a
secret key that never leaves it, and the login server writes a fingerprint of that key into the
token. From then on, every request carries the token plus a short note signed with the secret key,
saying "GET /orders, made at 08:00:00". The API accepts the token only together with a fresh note
signed by the key whose fingerprint is inside the token. Someone who copied the token has no key,
so they cannot sign the note. The rest of Part 1 walks through that slowly; Part 2 opens up each
piece.

## The idea in plain words

Follow one browser app, a shop's order page at `app.example.com`, reading the orders of user 42
from an API at `api.example.com`. Three programs take part: the app in the user's browser; a
**login server** that signs the user in and hands out tokens; and the **API** that holds the orders.
(The building blocks below give them their proper names.)

**Getting a token (once per login).**

1. Before it asks for a token, the app makes a **key pair**: two keys that belong together. The
   **private key** stays inside the browser, which lets the app's code use it to sign but never
   read it out. The **public key** can be shown to anyone.
2. The app asks the login server for a token and attaches a short note signed with the private
   key. The note contains the public key.
3. The login server checks the signature on the note. Then it computes a **fingerprint** of the
   public key, a short string that names exactly this key:
   `0ZcOCORZNYy-DWpqq30jZyJGHTN0d2HglBV3uiguA4I` in our example. It writes the fingerprint into the
   access token, next to "user 42" and "valid for 5 minutes", and sends the token to the app.

**Calling the API (every request).**

4. At 08:00:00 the app wants the orders. It writes a fresh note: "GET
   `https://api.example.com/orders`, made at 08:00:00, note ID `9f1c…`, for this token". It signs
   the note with the private key.
5. It sends the request with two headers: the token in the usual `Authorization` header, and the
   signed note in a header called `DPoP`.
6. The API runs three checks:
   - the signature on the note is valid for the public key written in the note;
   - that public key's fingerprint is the one written inside the token;
   - the note is for this request: GET, this URL, made in the last 60 seconds, with a note ID the
     API has not seen before.

   All three pass, so the API answers `200 OK` with the orders.

**What someone with a copied token can do.**

7. At 08:02:00 a thief copies the token from a log file and sends `GET /orders` from their own
   laptop, with no note. The API rejects it: no note.
8. The thief makes a key pair of their own and signs a note with it. The signature is valid, but
   the second check fails: the fingerprint of the thief's key is not the one inside the token.
9. The log also held the app's note from step 4, so the thief sends the token and that exact note
   again. The third check fails twice over: note ID `9f1c…` has already been used, and the note
   was made at 08:00:00, two minutes (120 seconds) ago, which is more than 60 seconds.

<Figure caption="Once, at login, the token gets the fingerprint of the app's key. On every request the app sends the token and a fresh note signed by that key. A thief who copied the token has no key, so cannot sign a note, and the API rejects them.">
  <MentalModel />
</Figure>

That answers the question. A token on its own no longer gets anyone in: it only says which key is
allowed to use it. The key never travels. The login server and the API only ever see the public
key, and seeing a signature does not reveal the private key that made it. So the thief would have
to get the private key out of the app, and the app is built so that nobody can read it out.

Why sign a fresh note for every request, rather than one note per login? Because a note that worked
forever would leak the same way the token does. A note that names one method, one URL and one
moment, and can be used once, is worth little to anyone who copies it.

An everyday picture: a boarding pass printed with your passport number. Someone who photographs
your boarding pass still cannot board, because they do not have your passport. The picture stops
working in two places. At the airport you show your passport; here the app never shows its key, it
signs a note, and only the holder of the key can sign. And anyone who gets their own code running
inside the app can use the key without taking it away, which is the last thing Part 2 looks at.

## The building blocks

Five ideas carry the rest of the page. Each gets a plain sentence, the reason it exists, a small
example, and then its proper name.

### Access tokens, refresh tokens and OAuth

**What it is.** An **access token** is a string the app sends with each API request to show that it
may act for a user.

**Why it exists.** The API should not see the user's password on every request, and the permission
should run out on its own if it leaks. So the user signs in once, at the login server, and the app
gets a token that the API can check and that expires.

**Example.** User 42 signs in at 08:00:00. The app gets an access token that says "user 42 may read
orders" and is valid for 5 minutes, so it stops working at 08:05:00. To keep going after that, the
app also got a **refresh token**: a second token, valid for days, whose only use is to ask the login
server for a new access token without making the user sign in again.

**The technical version.** The standard is **OAuth 2.0**. It calls the login server the
**authorization server** (AS), the API the **resource server** (RS), and the app the **client**.
The client usually gets its first tokens with an **authorization code**: a one-time code that the AS
hands back through the browser after the user signs in, and that the client then exchanges at the
AS's token endpoint, `POST /token`, for the tokens. Some access tokens are random strings that the
API looks up at the AS; many are JWTs, the signed notes described in the last building block.

### Bearer tokens

**What it is.** A **bearer token** works for whoever presents it, the way cash or a cinema ticket
works for whoever holds it. "Bearer" means the person carrying it.

**Why it exists.** It keeps the API simple. The API checks only that the token is genuine and has
not expired; it never has to know anything about who sent it.

**Example.** A thief copies user 42's 5-minute bearer token at 08:02:00. The token expires at
08:05:00, so it works from the thief's laptop for the remaining 3 minutes. A refresh token copied
the same way is far worse: it works for days, and the thief can use it to get a new 5-minute access
token whenever the last one runs out.

**The technical version.** Bearer tokens are sent as `Authorization: Bearer <token>`
([RFC 6750](https://www.rfc-editor.org/rfc/rfc6750), the standard still in force). Almost every
access token today is a bearer token. A token that works only for the party it was issued to is
called **sender-constrained**, and DPoP ([RFC 9449](https://www.rfc-editor.org/rfc/rfc9449),
September 2023) is one way to sender-constrain a token. A DPoP token is sent as
`Authorization: DPoP <token>`. (An **RFC** is a numbered standards document published by the IETF,
the body that standardises how internet software works.)

### Key pairs and signatures

**What it is.** A **key pair** is two matching keys: a private key that makes signatures, and a
public key that checks them.

**Why it exists.** The app has to prove that it holds a secret without ever sending the secret. A
**signature** made with the private key can be checked by anyone holding the public key, which is
safe to give out, yet only the private key can produce it.

**Example.** The app signs the text `GET /orders 08:00:00` and gets a signature. The API checks it
with the public key: valid. Change one character, `GET /orders 08:00:01`, and the same signature
fails the check. Without the private key, nobody can produce a signature that passes for the new
text.

**The technical version.** A **bit** is a single 0 or 1, and a **byte** is 8 bits, a number from 0
to 255; keys and signatures are measured in bytes. DPoP proofs in practice use **ES256**: ECDSA (the
Elliptic Curve Digital Signature Algorithm, a signature method built on a kind of maths called
elliptic curves) on the standard curve named P-256, with SHA-256 (next building block) applied to
the message first. An ES256 public key is two numbers, `x` and `y`, of 32 bytes each, and a
signature is two numbers, `r` and `s`, of 32 bytes each: 64 bytes in all. This is different from
the codes in [Google Authenticator](/case-studies/google-authenticator/), where the phone and the
server hold the same secret: here the API holds nothing secret at all.

### Hashes and key fingerprints

**What it is.** A **hash function** turns any input into a short, fixed-size output that looks
random. The same input always gives the same output.

**Why it exists.** The token has to name the app's key without carrying the whole key, and every
server that computes the name must get exactly the same result. A hash of the key is such a name:
short, fixed in size, and the same everywhere. That is the fingerprint from step 3.

**Example.** The hash function SHA-256 turns the word `orders` into 32 bytes, and the word `Orders`
into 32 completely different bytes. Nobody can work backwards from the 32 bytes to the input, and
nobody can find a second input with the same output. To put the 32 bytes into a token or a header,
they are written as text with **base64url**: an alphabet of 64 characters (`A`–`Z`, `a`–`z`,
`0`–`9`, `-` and `_`) that is safe inside URLs and headers. Each character carries 6 bits, because
2 × 2 × 2 × 2 × 2 × 2 = 64. That is why the fingerprint in step 3 is 43 characters long:

1. 32 bytes × 8 bits per byte = 256 bits.
2. 256 bits ÷ 6 bits per character = 42.7 characters.
3. Rounded up to whole characters: 43.

**The technical version.** In JSON-based security standards a key is written as a **JWK** (JSON Web
Key), for example `{"kty":"EC","crv":"P-256","x":"l8tF…","y":"9VE4…"}`: the key type, the curve, and
the two numbers in base64url. The fingerprint is a **JWK thumbprint**
([RFC 7638](https://www.rfc-editor.org/rfc/rfc7638), still in force), made repeatable: keep only the
key's required members, sort them by name, remove all spaces, hash with SHA-256, write in base64url.
The public key in RFC 9449's own examples becomes the string
`{"crv":"P-256","kty":"EC","x":"l8tFrhx-34tV3hRICRDY9zCkDlpBhF42UQUfWVAWBFs","y":"9VE4jf_Ok_o64zbTTlcuNJajHmt6v9TDVrU0CdvGRDA"}`,
and its thumbprint is `0ZcOCORZNYy-DWpqq30jZyJGHTN0d2HglBV3uiguA4I`, the fingerprint of our running
example. Our example code recomputes it from the key.

### A JWT: the signed note

**What it is.** A **JWT** (JSON Web Token) is a standard format for a small signed note: a few
fields of JSON plus a signature over them.

**Why it exists.** The app and the API must follow exactly the same rules for writing the note and
checking its signature, or a genuine note gets rejected over a space in the wrong place. A shared
format fixes those rules once.

**Example.** The note from step 4, as JSON:
`{"jti":"9f1c…","htm":"GET","htu":"https://api.example.com/orders","iat":1800000000}`. The time
`iat` is written as **Unix time**: the number of seconds since midnight UTC on 1 January 1970, which
is the same number everywhere in the world at the same instant. 1,800,000,000 seconds after that
midnight is 08:00:00 UTC on 15 January 2027, the "made at 08:00:00" of our story.

**The technical version.** A JWT is three base64url pieces joined by dots: a header (JSON saying
what this is and how it was signed), a payload of **claims** (the JSON fields above), and a signature
over the first two. A DPoP note is a JWT that the app writes and signs itself; an access token is
often a JWT too, signed by the AS. RFC 9449 calls the note a **DPoP proof**, and from here on so do
we.

:::tip[If you stop here]
- A normal access token is a bearer token: anyone who copies it can use it until it expires.
- With DPoP, the app makes a key pair and keeps the private key. The login server writes the
  public key's fingerprint into the token.
- Every request carries the token and a fresh signed note (a DPoP proof) for this method, this URL
  and this moment. The API checks the signature, checks that the signing key matches the
  fingerprint in the token, and checks that the note is fresh and unused.
- A thief with only the token cannot sign a note, so the token is useless to them.
:::

## Going deeper

Part 1 made DPoP sound airtight. Look closer. The proof signs the HTTP method and the URL, not the
request body. The key lives in the same browser page as the app's JavaScript, which is exactly
where an attacker's injected script would run. The API never learns whose key it is: anyone can make
a key pair. And "a note ID the API has not seen before" means the API must remember every note ID,
on every one of its servers. So what can a thief still do with DPoP, and what does the server have
to remember to stop the rest?

### Where bearer tokens leak

A bearer token is a password that travels on every request, and it leaks through more doors than a
password does:

- **Logs.** An `Authorization` header captured by a debug log, by a monitoring agent that
  records requests, by a browser's saved recording of network traffic (a HAR file) attached to a
  support ticket, or by a proxy (a server in the middle that forwards requests) that records
  headers.
- **The browser.** A token kept in `localStorage`, the browser's key-value storage for a website,
  or in a JavaScript variable, can be read and sent elsewhere by any script running on the page.
- **A malicious or broken API.** The app hands its token to every API it calls. One bad API can
  replay that token against the others, unless every token names the one API it is for.
- **Servers that hold tokens for users.** In April 2022, OAuth tokens that GitHub had issued to
  Heroku and Travis CI, so they could reach their users' repositories, were stolen from those
  companies and used to list and copy private repositories of dozens of organisations, npm among
  them ([GitHub, 2022](https://github.blog/news-insights/company-news/security-alert-stolen-oauth-user-tokens/)).
  From 8 to 18 August 2025, access and refresh tokens taken from Salesloft's Drift integration were
  used to export data from customers' Salesforce accounts; Google's threat intelligence team counted
  over 700 potentially affected organisations
  ([Google, 2025](https://cloud.google.com/blog/topics/threat-intelligence/data-theft-salesforce-instances-via-salesloft-drift)).

In every case the stolen token worked from the attacker's own machine, with nothing else. The damage
lasts as long as the token does, and for a refresh token that is days or months. **Revocation**, the
AS cancelling a token before it expires, helps only after someone notices. And an API that checks a
JWT access token by its signature alone never asks the AS whether it was revoked, so the token keeps
working until it expires.

## The obvious fix, and why it breaks

**"Make tokens short-lived."** A 5-minute token limits the damage of one stolen access token. It
does nothing for the refresh token that renews it: a thief with a refresh token gets fresh access
tokens for as long as the login session lasts. The Drift tokens included refresh tokens; nobody had
to race a 5-minute clock.

**"Bind the token to the client's IP address."** Phones change IP address when they move between
Wi-Fi and mobile data. Mobile carriers put thousands of users behind one shared address. Modern
devices change their IPv6 address on purpose, for privacy. You lock out real users, and an attacker
on the same network, or running code on the same device, passes anyway.

**"Restrict each token to one API."** An `aud` (audience) claim in the token names the API it is
for, so a token issued for the payments API does not work at the orders API. It does not stop a
thief from using it at the payments API, which is the API they wanted.

**"Use mutual TLS."** In normal TLS only the server shows a **certificate**, a signed document
that ties a public key to a name. In **mutual TLS (mTLS)** the
client shows one too, proving it holds the certificate's private key. OAuth mTLS
([RFC 8705](https://www.rfc-editor.org/rfc/rfc8705), 2020) binds the token to that client
certificate: the AS writes a hash of the certificate into the token, and the API compares it with
the certificate on the connection. It is strong, and it is standard for bank-to-bank APIs. It fits
browsers badly: a web page cannot create and present a client certificate of its own, and the
browser's certificate prompt is not something you show users. It also breaks when TLS ends at a load
balancer, which must then forward the certificate to the app. An older idea, **token binding**,
tied tokens to the TLS connection itself, and browsers never supported it.

Two neighbours get confused with DPoP. **HTTP Message Signatures**
([RFC 9421](https://www.rfc-editor.org/rfc/rfc9421), 2024) sign whichever parts of a request you
choose, including a hash of the body. The price is that both sides must rewrite the signed headers
into one exact form before signing and checking. They prove the request was not altered, which DPoP
does not try to do. **Device Bound Session Credentials** (DBSC), which Chrome made generally
available on Windows in April 2026
([The Hacker News, 2026](https://thehackernews.com/2026/04/google-rolls-out-dbsc-in-chrome-146-to.html)),
apply the same idea to a website's login cookie, with the key kept in the computer's security chip
(the TPM). They protect a site's own login cookie, not OAuth tokens sent to APIs.

## How it works, piece by piece

### The proof: one signed JWT per request

Part 1's note had a method, a URL, a time and an ID. The real proof has a few more fields, and each
one exists to stop one specific misuse. The figure lists every field of a proof, header first, then
claims, and next to each the misuse it rules out.

<Figure caption="A DPoP proof is a JWT signed by the client. The header carries the public key; each claim narrows where, when and with what the proof can be used.">
  <ProofAnatomy />
</Figure>

The header says what the JWT is: `typ` must be `dpop+jwt`, so that no other JWT the client signs
can be passed off as a proof. It says how it was signed: `alg`, a public-key algorithm such as
ES256, never `none` (which means "no signature"). And it carries the public key itself, as a JWK, in
`jwk`.

The claims:

- `jti` ("JWT ID"), a unique ID: at least 96 random bits, or a UUID (a standard
  format for random IDs).
  That is so many possible values that two proofs never pick the same one by chance. It lets the
  server notice a proof sent twice.
- `htm` and `htu`: the HTTP method and the target URL, without the query string (the part after
  `?`) or the fragment (the part after `#`). A proof for `GET /orders` cannot be used for
  `DELETE /orders/7`.
- `iat` ("issued at"): when the proof was made, in Unix time. The server accepts a proof only for a
  short time after that.
- `ath` ("access token hash"): the SHA-256 of the access token, in base64url, on every call to the
  API. A proof is good for one token only.
- `nonce`: a value the server handed out, when the server asks for one. Its own section is below.

What is not signed matters as much: the query string, the other headers and the body. RFC 9449
chose this on purpose. To sign a whole HTTP message, both sides must rebuild it byte for byte, after
proxies along the way have added, removed and reordered headers, and that is where signature schemes
usually fail. Keeping the body unaltered is left to TLS. Our proofs were 530 bytes each, about half a
kilobyte (a kilobyte is 1,000 bytes).

### Binding: the token remembers the key

The token request is ordinary OAuth with one extra header, the `DPoP` proof:

```http
POST /token HTTP/1.1
Host: auth.example.com
Content-Type: application/x-www-form-urlencoded
DPoP: eyJ0eXAiOiJkcG9wK2p3dCIsImFsZyI6IkVTMjU2IiwiandrIjp7…

grant_type=authorization_code&code=SplxlOBeZQQYbYS6WxSbIA&code_verifier=…
```

The AS checks the proof, computes the thumbprint of its `jwk`, and binds the token to it. A JWT
access token carries the thumbprint in a **confirmation claim**, `"cnf": {"jkt": "0ZcOCOR…"}`
(`jkt` stands for "JWK thumbprint"). An **opaque** token, a random string with nothing readable
inside, has the thumbprint stored at the AS instead; the API asks the AS about the token (this is
called **token introspection**), and the AS's answer includes the same `cnf`. The token response
says `"token_type": "DPoP"` instead of `"Bearer"`. If it says `Bearer`, the AS chose not to bind the
token, and a client that depends on the protection must refuse it.

The figure shows the two hashes that tie a request to the key: one inside the token, pointing at
the key, and one inside the proof, pointing at the token.

<Figure caption="Two hashes chain the request to the key. cnf.jkt in the token is the thumbprint of the client's public key; ath in the proof is the hash of the token. The API recomputes both, and both must match.">
  <Binding />
</Figure>

The API call then uses the `DPoP` authorization scheme and a fresh proof:

```http
GET /orders HTTP/1.1
Host: api.example.com
Authorization: DPoP Kz~8mXK1EalYznwH-LC-1fBAo.4Ljp~zsPE_NeO.gxU
DPoP: eyJ0eXAiOiJkcG9wK2p3dCIsImFsZyI6IkVTMjU2IiwiandrIjp7…
```

Notice what the server trusts. The `jwk` in a proof is self-asserted: anyone can make a key pair and
sign a perfect proof with it. A proof only means something next to a token whose `cnf.jkt` the AS
recorded. So DPoP is not **client authentication**, proof of which app is calling; it proves
continuity. The key that asked for this token is the key using it.

### What the API checks, and what each check stops

RFC 9449 lists the checks in its section 4.3. Grouped by the attack each one answers:

| Check | Stops |
|---|---|
| Exactly one `DPoP` header, a well-formed JWT, all required claims | malformed and ambiguous requests |
| `typ` is `dpop+jwt`; `alg` is a public-key algorithm the server allows | another signed JWT used as a proof; `alg: none` |
| Signature verifies with the `jwk` in the header, which has no private part | a forged or edited proof |
| `htm` and `htu` match this request | a captured proof used on another endpoint or method |
| `iat` within a short window | old captured proofs |
| `jti` not seen before for this URL | a captured proof replayed inside the window |
| `nonce` matches one the server issued recently | proofs signed in advance |
| `ath` equals the hash of the token | a proof for one token used with another |
| Thumbprint of `jwk` equals the token's `cnf.jkt` | a stolen token used with the thief's own key |

Our example server runs these checks in both languages. Its first experiment is Part 1's thief,
for real: the same stolen token, used from another machine in five ways.

```text
1. A token copied from a log file, used from another machine
   bearer token, no proof                         200 OK
   DPoP token, no proof                           rejected: no DPoP proof
   DPoP token, proof signed with thief's key      rejected: proof key does not match the token's cnf.jkt
   DPoP token sent as Bearer                      rejected: DPoP-bound token sent as Bearer
   same, to a server that predates DPoP           200 OK
```

The last line is not a bug in the example. JWT rules tell a server to ignore claims it does not
understand. So an API that has never heard of DPoP skips the `cnf` claim and accepts the token as a
bearer token. The gotchas come back to this.

### Replay: the window and the jti store

A **replay** is sending a captured request again, unchanged. A thief who captures a whole request,
token and proof together, from a log or a proxy, holds a valid pair. Two checks stand between them
and a replay.

The first is the `iat` window: how old a proof may be. The spec asks for "seconds or minutes"; we use
60 seconds, plus 5 seconds of allowance for a client whose clock runs ahead of the server's, so a
proof is accepted for at most 65 seconds. Inside those 65 seconds, only the second check stops the
same proof from working again: the `jti` check. And it only works if the server remembers.

That memory is the part people underestimate. The server must keep every `jti` it accepted, for each
target URL, for as long as the proof could still pass the window check: one entry per request, kept
65 seconds. Take an API serving 1,000 requests a second:

1. Each second adds 1,000 entries, and each entry lives 65 seconds.
2. So at any moment the store holds 1,000 entries a second × 65 seconds = 65,000 entries.
3. If each entry costs about 100 bytes, once the store's own bookkeeping is counted (an illustrative
   figure, not a benchmark), that is 65,000 × 100 bytes = 6,500,000 bytes, about 6.5 megabytes.

Store a hash of the `jti` rather than the value, and reject oversized ones, or an attacker fills your
memory with `jti` values a megabyte long.

The memory must also be shared by every server that accepts proofs for that URL. Most APIs run as
several copies, called **instances** or nodes, behind a **load balancer** that spreads requests
across them. If each instance keeps its own list of seen `jti` values, a replay sent to a different
instance finds an empty list. Our second experiment sends the real request to node 0 of four, then
replays the captured pair in several ways:

```text
2. One real request captured with its proof, then replayed
   the real request                               200 OK
   replayed 2 s later                             rejected: jti already used
   replayed as DELETE /orders/7                   rejected: htm is GET, request is DELETE
   replayed to 4 nodes, each with its own cache   3 of 4 accepted
   replayed 61 s later                            rejected: iat outside the window
```

Read the fourth line like this. Node 0 handled the real request, so it remembers the `jti` and
rejects the replay. Nodes 1, 2 and 3 never saw that `jti`, so each of them accepts it once: 3 of 4.

The fix is one store that all instances share. **Redis** is the usual choice: a fast in-memory
key-value store that many servers can reach over the network. Its command `SET key value NX EX 65`
writes the key only if it does not already exist (`NX`, "not exists") and deletes it after 65
seconds (`EX`, "expire"). Two instances that try to record the same `jti` at the same moment cannot
both succeed: the first write wins and the second one fails.

<Figure caption="With a cache per node, a captured proof is accepted once by every node that has not seen it yet. A shared store, such as one Redis SET with NX and an expiry, accepts it once in total.">
  <ClusterReplay />
</Figure>

The spec admits that strict single use "may not always be feasible" when servers share no state.
That is why the window must stay short either way: with a cache per node and a 60-second window, a
captured proof can be replayed at most once per node within that minute, and only at the one
endpoint the proof names.

### Server nonces: proofs signed in advance

The `iat` claim is chosen by the client. That is fine while the client is honest, and fatal when it
is not. The dishonest client here is an attacker's script running inside your page.

**Cross-site scripting** (XSS) is a bug that lets an attacker run their own JavaScript inside your
page, for example by getting a comment containing a `<script>` tag shown unescaped, or by
compromising a third-party script your page loads. That script runs with the same powers as your own
code.

Suppose such a script runs on your page for a moment. It cannot read the private key out (the
section on keys below shows why), but it can call `sign()` with it. Here is what it does:

1. It signs 20 proofs for `GET /orders`, with `iat` set 30 seconds apart, so they cover the next
   20 × 30 seconds = 600 seconds, 10 minutes.
2. It sends them home, with the access token, and stops.
3. The attacker uses each proof when its `iat` comes round. Each one has its own `jti`, and each
   one's `iat` is "now" at the moment it is used, so the window and the `jti` store both accept it.

A **nonce** ("number used once") is a value the server makes up, unpredictably, and hands out. It
exists so that the server, not the client, decides how fresh a proof is: a proof that contains a
nonce cannot have been made before the server handed that nonce out. For example, the server
answers a request with the header `DPoP-Nonce: kQ3v…`, and the next proofs must carry
`"nonce": "kQ3v…"`. A proof signed at 08:00 for use at 08:09 would have to contain the nonce the
server will hand out at 08:09, which nobody knows at 08:00. In the protocol, the server sends the
nonce in a `DPoP-Nonce` response header, requires it in the `nonce` claim, and decides when each
nonce stops being accepted, so pre-signed proofs die when the nonce they carry does.

The nonce does not have to be stored. Our example builds it from two parts. The first is the number
of the current 60-second period, counted from 1970. The second is an **HMAC** of that number: a
fingerprint that only someone holding a secret key can compute, here a key known only to the
servers. For example, at 08:00:00 the period number is 1,800,000,000 seconds ÷ 60 = 30,000,000,
and its HMAC is 16 bytes that look random; for period 30,000,001 the 16 bytes are completely
different, and without the servers' key nobody can compute either.

When a proof arrives, any server holding the key recomputes the HMAC for the current period
and for the previous one, and accepts the nonce if it matches either. Accepting the previous period
too means a client that fetched its nonce a moment before a change is not turned away. And because
the nonce carries the server's own time, it also limits a proof's age when the client's clock is
wrong by hours.

The third experiment runs the script attack above against a 5-minute access token:

```text
3. Script injected into the page signs 20 proofs for the next 10 minutes, then leaves
   no server nonce                                10 of 20 accepted, the last at t+270 s
   nonce, rotated every 60 s                      4 of 20 accepted, the last at t+90 s
```

Here is where those counts come from. `t` is the moment the script ran, so `t+270 s` means 270
seconds later. The 20 proofs are for 0, 30, 60 and so on up to 570 seconds after `t`.

- **No nonce.** The token expires at 300 seconds, and `ath` ties every proof to that one token. The
  proofs for 0, 30, 60 … 270 seconds come before the expiry. Counting them: 270 ÷ 30 = 9 steps of
  30 seconds after the first proof, so 9 + 1 = 10 proofs. The one for 300 seconds and every later one fail with the
  token.
- **Nonce, changed every 60 seconds.** The script got its nonce at the start of a 60-second period.
  The server accepts it during that period and the next one, 120 seconds in all. The proofs for 0,
  30, 60 and 90 seconds fall inside: 4 proofs. The one for 120 seconds is rejected.

So without a nonce, pre-signed proofs work until the access token expires. The attacker cannot
pre-sign proofs for a token that does not exist yet, which is why the spec says deployments without
nonces should not issue long-lived DPoP access tokens. With a nonce, they last at most two nonce
periods.

The simulation puts these defences in one place. From the first second, an attacker holds three
things: a token copied from a log, one complete captured request, and a stash of proofs signed in
advance. They try each one every 10 seconds for ten minutes against your API. You choose the
defences.

### Refresh tokens and authorization codes

A stolen access token dies with its lifetime. A refresh token is the real prize, so DPoP binds it
too, with one distinction between two kinds of client.

A **public client** is an app that cannot keep a secret of its own: a browser app or a mobile app,
whose code anyone can download and read. A **confidential client** is a backend server that proves
its identity to the AS with a secret or a signed statement of its own, kept on the server.

- For a public client, the AS must bind the refresh token to the DPoP key, and every refresh needs a
  proof from that key.
- For a confidential client, refresh tokens are not bound to the DPoP key. They are already bound to
  the client's own credentials, and binding them to a key as well would stop the client from
  changing its credentials without logging every user out.

An AS may also bind only the refresh token and hand out ordinary bearer access tokens. Keycloak 26.4
offers exactly that for public clients. It is a sensible first step: APIs need no change, and the
long-lived credential, the kind stolen in the incidents above, is protected.

One gap remains before the first token. An authorization code stolen from a redirect URL or a log
can be redeemed by the thief with their own key, and the tokens are then bound to the thief.
**PKCE** (Proof Key for Code Exchange) already stops this when the thief has only the code: the
client makes up a random secret before the login, sends only a hash of it when the login starts,
and later sends the secret itself with the code, as the `code_verifier` seen in the token request
above. The AS refuses the code unless the two match.

The `dpop_jkt` parameter goes further: the client puts its key's thumbprint in the authorization request, and the AS refuses
to redeem the code with a proof from any other key. It helps only if the client uses a new key for
each authorization. **FAPI 2.0**, the OpenID Foundation's security profile for open banking and other
high-value APIs, requires servers to support it.

### Where the key lives, and what script on the page can still do

DPoP is only as strong as the private key's hiding place. In a browser, the built-in **Web Crypto**
API creates keys with an `extractable` flag. With `extractable: false`, the call that exports a key,
`exportKey()`, throws an error, and the key's bytes are never exposed to JavaScript. The key object
can still be saved in IndexedDB, the browser's built-in database, and used for signing after the page
reloads.

On mobile, the phone's key stores (Android Keystore, the iOS Secure Enclave) hold keys that the app
can use but not read. On a server, the key belongs in a **KMS** (key management service, a separate
locked-down service that holds keys and signs on request without handing the keys out) or an **HSM**
(hardware security module, a tamper-resistant device built for the same job). At the very least it
belongs outside the database where the tokens are kept.

"Cannot be read" is not "cannot be used". RFC 9449 is direct that once an attacker runs code in the
client, DPoP's guarantees are gone, and it puts that case out of its scope. The figure lists what
injected script can and cannot do when the key is non-extractable.

What DPoP does give you against script on the page: a token and a refresh token that the script
sends home are worthless on their own. Anything it does afterwards needs the victim's page to stay
open, or proofs it pre-signed, which a nonce and a short token lifetime cut short.

What it does not give you: protection while the page is open. Nor does it stop the last row of the
figure. The script can open a hidden frame (an `iframe`) that starts a new login with a key of the
script's own. If the user is still signed in at the AS, the AS may finish that login without asking
the user anything (a **silent login**), and the new tokens are bound to the attacker's key. Content
Security Policy, a header that tells the browser which scripts may run, and the rest of the XSS
defences still decide that; the XSS topic in "Where to go next" covers them.

## Choosing between them

**RFC 9700** ([OAuth 2.0 Security Best Current Practice](https://www.rfc-editor.org/rfc/rfc9700),
January 2025) is the IETF's current rulebook for using OAuth safely, and it sets the floor in this
table. One term first: **refresh token rotation with reuse detection** means every refresh hands out
a new refresh token and retires the old one, and if a retired one is ever used again, the AS knows
one copy was stolen and cancels the whole session.

| Approach | What a stolen token is worth | What it costs | Fits |
|---|---|---|---|
| Bearer, long-lived | full access until expiry or revocation | nothing | nothing you would choose today |
| Bearer, short-lived, rotated refresh | a few minutes; the refresh token until reuse is noticed | refresh traffic | low-value APIs; the minimum RFC 9700 accepts for public clients |
| DPoP | nothing alone; captured proofs only inside the window | a signature per request, a `jti` store, nonce round trips | browser and mobile apps, public clients, APIs you do not all control |
| mTLS-bound (RFC 8705) | nothing alone | client certificates, TLS termination that forwards them | server-to-server, open banking, private service-to-service networks |
| HTTP Message Signatures | nothing alone, and the body is protected | rewriting headers into one exact form on both sides, more code | requests whose content must be provably unaltered |

How to choose: for browser and mobile apps, use DPoP. Start with refresh tokens if your APIs are not
ready, then bind access tokens once every API enforces it. For backend-to-backend calls where you
already run mTLS, bind tokens to the certificate and skip DPoP. RFC 9700 requires the refresh tokens
of public clients to be either sender-constrained or rotated with reuse detection, and recommends
sender-constrained access tokens.

## Build it yourself

The client side is one function: build the header and claims, then sign. An ES256 signature in a JWT
is the two 32-byte numbers `r` and `s` placed side by side. Python's `cryptography` package returns
them packed in a different format, called DER, so the example unpacks them. JavaScript's
`node:crypto` returns them side by side when asked with `dsaEncoding: 'ieee-p1363'`.

def make_proof(key, htm: str, htu: str, *, now: float, access_token: str | None = None,
               nonce: str | None = None, iat: float | None = None) -> str:
    """One DPoP proof: a JWT signed with the client's private key, valid for one request."""
    header = {"typ": "dpop+jwt", "alg": "ES256", "jwk": public_jwk(key)}
    claims = {"jti": str(uuid.uuid4()), "htm": htm, "htu": htu, "iat": int(iat if iat is not None else now)}
    if access_token:
        claims["ath"] = sha256_b64(access_token)  # ties this proof to this one token
    if nonce:
        claims["nonce"] = nonce  # proves the proof was made after the server said this
    compact = {"separators": (",", ":")}
    signing_input = f"{b64url(json.dumps(header, **compact).encode())}.{b64url(json.dumps(claims, **compact).encode())}"
    r, s = decode_dss_signature(key.sign(signing_input.encode(), ec.ECDSA(hashes.SHA256())))
    return f"{signing_input}.{b64url(r.to_bytes(32, 'big') + s.to_bytes(32, 'big'))}"

/** One DPoP proof: a JWT signed with the client's private key, valid for one request. */
export function makeProof(key, htm, htu, { now, accessToken, nonce, iat } = {}) {
  const header = { typ: 'dpop+jwt', alg: 'ES256', jwk: key.jwk };
  const claims = { jti: randomUUID(), htm, htu, iat: Math.floor(iat ?? now) };
  if (accessToken) claims.ath = sha256b64(accessToken); // ties this proof to this one token
  if (nonce) claims.nonce = nonce; // proves the proof was made after the server said this
  const signingInput = `${b64json(header)}.${b64json(claims)}`;
  const sig = sign('sha256', Buffer.from(signingInput), { key: key.privateKey, dsaEncoding: 'ieee-p1363' });
  return `${signingInput}.${b64url(sig)}`;
}

export function checkProof(proof, { method, url, now, jtiStore, accessToken, boundJkt, nonces }) {
  const [h64, c64, s64] = proof.split('.');
  let header, claims;
  try {
    header = JSON.parse(Buffer.from(h64, 'base64url'));
    claims = JSON.parse(Buffer.from(c64, 'base64url'));
  } catch {
    throw new Rejected('not a JWT');
  }

  let ok = false;
  try {

`cnf.jkt`). Only when everything has passed, record the `jti`.

## How real systems do it

**Bluesky** (the AT Protocol) requires DPoP of every client. Its OAuth profile, read in October 2026,
makes DPoP mandatory at the authorization server and at each user's data server, makes server nonces
mandatory, and requires servers to change them at least every 5 minutes, while accepting a recently
replaced nonce so that requests sent shortly before a change still succeed. Clients must make a new DPoP key
for every session and device. Access tokens should live under 30 minutes (5 recommended), and a
public client's whole session at most two weeks
([AT Protocol OAuth spec](https://atproto.com/specs/oauth)). Every rule on this page is in there,
turned to the strict setting.

**Okta** answers a client's first token request with `400 use_dpop_nonce` and a `dpop-nonce` header.
Its nonce changes every 24 hours, and an old one keeps working for three days
([Okta DPoP guide](https://developer.okta.com/docs/guides/dpop/main/), as of October 2026). Compare
that with Bluesky's 5 minutes: at the token endpoint, a nonce that lives for days does almost nothing
against proofs signed in advance, and the remaining limit is the lifetime of the tokens those proofs
are tied to. Okta's guide also tells resource servers to track the `jti` of every proof and reject
repeats.

**Keycloak**, an open-source authorization server, shipped DPoP as a preview from version 23 and
declared it fully supported in 26.4 (September 2025). It can bind only the refresh tokens of public
clients, has a setting that requires `dpop_jkt` in every authorization request, and has client
profiles for FAPI 2.0 with DPoP ([Keycloak, 2025](https://www.keycloak.org/2025/10/dpop-support-26-4)).

**Spring Security**, the standard security library for Java's Spring framework, added DPoP support
for resource servers in 6.5 (2025). As of October 2026 its default replay check (since 6.5.12) keeps
`jti` values in an in-memory cache, separate for each running instance of the application, for 30
seconds past `iat`, with at most 100,000 entries and 1,000 proofs per key. It compares `htu` with the
request URL as an exact string. Both defaults matter in the gotchas below.

**FAPI 2.0** (final in February 2025) allows only sender-constrained access tokens, by mTLS or DPoP.
With DPoP, servers are expected to use nonces and must support binding the authorization code with
`dpop_jkt` ([FAPI 2.0 Security Profile](https://openid.net/specs/fapi-security-profile-2_0.html)).

## Gotchas and war stories

:::caution[The URL your app sees is not the URL the client signed]
A load balancer often handles the TLS connection itself and passes plain HTTP to the instances
behind it. The app then sees `http://10.0.3.7:8080/orders` while the client signed
`https://api.example.com/orders`, and every proof fails `htu`. Our fourth experiment shows it:
`rejected: htu is https://api.example.com/orders, request is http://10.0.3.7:8080/orders`. Build the
URL from the configured public address, or from the `X-Forwarded-Proto` and `X-Forwarded-Host`
headers that only your own proxy can set, never from the connection. The spec asks servers to
normalise before comparing: lower-case the scheme and host, drop default ports such as `:443`, and
write `%`-escaped characters one standard way. An exact string match, as in Spring's default,
rejects `HTTPS://API.example.com:443/orders`, which the spec would accept.
:::

:::caution[A replay cache per instance is a replay cache per instance]
An in-memory `jti` cache, the default in more than one library, lets a captured proof through once
on every instance behind the balancer, as the second experiment showed: 3 of 4. Put the store where
all instances share it, as one `SET key 1 NX EX 65` in Redis per proof, keyed by a hash of
URL and `jti`. If that is not possible, keep the window short, because it is then your only limit.
:::

:::danger[Every API must refuse a bound token sent as Bearer]
A DPoP-bound access token is a perfectly good bearer token to any API that does not know DPoP. If
the public gateway (the front server all outside traffic passes through) enforces DPoP but internal services also accept the same tokens with
`Authorization: Bearer`, a thief who can reach one internal service, or one old API that accepts the
same tokens, uses the stolen token without a key. RFC 9449 requires an API that supports both
schemes to reject a DPoP-bound token presented as `Bearer`; an API that knows nothing of DPoP cannot.
Bind access tokens only when every API that accepts them checks the binding, and bind only refresh
tokens until then.
:::

:::danger[DPoP on a backend only helps if the key is not next to the tokens]
GitHub's and Salesloft's stolen tokens were held by backend services. A DPoP key stored in the same
database or the same environment variables as the tokens is stolen with them, and the binding
protects nothing. Keep the key in a KMS or HSM that signs on request, so that the attacker has to
keep control of your signing service, not copy a file. And remember that a confidential client's
refresh tokens are bound to its client credentials, not to the DPoP key: a stolen client secret plus
a refresh token is still a working pair.
:::

:::caution[Retries, nonce changes and CORS]
A proof is single-use, so a retried request needs a new proof; a client library that resends the
same headers after a network error gets `jti already used`. Nonces change while requests are on
their way: accept the previous nonce for a short while, and make clients retry once on `use_dpop_nonce`
with the new value. Finally, CORS (Cross-Origin Resource Sharing, the browser's rules for
reading responses from another site): a browser app's JavaScript cannot read a response header from
another origin (a different scheme, host or port: `app.example.com` reading from
`api.example.com`) unless the API lists it in `Access-Control-Expose-Headers`. If `DPoP-Nonce` and
`WWW-Authenticate` are missing from that list, the app never sees the new nonce, and you get an
endless loop of 401s.
:::

## Trade-offs and when not to use it

DPoP moves cost from the moment of theft to every request. The client signs every call (85 µs, about
0.1 ms, in our measurement, more in a browser). Every request carries the 530-byte proof, about half
a kilobyte more. The API verifies a signature and writes to a shared store on every call, where a
bearer token needed a cached signature check. Nonces add a round trip per server each time they
change, and clients need a retry path for them. The server now holds state for authentication that
used to need none.

DPoP does not protect the request body or headers: it relies on TLS for that. It does not
authenticate the client: anyone can make a key. It does not help once an attacker runs code inside
the client, beyond making that attacker stay online. And it protects only at APIs that enforce it,
so a token accepted anywhere as a bearer token is a bearer token.

Skip it, or wait, when the calls are server-to-server inside a network that already runs mTLS (bind
tokens to the certificate instead); when tokens are short-lived, low-value and used by one API you
control; or when you cannot yet make every API that accepts the tokens enforce the binding, in which
case start with refresh tokens only.

## Interview corner

DPoP comes up in designs for single-page apps, mobile apps and "how would you protect tokens if one
leaks". A strong answer names what it stops, what it does not, and the server state it needs.

- **"What is the difference between a bearer token and a sender-constrained token?"** Possession of
  a bearer token is enough; a sender-constrained token also needs proof of a key (DPoP) or a client
  certificate (mTLS) recorded in the token as `cnf`. Give one way bearer tokens leak: logs, XSS, a
  breached integration partner.
- **"What does a DPoP proof sign, and why not the body?"** Method, URL without query, time, a unique
  ID, the token's hash, and the server nonce when there is one. Signing the whole message needs both
  sides to rebuild it exactly, which proxies break; TLS already protects the body in transit.
- **"You run 20 API instances. How do you prevent replay?"** A short `iat` window and a shared `jti`
  store with an expiry equal to the window, keyed by URL and a hash of the `jti`; say what a
  per-instance cache lets through.
- **"Does DPoP protect a single-page app against XSS?"** Only partly. Tokens taken away are useless;
  the script can still use the non-extractable key while the page is open, pre-sign proofs (stopped
  by nonces and short tokens) and start a fresh login with its own key. Preventing XSS is still
  required.

## Check yourself

<details>
<summary>1. An attacker reads an access token and a refresh token from a public client's log file. Both are DPoP-bound. What can they do with them?</summary>

Nothing, on their own. Every API call needs a proof signed by the client's private key whose
thumbprint matches the token's `cnf.jkt`, and every refresh needs a proof from the same key. A proof
signed with the attacker's key fails the thumbprint check. The exception is any API that accepts the
access token as a bearer token.

</details>

<details>
<summary>2. Your API checks the iat window (60 s) and the signature, but keeps no jti store. A proxy logs one full request, token and proof. What can an attacker do with it?</summary>

Replay that exact request, same method and URL, as many times as they like for up to 60 seconds after
the proof was made. Nothing else: `htm`, `htu` and `ath` stop it from being used on any other
endpoint or with any other token. A shared `jti` store would let it through zero times.

</details>

<details>
<summary>3. Why can't the jti store and the iat window stop proofs signed in advance by injected script?</summary>

Each pre-signed proof has its own unique `jti`, and its `iat` was set to the moment it would be used,
so it is fresh when it arrives. Only something the client could not know at signing time stops it: a
server nonce issued later, or the access token expiring, since `ath` ties the proofs to that one
token.

</details>

<details>
<summary>4. After you enable DPoP behind your load balancer, every API call fails with an htu mismatch, but calls straight to one instance work. What is happening?</summary>

The instance rebuilds the request URL from the connection it received, `http://` and an internal host
and port, while the client signed the public `https://` URL. Build the URL from the configured public
address or from forwarded headers set by your own proxy, and normalise before comparing.

</details>

<details>
<summary>5. Why are a confidential client's refresh tokens not bound to its DPoP key?</summary>

They are already bound to the client: the client must authenticate to the AS with its own credentials
to use them. Binding them to a DPoP key as well would add little, and the client could not change the
key without invalidating every user's refresh token.

</details>

## Recap

- A bearer token works for whoever holds it; DPoP adds a per-request proof signed by a key whose
  thumbprint the AS writes into the token as `cnf.jkt`.
- The proof signs the method, the URL without query, `iat`, a unique `jti`, the token's hash `ath`,
  and the server's `nonce` when there is one. Not the body or headers.
- The API checks signature, `typ`, `alg`, `htm`, `htu`, window, nonce, `ath` and the thumbprint;
  stopping replay inside the window needs a `jti` store shared by every instance.
- Server nonces are the only defence against proofs signed in advance; short access tokens limit the
  rest.
- Public clients' refresh tokens are bound to the key; confidential clients' are bound to their
  credentials. `dpop_jkt` binds the authorization code.
- Script running in the client can still use a non-extractable key. Every API that accepts the token
  must refuse it as `Bearer`.
